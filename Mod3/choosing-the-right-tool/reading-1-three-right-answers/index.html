Three Right Answers, One Good Choice

A gym chain sends you two requests before 10 a.m. Both can be answered in SQL. Both can be answered correctly in more than one way. Nothing here is about a query that breaks. It is about standing in front of three tools that all work and saying out loud why you picked the one you picked.

1. Introduction

Northline Fitness is a made-up gym chain used throughout this reading. It runs six gyms in different neighborhoods under one brand. Each gym is called a location. The locations are grouped into three regions, which is just the company's word for "part of the map": North, East, and South. Head office watches how many new members sign up at each location every month.

Two requests land in your inbox the same morning.

  1. The operations lead writes: "Which locations had more new sign-ups than the chain-wide average?"
  2. A regional manager writes: "List every location next to its own region's average, so we can see how far off each one is."

Those two sentences sound like the same kind of question. They are not. The first one wants a shorter list: the six locations go in, and only the ones above a single number come back. The second one wants a wider table: all six locations come back, each carrying an extra number beside it. Look at the shape of each answer before you look at any code.

The gold table on the left is short because three locations were dropped. The blue table on the right is the full six, with one extra column bolted on. Notice that 102.50 shows up twice, and so does 120.00. That is not a mistake. The average belongs to the region, so every location in that region carries the same value.

Why this matters: nobody is going to hand you a ticket that says "use a common table expression here." You get a sentence in plain English and you pick the tool. In a code review, "it returns the right rows" is the floor, not the bar. The question you actually get asked is why you wrote it this way instead of the other way, and "I just like CTEs" is not an answer. Data-analyst interviews ask this directly: "what is the difference between a common table expression and a subquery, and when would you use each?" is one of the most commonly asked SQL questions in the field.

Where you're coming from, where this is headed: you already know how to nest one query inside another, how to name a step with WITH, and how to write a window function that keeps every row. Nothing new gets installed here. What gets added is a short routine for choosing between them, and the habit of writing your reason down in one sentence. That habit carries straight into schema documents, code reviews, and every technical conversation with someone who does not write SQL.

Three skills are prerequisites for what follows: summarizing rows with GROUP BY, filtering a summarized result with HAVING, and naming a step with WITH. Check each one before moving on.

3. One question, written two ways

Start with the first request: which locations had more new sign-ups than the chain-wide average? Northline stores this across two tables, which is normal for a real database.

Because sign-ups are stored one row per person, the query has to do two things. It has to count sign-ups per location, and it has to know the average of those counts. Here is the version that does both without naming anything.

SELECT l.location_name, COUNT(s.signup_id) AS sign_ups FROM locations AS l LEFT JOIN signups AS s ON s.location_id = l.location_id GROUP BY l.location_name HAVING COUNT(s.signup_id) > ( SELECT AVG(per_loc.n) FROM ( SELECT COUNT(s2.signup_id) AS n FROM locations AS l2 LEFT JOIN signups AS s2 ON s2.location_id = l2.location_id GROUP BY l2.location_name ) AS per_loc );

The LEFT JOIN is doing one small but important job there. It keeps a location in the result even if nobody signed up at it that month, so a quiet location shows a count of 0 instead of vanishing.

That query is correct. It returns Southgate at 205, Bayview at 148, and Eastport at 131, because the chain-wide average is 126.67 sign-ups per location. Say the "it is correct" part out loud, because the instinct on first read is that something must be wrong with it. Nothing is. Plenty of working SQL looks exactly like this.

There are two kinds of subquery packed in there, and both deserve a name.

  • A scalar subquery is a query inside another query that hands back exactly one value. The whole (SELECT AVG(per_loc.n) FROM ...) is one, because it produces a single number: 126.67. That is what makes it usable on the right side of a > comparison.
  • A derived table is a subquery written inside a FROM clause and given a name, so the query around it can read from it like a table. Here that is (SELECT COUNT(...) ... GROUP BY l2.location_name) AS per_loc. It only exists for as long as this one query runs. Nothing is stored.

Now count how many times the counting step appears in that query. Twice, nearly character for character. The day a third table joins the picture, there are two places to edit, and one of them sits five lines deep inside a HAVING clause. Here is the same answer with that step named once.

WITH per_location AS ( SELECT l.location_name, l.region, COUNT(s.signup_id) AS sign_ups FROM locations AS l LEFT JOIN signups AS s ON s.location_id = l.location_id GROUP BY l.location_name, l.region ) SELECT location_name, sign_ups FROM per_location WHERE sign_ups > (SELECT AVG(sign_ups) FROM per_location);

Same three locations, same three numbers. What changed is that the counting step now has a name, so it can be pointed at, reused without retyping, and run on its own. That last one is worth showing rather than asserting. Swap the final SELECT for this:

SELECT * FROM per_location;

Now you can see all six counts before any filtering happens, and check two of them by hand against something you already know. There is no equivalent move on the nested version without cutting the query apart first.

Notice what did not change: correctness. Both queries return the same rows in the same order. The CTE version is not more correct and it is not measurably faster on six rows. What it buys you is a middle step you can inspect and a step you only have to edit in one place. Those are the real costs the nested version charges you, and naming them precisely is what separates a reviewed opinion from a preference.

A word of caution that catches people in interviews: claims like "CTEs are always slower" are about a specific database engine and a specific version, not about SQL in general. If performance comes up, name the engine you mean and say you would check the query plan rather than quote a rule.

5. Type the keyword

Here is the top of the CTE version with one word removed. It is the keyword that opens a named step.

______ per_location AS ( SELECT l.location_name, l.region, COUNT(s.signup_id) AS sign_ups FROM locations AS l LEFT JOIN signups AS s ON s.location_id = l.location_id GROUP BY l.location_name, l.region ) SELECT location_name, sign_ups FROM per_location;
Need a hint?

It is a single four-letter word, and it is the first thing on the line. Section 2's third question named it.

6. Turning a nested query into a named one

Rewriting the first version into the second is a repeatable routine, not a flash of insight. Click the steps below into the order you would actually do them, then self-check.

  • Find the step that appears more than once, or the one you keep having to re-read.
  • Copy that step out and put it at the top of the query inside WITH ... AS ( ... ).
  • Give it a short, plain name that says what it holds, such as per_location.
  • Replace every copy of that step in the rest of the query with the name.
  • Run SELECT * FROM per_location; on its own and check a couple of numbers by hand.

This matters when an AI assistant writes the query for you. Ask an AI tool to "make this query cleaner" and it will usually hand back a CTE version without being asked. Often it is a fine rewrite. Sometimes it quietly changes a LEFT JOIN to an inner join, or drops a column from the GROUP BY, and the row count moves. The check in the last step is exactly how you catch that: run the named step on its own, and confirm the row count and a couple of values match what you had before the rewrite.

7. The second request: when every row has to stay

Now the regional manager's request. List every location next to its own region's average. Read that sentence for shape rather than for keywords. Every location has to survive, and each surviving row needs a number that belongs to its region.

Here is the honest long way around, written on top of the same named step.

WITH per_location AS ( SELECT l.location_name, l.region, COUNT(s.signup_id) AS sign_ups FROM locations AS l LEFT JOIN signups AS s ON s.location_id = l.location_id GROUP BY l.location_name, l.region ) SELECT location_name, region, sign_ups, (SELECT ROUND(AVG(p2.sign_ups), 2) FROM per_location AS p2 WHERE p2.region = per_location.region) AS region_avg FROM per_location ORDER BY region, sign_ups DESC;

That returns all six locations with the right averages. Look closely at the inner query: it mentions per_location.region, which is a column belonging to the outer query. That dependency is the whole definition of a correlated subquery, a subquery that re-runs for every row of the outer query. Copy that inner query out and paste it into a database client on its own and it fails, because there is no outer row for it to point at.

In plain language, that query says: for each location, go and work out that location's region average. Six locations means the question is asked six times. On six rows nobody notices. On six million, that per-row repetition is exactly why a correlated subquery gets a reputation for being slow.

Here is the same answer in one line.

WITH per_location AS ( SELECT l.location_name, l.region, COUNT(s.signup_id) AS sign_ups FROM locations AS l LEFT JOIN signups AS s ON s.location_id = l.location_id GROUP BY l.location_name, l.region ) SELECT location_name, region, sign_ups, ROUND(AVG(sign_ups) OVER (PARTITION BY region), 2) AS region_avg FROM per_location ORDER BY region, sign_ups DESC;

AVG is the same function it has always been. OVER (PARTITION BY region) is what turns it into a window function: instead of collapsing the three regions into three rows, it works out each region's average and writes it beside every row in that region. The two-line correlated subquery collapsed into a single expression, and the second read of per_location disappeared.

Worth memorizing: GROUP BY region would have returned 3 rows. PARTITION BY region returns all 6. They read alike and they do opposite things to your row count.

8. Read the request, not the keywords

Before any tool gets picked, the request itself tells you whether the rows are meant to survive. Drag each phrase into the shape it points at, then self-check.

"every location listed" "next to its own region's average" "the two regions with the highest average" "one number for the whole chain"

Rows survive

Rows collapse

Words like "each," "every," and "alongside" are usually a sign the rows are meant to survive. Words like "total," "top," and "per region" are usually a sign they are meant to collapse. Usually, not always, which is why the routine below has four checks and not one.

9. Four checks before you pick a tool

This is the routine. It is short on purpose, because a routine you cannot say out loud in an interview is not a routine.

  1. Shape. Does the answer need one value, or a whole set of rows?
  2. Rows. Does every original row need to survive, with something added beside it?
  3. Check. Will you need to run a middle step on its own to trust the result?
  4. Reader. Who opens this query after you do, and what will they have to hold in their head?

Run it on the two requests from the introduction and watch it do real work.

  • Request 1. Shape: one number, the chain-wide average. Rows: no, the answer is a shorter list. Check: yes, the counting step is the part most likely to be wrong. Reader: a dashboard someone else maintains. That lands on a CTE holding the counts, with a small scalar subquery inside it.
  • Request 2. Shape: a whole set of rows. Rows: yes, every location has to stay. Check: yes, same counting step. Reader: regional managers who will ask you to change it. That lands on a window function, sitting on top of the same CTE.

The checks do not add up to a score, and the tools do not compete. Request 2's answer used a CTE and a window function in the same query. Picking one tool almost never rules the others out. The checks exist to make your reasoning sayable, which is the part that actually gets assessed.

The check people skip is the last one. Shape, rows, and inspection all feel technical, so they get considered. Who has to read the query next is the one that quietly decides whether a codebase stays workable, and it is the one a working analyst gets judged on.

10. Decision drill

Four requests, in the words they would actually arrive in. For each one, run the four checks in your head, then pick the tool.

Request: "Only show me the locations whose monthly revenue is above the chain-wide average revenue." Revenue is already a column on the locations table, so nothing has to be counted first. Which tool fits?

Request: "Count personal-training sessions per trainer, then list only the trainers above the average. And let me see the raw counts too, because last month's numbers looked off." Which tool fits?

Request: "Put every group class on the schedule next to the average attendance for its own time slot, so we can see which ones are under-filled." Which tool fits?

Request: "Which two regions have the highest average sign-ups per location?" Which tool fits?

Now write one sentence. A new request arrives: "Give me every personal trainer next to the average client rating at their own home location." Run the four checks, then name your tool and the single check that decided it, in one sentence.

13. How this shows up in interviews

"What's the difference between a CTE and a subquery, and when would you use each?" is a standard data-analyst interview question. The weak answer recites every fact the candidate knows about both. The strong answer is four short beats: state the difference in one sentence, say why it matters, give one real example from something you actually built, then close with a decision rule.

Two traps are worth naming. The first is answering with an unscoped performance claim, because the follow-up is always "in which database, and which version?" The second is forgetting the next reader. Interviewers asking this want to see that you write code other people can pick up, so an answer that never mentions whoever maintains the query next has missed what the question is for.

Interview-style question: a product manager, who does not write SQL, asks why you spent an afternoon rewriting a query that already worked. What is the strongest response?

14. Summary and critical thinking

Three ideas carried this reading. First, a nested subquery and a CTE can return identical rows, and what separates them is whether the middle step can be named, reused, and checked on its own. Second, some questions need every original row to survive with a group value beside it, and that shape belongs to a window function, not to GROUP BY. Third, correctness is the floor. The choice you make above that floor is a judgment call, and you should be able to say it in one sentence.

New situation: a statewide car-wash chain wants every one of its 40 sites listed next to its own district's average wash count, so district managers can see the gap at each site. Which approach delivers that?

15. Thinking ahead

One rule connects the three tools more tightly than it first looks. A window function's value is worked out late in a query's order of operations, after WHERE has already run. So you cannot filter on it in WHERE at all. If a request ever becomes "show me only the locations above their own region's average," the window function alone will not do it. You give the window result a name first, then filter the name. That is the same move you already made in this reading, used for a different reason: naming a step is what makes it usable later. The tools were never really competing.
