Three Right Answers, One Good Choice

A gym company gets two questions on the same morning. Both can be answered in SQL, and each can be answered correctly in more than one way. No query here breaks. The skill is picking between tools that all work, and saying in one sentence why you picked the one you did.

1. Two questions, two answer shapes

Northline Fitness is a made-up company with six gyms. Each gym is a location, and the locations sit in three regions (parts of the map): North, East, and South. A sign-up is one new person joining a gym. Two questions arrive:

  1. "Which locations had more new sign-ups than the chain-wide average?" (A chain is one company's group of gyms, so this is the average over all six.)
  2. "List every location next to its own region's average, so we can see how far off each one is."

They sound alike, but the answers have different shapes. The first is a shorter list. The second keeps all six locations and adds a number beside each one.

102.50 appears twice on the right, and that is correct: the average belongs to the region, so both East locations carry it. This matters because a request never names the tool, and people will ask why you wrote a query the way you did. You already know subqueries, CTEs, and window functions. Now you'll choose between them.

How the examples work: the SQL boxes run real SQL in your browser. Edit a query and click Run to try your own version. It works the same in the PostgreSQL you use in class. The data is two tables: locations (one row per gym, with location_id, location_name, and region) and signups (one row per person who joined, with a location_id).

2. Recall

A table has 6 location rows across 3 regions. How many rows does SELECT region, COUNT(*) FROM locations GROUP BY region; return?

A CTE is a named step written at the top of a query with WITH. How long does that name last?

3. Question 1, written two ways

To answer question 1, a query has to count sign-ups per location, then compare each count to the average of those counts. Here is a version that names nothing. It has two kinds of subquery inside it:

  • A scalar subquery hands back exactly one value. (SELECT AVG(per_loc.n) ...) is one: it gives a single number, so it can sit on the right side of >.
  • A derived table is a subquery inside FROM, given a name with AS, so the query around it can read it like a table. Here that is per_loc. It lasts only while this one query runs.

Predict: the chain-wide average is 126.67 sign-ups. Using the counts in the picture, how many locations does nested.sql print?

 location_name | sign_ups
---------------+----------
 Southgate     |      205
 Bayview       |      148
 Eastport      |      131
(3 rows)

That query is correct. But the counting step is written twice, and the second copy sits deep inside HAVING. Change one, forget the other, and the numbers stop matching. A CTE names the step once.

Fill in the blank: name the step

____ per_location AS (
  SELECT l.location_name, l.region, COUNT(s.signup_id) AS sign_ups
  FROM locations AS l
  LEFT JOIN signups AS s ON s.location_id = l.location_id
  GROUP BY l.location_name, l.region
)
SELECT location_name, sign_ups
FROM per_location
WHERE sign_ups > (SELECT AVG(sign_ups) FROM per_location)
ORDER BY sign_ups DESC;
  1. Type the one keyword that opens a CTE. It is four letters. Capital letters or not, either is fine.
  2. Press Check. Then the query runs below. Compare its rows with nested.sql.

---------------+----------

 Bayview       |      148

(3 rows)

Same rows. The CTE is not more correct, and on six gyms it isn't measurably faster. What it gives you is a middle step you can check on its own. Swap the last part for SELECT * FROM per_location:

4. Question 2: every row has to stay

Question 2 wants all six locations, each with its region's average. One way uses a correlated subquery: a subquery that uses a column from the outer query, so it runs again for every outer row. Here, per_location.region comes from the outer query.

 location_name | region | sign_ups | region_avg
---------------+--------+----------+------------
 Eastport      | East   |      131 |      102.5
 Lakeshore     | East   |       74 |      102.5
 Bayview       | North  |      148 |      120.0
 Ridgeway      | North  |       92 |      120.0
 Southgate     | South  |      205 |      157.5
 Clay Hill     | South  |      110 |      157.5
(6 rows)

Six locations means the inner question gets asked six times. On six rows nobody notices. On millions of rows, that repeating is why correlated subqueries can get slow.

A window function does the same job in one line. It looks across a set of related rows and writes one value onto each row, without folding rows together. PARTITION BY region restarts the calculation for each region.

Predict: window.sql starts from the 6 rows of per_location. How many rows does it print?

 location_name | region | sign_ups | region_avg
---------------+--------+----------+------------
 Eastport      | East   |      131 |      102.5
 Lakeshore     | East   |       74 |      102.5
 Bayview       | North  |      148 |      120.0
 Ridgeway      | North  |       92 |      120.0
 Southgate     | South  |      205 |      157.5
 Clay Hill     | South  |      110 |      157.5
(6 rows)

The browser prints 102.5 and 120 where PostgreSQL prints 102.50 and 120.00. They are the same numbers, shown with fewer zeros.

Worth remembering: GROUP BY region would return 3 rows. PARTITION BY region returns all 6.

5. Four checks before you pick a tool

  1. Shape. Does the answer need one value, or a whole set of rows?
  2. Rows. Does every original row need to stay, with something added beside it?
  3. Check. Will you need to run a middle step on its own to trust the result?
  4. Reader. Who reads this query after you, and what will they need to keep in mind?

Question 1: the rows shrink to a shorter list, and the counting step is worth checking, so a CTE with a small scalar subquery fits. Question 2: every row stays, so a window function fits, on top of the same CTE. Tools can work together, as question 2 shows.

7. Wrap-up

  • A nested subquery and a CTE can return the same rows. The CTE names a step once, so you can reuse it and check it on its own.
  • When every row must stay with a group value beside it, use a window function with PARTITION BY, not GROUP BY.
  • A correct answer is the starting point. Pick with the four checks, and say why in one sentence.

New situation: Northline wants every personal trainer listed next to the average client rating at the trainer's own location. Which approach fits?

In interviews: "What is the difference between a CTE and a subquery, and when would you use each?" is a common question, and a strong answer ends with a rule for choosing, not just definitions.

Where this goes next: you can't filter a window function's result in WHERE, so to keep only the locations above their region's average, you name the window step first and then filter the name.
