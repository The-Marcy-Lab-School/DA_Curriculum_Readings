Clearing the Bar

Pine Street Design is a three-person studio that makes logos and websites for local shops. It keeps one table with a row for every project. The owners want two answers: how much each client has paid in total, and which clients came back more than once. Both answers mean turning many rows into one row per client.

This matters because "which customers cross some line" is one of the most common questions in a data job: more than 3 orders, over $10,000 spent. You already know how to filter rows with WHERE and how a join can repeat a row. Now you'll summarize many rows into one per group.

The studio also has a contacts table, with one row for each person the studio talks to at a shop. Harbor Florist's logo project has 2 contacts. If you INNER JOIN projects to contacts, how many rows does that one project become?

That second answer is a trap to remember: counting raw rows after a join can count the same project twice. Grouping rows by the thing you care about fixes that.

3. GROUP BY: one row per client

GROUP BY gathers rows that share the same value in a column into a group. The column you name is the group key, and here it is client_name. Then an aggregate function turns each group's many values into one number. COUNT(*) counts the rows, SUM() adds them up, and AVG() finds the average. You get one output row per group.

New in this file: AS total_billed gives an output column a name. Without it, psql would label the column sum.

Predict: what two numbers does client_totals.sql show for Union Grain Bakery?

SELECT client_name,
       COUNT(*) AS projects,
       SUM(bill_amount) AS total_billed
FROM projects
GROUP BY client_name
ORDER BY client_name;
    client_name     | projects | total_billed
--------------------+----------+--------------
 Harbor Florist     |        2 |         2900
 Pinewood Dental    |        1 |         3100
 Union Grain Bakery |        3 |         5900
(3 rows)

Six rows went in and three came out, one per client. GROUP BY doesn't delete anything from the table. It only shapes the result.

4. HAVING: keep only the groups that clear the bar

Now the second question: which clients came back more than once? That means COUNT(*) > 1, and the count only exists after the rows are grouped. HAVING is the clause that filters whole groups, after GROUP BY and the aggregate functions have run.

Why WHERE can't do HAVING's job

Predict: where_count.sql puts the count test in WHERE. What happens?

SELECT client_name, COUNT(*) AS project_count
FROM projects
WHERE COUNT(*) > 1
GROUP BY client_name;
psql:where_count.sql:4: ERROR:  aggregate functions are not allowed in WHERE
LINE 3: WHERE COUNT(*) > 1
              ^

The error points at the problem with ^. WHERE looks at one row at a time, before grouping, so there is no count for it to test yet.

5. WHERE and HAVING in one query

A query runs its parts in a different order than you type them. This order is the logical query order: FROM, then WHERE, then GROUP BY, then HAVING, then SELECT, then ORDER BY. So WHERE vs. HAVING comes down to timing: WHERE drops single rows before grouping, and HAVING drops whole groups after.

Predict: busy_2025.sql keeps only 2025 projects, then keeps clients with more than 1 of them. Which clients come back?

SELECT client_name, COUNT(*) AS project_count
FROM projects
WHERE year = 2025
GROUP BY client_name
HAVING COUNT(*) > 1
ORDER BY project_count DESC;
    client_name     | project_count
--------------------+---------------
 Union Grain Bakery |             2
(1 row)

7. Wrap-up

  • GROUP BY makes one output row per group key value, and an aggregate function gives each group one number.
  • HAVING filters whole groups using aggregates like COUNT(*) and SUM(). WHERE can't, because it runs before grouping.
  • One query can use both: WHERE drops rows first, then HAVING drops groups.

New situation: the owners want the clients whose projects take more than 15 hours on average. Which query does that?

In interviews: "Find the customers with more than 3 orders" is a very common SQL task, and the answer is GROUP BY plus HAVING, not WHERE.
