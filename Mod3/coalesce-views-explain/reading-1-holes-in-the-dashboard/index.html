Holes in the Dashboard

A school runs a walking challenge. Each day, students log their steps, and a dashboard (a web page that shows numbers at a glance) shows each class team's totals. Two things go wrong. Some students have not logged yet, so blanks appear. And adding up every log each time someone opens the page is slow.

3. NULL means unknown

Here is the query behind the dashboard. The LEFT JOIN keeps every student, even one with no log.

SELECT s.name, l.steps FROM students s LEFT JOIN step_logs l ON l.student_id = s.student_id WHERE s.team_id = 1 ORDER BY s.name;
$ psql -d step_challenge -f room12.sql
 name  | steps
-------+-------
 Ava   |  8200
 June  |  6100
 Luis  |  9400
 Priya |  7300
 Tomas |
(5 rows)

Tomas's cell is NULL: the absence of a value. NULL means unknown. It is not zero, and it is not empty text. To find students with no log, the obvious try is = NULL.

Predict: how many rows does missing_try.sql return?

SELECT s.name FROM students s LEFT JOIN step_logs l ON l.student_id = s.student_id WHERE s.team_id = 1 AND l.steps = NULL;
$ psql -d step_challenge -f missing_try.sql
 name
------
(0 rows)

Asking whether an unknown value equals something gives another unknown, and WHERE only keeps rows it knows are true. So = NULL never matches anything, not even another NULL. IS NULL is the keyword that tests whether a value is absent.

Fill in the blank: find the missing log

SELECT s.name FROM students s LEFT JOIN step_logs l ON l.student_id = s.student_id WHERE s.team_id = 1 AND l.steps ____;
$ psql -d step_challenge -f missing.sql
 name
-------
 Tomas
(1 row)
  1. Type the two words that test whether l.steps has no value. Leave out l.steps itself.
  2. Put one space between the words. Capital letters or lowercase both work.

4. COALESCE fills the gap, and you choose what it claims

COALESCE is a function that returns the first value in its list that is not NULL, checking left to right. COALESCE(l.steps, 0) shows the real steps when they exist and 0 when they don't. The 0 is a fallback: the stand-in value you choose to show in place of a NULL. Choosing one is a claim about what the missing value means. COALESCE changes only this query's output; the NULL is still stored in the table.

New in this file: ROUND(x) rounds a number to the nearest whole number, so ROUND(7750.4) gives 7750. AVG skips NULLs, the same way COUNT(column) does.

Predict: the four logged students average 7750 steps. What does avg_with_zero show once Tomas counts as 0?

SELECT ROUND(AVG(l.steps)) AS avg_logged, ROUND(AVG(COALESCE(l.steps, 0))) AS avg_with_zero FROM students s LEFT JOIN step_logs l ON l.student_id = s.student_id WHERE s.team_id = 1;
$ psql -d step_challenge -f room12_average.sql
 avg_logged | avg_with_zero
------------+---------------
       7750 |          6200
(1 row)

That 0 claims Tomas walked zero steps, which nobody measured, and it pulls Room 12's average down by 1550. A zero is honest only when it means "none," such as a column labeled "steps logged so far." Same function, two different claims. The judgment belongs to you, not to SQL.

5. Store the answer instead of redoing it

The team totals join three tables and add up every log. Run that on every page load, all day, and it gets slow. A view is a query saved under a name. It stores only the query text, so it re-runs every time you read from it. A materialized view is a saved query whose result rows are stored on disk, so reading it does not redo the work:

CREATE MATERIALIZED VIEW team_steps AS SELECT t.team_name, COUNT(l.log_id) AS logs, COALESCE(SUM(l.steps), 0) AS total_steps FROM teams t LEFT JOIN students s ON s.team_id = t.team_id LEFT JOIN step_logs l ON l.student_id = s.student_id GROUP BY t.team_name; SELECT * FROM team_steps ORDER BY team_name;
$ psql -d step_challenge -f create_team_steps.sql
SELECT 3
 team_name | logs | total_steps
-----------+------+-------------
 Room 12   |    4 |       31000
 Room 14   |    2 |       11500
 Room 15   |    0 |           0
(3 rows)

The SELECT 3 line is psql saying it stored 3 rows. You read a materialized view the same way you read a table. Now Tomas logs 7000 steps.

Predict: in late_log.sql, what does the first SELECT show for Room 12's total_steps?

INSERT INTO step_logs (log_id, student_id, log_date, steps) VALUES (7, 5, '2026-10-05', 7000); SELECT * FROM team_steps ORDER BY team_name; REFRESH MATERIALIZED VIEW team_steps; SELECT * FROM team_steps ORDER BY team_name;
$ psql -d step_challenge -f late_log.sql
INSERT 0 1
 team_name | logs | total_steps
-----------+------+-------------
 Room 12   |    4 |       31000
 Room 14   |    2 |       11500
 Room 15   |    0 |           0
(3 rows)

REFRESH MATERIALIZED VIEW
 team_name | logs | total_steps
-----------+------+-------------
 Room 12   |    5 |       38000
 Room 14   |    2 |       11500
 Room 15   |    0 |           0
(3 rows)

Between the INSERT and the refresh, the stored rows were stale: correct at their last refresh, but no longer matching the live tables. REFRESH MATERIALIZED VIEW re-runs the stored query and replaces every stored row. PostgreSQL never does this on its own. The rule: if the numbers must be right to the second, use a plain view. If the query is slow and the numbers can be a little behind, use a materialized view and say how fresh it is.

6. Measure the cost with EXPLAIN ANALYZE

A query plan is the step-by-step method PostgreSQL picks for running your query, printed one line per step. EXPLAIN shows the plan without running the query. EXPLAIN ANALYZE runs the query and prints the plan with real times and real row counts next to the planner's guesses. Because it really runs the statement, only use it on a SELECT while you practice: on an INSERT it would really add the row.

The whole school district runs this challenge: 12 teams, 250 students, and about 180,000 step logs. Here is the team totals query on that data, before the materialized view existed. The block scrolls sideways; each step that sits further right runs first.

EXPLAIN ANALYZE SELECT t.team_name, COUNT(l.log_id) AS logs, COALESCE(SUM(l.steps), 0) AS total_steps FROM teams t LEFT JOIN students s ON s.team_id = t.team_id LEFT JOIN step_logs l ON l.student_id = s.student_id GROUP BY t.team_name;
$ psql -d district_steps -f explain_totals.sql
                                                            QUERY PLAN
----------------------------------------------------------------------------------------------------------------------------------
 HashAggregate  (cost=6911.52..6911.64 rows=12 width=48) (actual time=97.402..97.410 rows=12 loops=1)
   Group Key: t.team_name
   ->  Hash Right Join  (cost=11.78..5561.40 rows=180016 width=44) (actual time=0.231..62.118 rows=180020 loops=1)
         Hash Cond: (l.student_id = s.student_id)
         ->  Seq Scan on step_logs l  (cost=0.00..3105.16 rows=180016 width=12) (actual time=0.010..15.204 rows=180016 loops=1)
         ->  Hash  (cost=8.66..8.66 rows=250 width=36) (actual time=0.205..0.207 rows=250 loops=1)
               ->  Hash Right Join  (cost=1.27..8.66 rows=250 width=36) (actual time=0.031..0.152 rows=250 loops=1)
                     Hash Cond: (s.team_id = t.team_id)
                     ->  Seq Scan on students s  (cost=0.00..5.50 rows=250 width=8) (actual time=0.005..0.041 rows=250 loops=1)
                     ->  Hash  (cost=1.12..1.12 rows=12 width=36) (actual time=0.014..0.015 rows=12 loops=1)
                           ->  Seq Scan on teams t  (cost=0.00..1.12 rows=12 width=36) (actual time=0.006..0.009 rows=12 loops=1)
 Planning Time: 0.412 ms
 Execution Time: 97.871 ms
(13 rows)

You don't have to read every line. Look for three things:

  1. Seq Scan lines: a step that reads every row of a table in order. That is fine on a small table and worth a look on a huge one. Here step_logs got a Seq Scan over 180,016 rows.
  2. Guess versus real: each line has a guessed rows= in the first parentheses and the real rows= in the actual parentheses. Here they are close, which is a good sign.
  3. Execution Time, the last line: how many milliseconds the run really took. The cost= numbers are not times. They are units the planner uses to compare its own options.

Which part of the plan tells you how long the query really took?

Now the same question, asked of a materialized view built on the district data:

EXPLAIN ANALYZE SELECT * FROM team_steps;
$ psql -d district_steps -f explain_view.sql
                                               QUERY PLAN
-------------------------------------------------------------------------------------------------------
 Seq Scan on team_steps  (cost=0.00..1.12 rows=12 width=48) (actual time=0.008..0.010 rows=12 loops=1)
 Planning Time: 0.051 ms
 Execution Time: 0.024 ms
(3 rows)

One line of plan instead of eleven, and no joins, because the joins already ran once when the view was stored. Times move a little from run to run, so compare the shape of the plan, not one run's milliseconds.

8. Wrap-up

  • NULL means unknown, so = NULL matches nothing and IS NULL is the test. COALESCE fills a gap with whatever fallback you choose, so choose one that tells the truth.
  • A materialized view trades freshness for speed. Someone has to run REFRESH MATERIALIZED VIEW.
  • EXPLAIN ANALYZE measures what a query costs, so you check instead of guess.

New situation: the school hallway screen shows which students have logged steps today, and students check it all day. The query reads one small table. Which fits?

In interviews: for "How do you handle missing values in SQL?", a strong answer names what the missing value means and what your fallback claims, not only "I use COALESCE."

Where this goes next: once a plan shows a step reading far more rows than it needs, you can change that step, for example with an index that lets PostgreSQL jump straight to matching rows.
