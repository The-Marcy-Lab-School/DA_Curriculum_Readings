Holes in the Dashboard

Renata is the operations analyst at Brightline Studio, a sixty-person architecture firm that designs schools, libraries, and apartment buildings. Her job this week is a billable-hours dashboard: one page that tells each project lead how many paid hours the team has logged against their building. Two things are going wrong. Some people have not turned in a timesheet yet, so the numbers come back with blanks in them. And rebuilding the totals from three tables every time somebody opens the page is slow enough that leads have started complaining. This reading is about fixing both honestly, and then actually measuring whether the fix worked.

1. The dashboard with holes in it

At Brightline Studio, a billable hour is an hour of work a staff member logs against a client's building project, so the firm can invoice the client for it. Every Friday, staff type their week into a timesheet. Renata's dashboard adds those hours up per project and shows each project lead the total.

On Monday morning she opened her own first draft and found this. Amara, Luis, Priya, and June all show hours. Tomas shows nothing at all, because he had not filed his timesheet yet when the page loaded.

Why this matters: a project lead looking at that screen will read the blank as a zero, decide Tomas had a light week, and maybe move work onto him. That is a real staffing decision made from a hole in the data. Dashboards get trusted, and a number nobody questioned is exactly how a wrong number spreads. In a data-role interview this shows up as a direct question: "how do you handle missing values in SQL?" and, right behind it, "how would you investigate a query that suddenly got slow?" Both are questions you can answer concretely by the end of this page.

Where you're coming from, where this is headed: you already know how to join tables and add numbers up with GROUP BY, and you already know a join can leave you holding rows that have no match on the other side. This reading picks up exactly at that blank cell: what it actually is, how to fill it on purpose, how to save an expensive answer so nobody pays for it twice, and how to ask the database itself what your query cost. Later on, the same habit of measuring first is what lets you decide whether an index or a rewrite is worth it, instead of guessing.

2. Concept overview: three problems, one dashboard

Brightline's database has three tables that matter here. staff holds one row per employee. projects holds one row per building. timesheets holds one row per person, per week, per project, with the hours they logged. Renata's dashboard has to pull from all three.

Her first query lists everyone in Studio B next to the hours they logged. She uses a LEFT JOIN, which keeps every row from the first table even when the second table has no matching row. That is on purpose: she wants all five people listed, including anyone who has not filed yet.

SELECT s.full_name, t.billable_hours FROM staff s LEFT JOIN timesheets t ON t.staff_id = s.staff_id ORDER BY s.full_name; full_name | billable_hours ---------------+---------------- Amara Diallo | 22.50 June Okada | 12.00 Luis Ferrara | 18.00 Priya Raman | 30.00 Tomas Vega | (5 rows)

Tomas's cell is not an empty piece of text and it is not a zero. It is NULL, which is PostgreSQL's way of saying "there is no value here and I do not know what it should be." That distinction drives everything else in this reading.

Renata's first instinct was to hunt for the missing rows with WHERE t.billable_hours = NULL. It ran without an error and returned nothing at all. Here is why. NULL means unknown, so asking whether an unknown thing equals something is itself unknown. Picture two sealed envelopes with no idea what is inside either one. Are their contents equal? You cannot say yes, and you cannot say no. A WHERE clause only keeps rows it can prove are true, so a row whose answer is "unknown" never survives. The keyword that actually tests for absence is IS NULL.

Once she could find the blanks, she had to decide what to show in them. COALESCE takes a list of values and hands back the first one that is not NULL, reading left to right. COALESCE(t.billable_hours, 0) shows the real hours when they exist and 0 when they do not. COALESCE(p.project_name, 'No timesheet yet') does the same thing with a piece of text. Both are one function. The difference between them is a judgment call about what the blank means, and that judgment belongs to Renata, not to SQL.

The second problem is cost. Brightline has four years of timesheets, which is about 180,000 rows. The totals query reads all of them, joins three tables, and groups the result every single time the page loads. A view would not help much: a view stores only the query's text and re-runs it on every read. A materialized view stores the actual answer rows on disk, so reading it is just reading rows.

Think of the printed room schedule taped to a conference-room door. Reading it takes a second, because somebody already did the work of looking everything up and printing it. It is also only true as of the moment it was printed. If a meeting moves, the sheet on the door says nothing about it until a person prints a fresh one. A materialized view works the same way, and printing a fresh one is a real command: REFRESH MATERIALIZED VIEW. Until somebody runs it, the stored rows are stale, meaning they were correct once and are not correct now.

The third problem is that Renata had assumed the totals query was expensive without ever measuring it. EXPLAIN asks PostgreSQL to describe the query plan it intends to use, step by step, with estimated costs, without running anything. Adding ANALYZE actually runs the query and prints the measured times and true row counts next to those estimates.

An architecture firm is a good place for this comparison. When Brightline hires a contractor, the bid is an estimate of what each stage will take. The invoice at the end is the itemized list of what each stage really took. EXPLAIN is the bid. EXPLAIN ANALYZE is the invoice, with the real hours filled in next to the guesses.

One safety note, worth knowing before you ever type it: because ANALYZE genuinely runs the statement, running it on an INSERT, UPDATE, or DELETE really does change your data. On a SELECT it is completely safe, and every example in this reading is a SELECT.

5. Why = NULL never matches

Renata wanted a list of everyone who still owed her a timesheet. Here is the query she tried first.

SELECT s.full_name FROM staff s LEFT JOIN timesheets t ON t.staff_id = s.staff_id WHERE t.billable_hours = NULL;

Tomas is the one person with no timesheet row. How many rows does this query return?

This is the most common silent bug in SQL. There is no error, no warning, and no red text. The query simply answers a different question than the one you meant to ask, and hands back an empty result that looks like a real finding. Fix it by naming absence directly.

SELECT s.full_name FROM staff s LEFT JOIN timesheets t ON t.staff_id = s.staff_id WHERE t.billable_hours __BLANK__;
Need a hint?

You are not comparing the column to a value. You are asking whether the column has a value at all, so the keyword reads like plain English about the row's state.

PostgreSQL treats != the same way. WHERE t.billable_hours != NULL also returns nothing, which catches people out even more often than the first version does. The opposite of IS NULL is IS NOT NULL.

6. COALESCE, and what a fallback claims

Now Renata fills the gaps on purpose. She writes two fallbacks into one query: a number for the hours column, and a piece of text for the project column.

SELECT s.full_name, COALESCE(p.project_name, 'No timesheet yet') AS project, COALESCE(t.billable_hours, 0) AS hours FROM staff s LEFT JOIN timesheets t ON t.staff_id = s.staff_id LEFT JOIN projects p ON p.project_id = t.project_id ORDER BY s.full_name; full_name | project | hours ---------------+--------------------+------- Amara Diallo | Eastside Library | 22.50 June Okada | Cedar Grove School | 12.00 Luis Ferrara | Eastside Library | 18.00 Priya Raman | Harbor View Apart. | 30.00 Tomas Vega | No timesheet yet | 0.00

Two things are worth noticing. First, COALESCE changed nothing in the table. The NULL is still sitting in the database afterward; only this one query's output looks different. Second, the two fallbacks on Tomas's row disagree with each other. 'No timesheet yet' tells the truth. 0.00 quietly states that he billed nothing.

Now try writing one yourself. The query below should show each person's hours, with any missing value displayed as 0 and the column renamed to hours.

SELECT s.full_name, __BLANK__ AS hours FROM staff s LEFT JOIN timesheets t ON t.staff_id = s.staff_id;
Need a hint?

The function takes two things inside its parentheses, separated by a comma: the column you are reading, then the value to fall back on. The column lives on the timesheets table, so it is written t.billable_hours.

The part SQL will not decide for you

The four submitted timesheets are 22.50, 18.00, 30.00, and 12.00 hours. Their average is 20.63 hours per person. Wrap the column in COALESCE(t.billable_hours, 0) and the average is computed over five people instead of four, which drops it to 16.50.

Which statement describes what that 0 is claiming?

Where a zero fallback genuinely is the right answer: Renata's project totals use COALESCE(SUM(t.billable_hours), 0) so that a brand-new project with no timesheet rows at all shows 0.00 instead of a blank. That zero is honest, because the rows genuinely do not exist: nobody has logged any time against that building yet. A person who simply has not filed yet is a different situation, and deserves a different fallback. Same function, two different claims.

7. Storing the answer instead of recomputing it

Renata's totals query joins all three tables and groups the result. Running it once is fine. Running it on every page load, for every lead, all day, is the part that hurts. Both kinds of saved query look identical to read from, which is exactly why the difference catches people out.

A late timesheet lands in the timesheets table.
The dashboard keeps showing its stored numbers, which no longer match the live tables.

Need a hint?

Nothing can go stale before it has been stored, and nothing gets refreshed before anything has changed. Start from the plain query and follow the timeline forward.

The honest decision rule: if the answer has to be correct to the second, a plain view is right. If the query is expensive and you control how fresh the numbers need to be, a materialized view is right. Most dashboards are the second case. Whoever builds one owes the people reading it a plain statement of how fresh the numbers are, which is why so many real dashboards carry a small "last updated at" line in the corner.

9. Reading what the plan tells you

On five practice rows everything is fast, so the timings above mean very little on their own. Renata ran the same two shapes against the firm's real database, where timesheets holds about 180,000 rows. Here is the totals query, before the materialized view existed.

The plan below keeps its real indentation, so the block scrolls sideways on a narrow screen instead of wrapping. The indentation is part of the meaning: a step sitting further right runs before the step above it.

EXPLAIN ANALYZE SELECT p.project_name, COUNT(s.staff_id) AS people, COALESCE(SUM(t.billable_hours), 0) AS total_hours FROM projects p LEFT JOIN timesheets t ON t.project_id = p.project_id LEFT JOIN staff s ON s.staff_id = t.staff_id GROUP BY p.project_name; HashAggregate (cost=9184.22..9184.25 rows=3 width=48) (actual time=408.91..408.94 rows=3 loops=1) Group Key: p.project_name -> Hash Left Join (cost=41.60..7834.10 rows=180016 width=44) (actual time=1.02..286.74 rows=180016 loops=1) Hash Cond: (t.staff_id = s.staff_id) -> Hash Left Join (cost=1.07..5309.44 rows=180016 width=40) (actual time=0.06..118.60 rows=180016 loops=1) Hash Cond: (t.project_id = p.project_id) -> Seq Scan on timesheets t (cost=0.00..3105.16 rows=180016 width=18) (actual time=0.01..27.44 rows=180016 loops=1) -> Seq Scan on projects p (cost=0.00..1.03 rows=3 width=26) (actual time=0.01..0.02 rows=3 loops=1) -> Seq Scan on staff s (cost=0.00..1.60 rows=60 width=4) (actual time=0.01..0.03 rows=60 loops=1) Planning Time: 0.38 ms Execution Time: 412.65 ms

That looks like a wall of text the first time. You do not have to read all of it. Three things carry almost all of the meaning.

  1. What kind of scan each table got. Three Seq Scan lines here, one per table. A sequential scan reads every row in order, because no index was used. An index is a separate lookup structure a table can have that lets PostgreSQL jump straight to matching rows instead of reading all of them.
  2. How close the guess was to reality. Each line carries a guessed rows= from the planner and an actual rows= from the run. Here they match exactly, which is a healthy sign. A wide gap between them on a large table is the first thing a performance engineer looks at.
  3. The last line. Execution Time is real milliseconds. The cost= numbers are not: they are made-up units the planner uses only to compare its own options against each other, so never read a cost as a time.

Here is that second point up close. This is the timesheets line from the plan above, split across three lines here so the whole thing fits on screen.

Seq Scan on timesheets t (cost=0.00..3105.16 rows=180016 width=18) (actual time=0.01..27.44 rows=180016 loops=1)

The first rows=180016 sits in the estimate parentheses: that is the planner's guess before it ran anything. The second sits in the actual parentheses: that is what really came back. Matching numbers mean the planner understood this table well. A guess of 200 next to an actual of 180,016 would mean it did not, and that gap is often the real reason a query got slow.

Now the same question, asked of the materialized view instead.

EXPLAIN ANALYZE SELECT * FROM project_hours; Seq Scan on project_hours (cost=0.00..1.03 rows=3 width=48) (actual time=0.01..0.02 rows=3 loops=1) Planning Time: 0.06 ms Execution Time: 0.09 ms

One line instead of nine. No joins anywhere, because the joins already happened once, at creation time, and reading the stored rows never redoes them. That is the whole point of the previous section, made visible and measured rather than assumed.

One honest caution: run the same query twice and the execution time will move, because caching and whatever else the machine is doing both affect it. Compare shapes and row counts, not one run's milliseconds.

11. How this shows up in interviews

"How do you handle missing values in SQL?" is a standard screening question for data roles, and the weak answer is "I use COALESCE." The strong answer names the judgment: what the missing value means, what the fallback would be claiming, and why you picked the one you picked. Renata's dashboard is a ready-made example of that, with two different fallbacks on the same row for two genuinely different reasons.

"What is the difference between a view and a materialized view?" leans toward analytics-engineering and data-engineering roles more than pure analyst roles, but it is worth knowing cold. Answer in one sentence, ground it in something you actually built, then close with the decision rule rather than a summary.

"A dashboard query that used to take two seconds now takes forty. How would you investigate?" is a mid-level question, and interviewers are listening for a process rather than a fix. A strong shape: confirm the slowdown is real and repeatable, ask what changed and when, name several possible causes out loud before picking one, then run EXPLAIN ANALYZE and compare the plan and row counts against what the query used to do. That evidence step is the part most candidates hand-wave, and it is the part you can now actually demonstrate.

12. Summary & critical thinking

Three ideas carried this whole reading. NULL means unknown, which is why = NULL matches nothing and IS NULL exists. COALESCE will put any fallback you name into a gap without any opinion about whether that fallback is honest, so the judgment is always yours. And a materialized view buys speed by storing an answer, which means someone has to decide how stale is too stale and run REFRESH MATERIALIZED VIEW on a schedule that matches that decision. EXPLAIN ANALYZE is how you check any of this instead of assuming it.

New situation: a dental clinic's front-desk screen shows how many patients are currently checked in and waiting. Staff need that count correct to the minute, and the query behind it reads one small table. Which choice fits?

13. Thinking ahead

Every plan in this reading answered the same question: what did this query cost? The natural next step is the question right behind it. Once a plan shows one step reading far more rows than the answer actually needs, the work becomes changing that step, by adding an index so PostgreSQL can jump to matching rows instead of reading all of them, or by rewriting the query so fewer rows ever reach the expensive part. Measuring first is what makes that next step a decision rather than a guess.
