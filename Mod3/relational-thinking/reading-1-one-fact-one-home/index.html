One Fact, One Home

A community library tracks every book loan in a single, growing spreadsheet: one row per checkout, with the patron's name, email, and phone typed in fresh every time they borrow something. That works fine for the first fifty rows. By row five thousand, changing one patron's phone number means hunting down every row that mentions them, and missing even one leaves the library with two different phone numbers for the same person. This reading is about the fix: designing tables where every fact lives in exactly one place.

1. Concept overview

Picture the library's spreadsheet in full. Maria Chen borrows three books over a month: The Hobbit, Dune, and Circe. Each checkout is its own row, so her name, email, and phone number get typed out three separate times, once per row, identically, by whoever's at the front desk that day. James Okoro borrows The Hobbit too, so its title and author get typed out a second time as well, on a completely different row, for a completely different patron.

Nothing about this is broken yet. The spreadsheet opens, the rows are readable, every column has a value in it. The problem only shows up the moment something changes: Maria moves and gets a new phone number, and now there are three rows to find and edit, in a spreadsheet with thousands of them. Miss one, and the library now has two different phone numbers on file for the same real person, with no way for the spreadsheet itself to notice the disagreement.

Why this matters: "why would you normalize this schema" and "what's a foreign key" are two of the most common questions in data and analytics interviews, often asked before a single line of SQL syntax comes up. And in any real data job, a dataset that arrives as one flat file, an export from a form tool, a CSV from another team, almost always needs to be reshaped into related tables before its numbers can be trusted.

Where you're coming from, where this is headed: you already know how to read a table's rows and columns. This reading is about what happens once a single flat table starts describing more than one kind of real-world thing at once, patrons and their loans and the books they borrowed, all crammed into one row. Once you can spot that mixing and split it apart, the same instinct carries into any dataset you're ever handed: what are the real, separate things here, before you write a single query against them.

5. The fix: three related tables

The repeating group is patron information: name, email, and phone, copied onto every loan row for the same person. So pull it out. Give patrons their own table, with one row per real person instead of one row per loan. Do the same for books: one row per title instead of one row copied onto every loan for it. What's left in loans is exactly what a loan actually is, who borrowed what, and when, plus a pointer back to the right patron and the right book.

Together: one patron can have many loans, and one book can have many loans. Reading that both ways at once, one patron can borrow many books, and one book can be borrowed by many patrons, over time, is exactly what makes patrons and books many-to-many with each other, through loans sitting in between.

6. Foreign keys, up close

The loans table doesn't repeat a patron's name or a book's title anymore. Instead, each loan row stores two foreign keys: a value that points at exactly one row in patrons, and a value that points at exactly one row in books. Nothing about a patron or a book is copied, only a reference to where the real, single copy of that fact already lives.

8. Turning a flat table into related ones

Click steps, in order, to build the sequence for splitting a flat table like the library's loans sheet. Click a step again to remove it if you change your mind, then press "Check my order" when you're ready. This is a self-check, not graded on correctness.

  • Spot a group of columns that keeps repeating together, like a patron's name, email, and phone on every one of their loan rows.
  • Pull that repeating group into its own table, with one row per real-world patron instead of one row per loan.
  • Give the new table a primary key that uniquely identifies each row in it.
  • Add that primary key as a foreign key back in the original table, replacing the repeated columns.

10. How this shows up in interviews

"What's the difference between a primary key and a foreign key?" and "why would you normalize this table?" are two of the most common warm-up questions in data and analytics interviews, often asked before a single line of SQL gets written. Interviewers are listening for whether you can point at a real consequence, an update anomaly, a table that can end up disagreeing with itself, rather than reciting a textbook definition.

A second common version hands you a messy, flat dataset and asks how you'd design tables for it. The habit this reading practiced, looking for a group of columns that keeps repeating together, is exactly the first move that question is testing for.

Interview-style: you're shown a spreadsheet where every row is a customer's product review, and the customer's full shipping address is repeated on every review they've ever left. What's the strongest first thing to name?

12. Summary & critical thinking

Two ideas carried this whole reading: a flat table that mixes more than one real-world thing together almost always ends up repeating data, and repeated data is exactly what makes a table contradict itself the moment someone updates only part of it. Splitting a flat table into related tables, connected by primary and foreign keys, is how a database keeps each fact in exactly one place.

New situation: a gym's sign-in sheet has one row per class attendance, with the member's name, membership plan, and phone number repeated on every row they ever sign in. What would you do first?

13. Thinking ahead

A schema like the one sketched in this reading, patrons, books, and loans, linked by real keys, is still just a design on paper. The real next step is making it real: creating actual tables in a database that enforce these same rules automatically, so a bad insert gets rejected instead of quietly corrupting the data. That's genuinely different work: everything here has been about reasoning through a design, and building the actual thing is its own separate skill, worth its own real practice.
