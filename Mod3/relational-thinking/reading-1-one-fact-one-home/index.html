One Fact, One Home

A town library keeps every book loan in one spreadsheet. Each row holds the borrower's name, email, and phone, typed again for every book. When a phone number changes, someone has to fix every row. Miss one, and the library has two numbers for one person. Here you learn to set up tables so each fact is stored once.

Storing the same fact in more than one place is called redundancy. Nothing is broken yet. The trouble starts the day a fact changes. The picture shows where this reading ends up: the one sheet becomes three smaller tables.

This matters because data at work often arrives as one big file like this one, and it has to be split up before anyone can trust its numbers. You already know how to read a table's rows and columns. Now you'll learn to design them.

How this reading works: there is no code yet. You read small tables, predict what goes wrong, and then design a better set of tables.

3. Three problems that copies cause

Redundancy leads to three kinds of bugs. Each one is called an anomaly, which means something that goes wrong in a way you didn't expect.

  • An update anomaly: one real change has to be made in many rows. Miss one row, and the table disagrees with itself.
  • An insert anomaly: you can't add a new fact until some other fact exists to fill out the row.
  • A delete anomaly: deleting one row also wipes out a fact you wanted to keep.

Maria gets a new phone number. In the loans sheet in section 1, how many rows must change so every row shows the new number?

The library buys a new book, Kindred. Nobody has borrowed it yet, and every row in the sheet is a loan. So the sheet has no place to record the new book. Which problem is this?

4. Split the sheet: one table for each kind of thing

Normalization means setting up tables so each real-world fact lives in exactly one place. The loans sheet mixes three kinds of things: members, books, and loans. So each one gets its own table.

Each table also needs a primary key: a column whose value is different in every row, so you can point at exactly one row. Here, member_id, book_id, and loan_id are the primary keys.

5. Foreign keys connect the tables

Look at loans again. It no longer copies anyone's name or any book's title. Instead it stores two numbers that point at rows in the other tables. A foreign key is a column in one table that holds another table's primary key. A database checks foreign keys for you, so a loan can't point at a member who doesn't exist.

This diagram shows the three tables and their keys. PK marks a primary key and FK marks a foreign key.

Read the line from members to loans: one member can have many loans, but each loan belongs to one member. That is a one-to-many relationship. Books and loans are one-to-many too. Put the two lines together, and one member can borrow many books while one book can be borrowed by many members. That is a many-to-many relationship. It needs a table in the middle, and here loans is that table.

7. Wrap-up

  • Redundancy (the same fact in many rows) leads to update, insert, and delete anomalies.
  • Normalization gives each kind of thing its own table, with a primary key that names each row.
  • A foreign key points at another table's primary key instead of copying its facts.

New situation: the library starts a book club. Its sign-in sheet has one row per meeting someone attends. The member's name, email, and phone are typed on every row. What should you do first?

In interviews: "What is the difference between a primary key and a foreign key?" is one of the most common first questions, and a strong answer names a real problem, like an update anomaly.

Where this goes next: a design on paper can't stop bad data, so the next step is building these tables in a real database that checks the keys for you.
