The Table That Says No

Deja runs volunteer operations for Neighborhood Tool Share, a lending library where neighbors borrow drills, ladders, and pressure washers instead of buying tools they will use twice a year. For two years the whole operation lived in one shared spreadsheet: a member's name retyped by hand on every checkout row, a borrowed tool with no real link back to who actually has it, dates typed as plain text that sort however the spreadsheet feels like sorting them. This reading is about leaving that spreadsheet behind for real: creating an actual PostgreSQL database from a terminal, building tables with types and constraints that genuinely refuse bad data, and asking that data real questions with a first SELECT query.

1. Concept overview

Here is what actually broke, over and over, in Deja's spreadsheet: two rows for "Deja Okafor" and "Deja O." that a report quietly counted as two different members. A checkout row with a tool name but a totally blank member column, because someone was in a hurry. A "date returned" column where one volunteer typed 3/8 and another typed March 8, so nothing sorted correctly. None of these were typos anyone caught in time. A spreadsheet has no opinion about what belongs in a cell; it will hold whatever gets typed into it.

A real database can have an opinion, and enforce it. psql is PostgreSQL's own command-line client: a terminal program that connects directly to a running database and lets you type real SQL against it, no spreadsheet and no separate graphical tool in between. Inside psql, a database is the whole named container Deja's tool-share data lives in. A table is one structured grid inside that database, with fixed, named columns. And every column gets a data type, a rule about exactly what kind of value it's allowed to hold, decided once, at creation time, not re-guessed every time someone types something into it.

On top of a data type, a column can carry a constraint: an extra rule PostgreSQL actively checks on every single row, every single time, forever, whether or not anyone remembers it's there. NOT NULL refuses a row with that field left blank. PRIMARY KEY refuses a duplicate value in that column, guaranteeing every row can be told apart from every other row. FOREIGN KEY refuses a value that doesn't already exist as a real row somewhere else, which is exactly the rule that would have caught a checkout pointing at a member who was never actually entered. Two of psql's own habits are worth naming before typing anything: many commands that succeed print back nothing at all (silence means it worked, not that nothing happened), and a command that actually creates something usually echoes its own name back as confirmation, like CREATE TABLE printed after a successful CREATE TABLE statement.

Why this matters: a data-role technical screen will very often put you in front of a real terminal and ask you to create a small schema on the spot, not a diagram of one. Getting the column list, types, and constraints right the first time, from a blank prompt, is treated as baseline fluency, the same way basic pandas syntax is assumed baseline for an analyst role. On the job, this is also frequently the literal first command typed against a brand-new project: before any analysis happens, something has to exist to hold the data.

Where you're coming from, where this is headed: you already know, in plain language, what a primary key and a foreign key are supposed to do and why splitting data into related tables beats one flat spreadsheet. This reading is about typing that exact idea as real, enforced syntax for the first time. Once creating a table and asking it a first question with SELECT feels automatic, the natural next step is asking one question that needs facts from two related tables at the same time, matching rows across them instead of reading each table on its own.

4. Order the setup, before you type it

11. How this shows up in interviews

Being able to sit down at a real psql prompt, with no GUI in between, and create a working schema from a plain-language description is a genuine, common signal in a data-role technical screen. It's less about memorizing exact syntax and more about whether reaching for the terminal feels normal instead of intimidating.

A frequent live-coding moment is being handed two related entities in plain English and asked to sketch the CREATE TABLE statements for both, out loud, including which column is the primary key and which is a foreign key. Interviewers are listening for the parent-before-child ordering from section 4 without being told to think about it, and for naming NOT NULL on any column that genuinely shouldn't ever be blank.

A sharper follow-up question tests exactly what section 6 practiced: "what happens if this INSERT is missing a required field, or points at a foreign key that doesn't exist?" Naming the real, specific error PostgreSQL raises, rather than a vague "it would fail," is a strong, concrete answer that a guess can't produce.

Interview-style question: an INSERT into checkouts fails with ERROR: insert or update on table "checkouts" violates foreign key constraint "checkouts_member_id_fkey", DETAIL: Key (member_id)=(12) is not present in table "members". What does this actually tell you?

13. Summary & critical thinking

Three ideas carried this whole reading: a column's data type and constraints are decided once, at creation time, and enforced by PostgreSQL every time after that, without exception; a foreign key has to point at something that already exists, which is exactly why a parent table gets created before the child table that references it; and a first SELECT with WHERE and ORDER BY is really two separate jobs, filtering down to the rows that matter and then choosing what order to read them in.

New situation: a community garden tracks gardeners and the plots they've been assigned. Which CREATE TABLE statement for plot_assignments correctly uses a real foreign key back to a gardeners table?
