Un-Nesting the Query

You write a SQL query that answers a real business question, and it's completely correct. Then a teammate reviewing it has to read the innermost parentheses first just to figure out what the outer clause is even comparing against. Correct and readable turned out to be two different things — and SQL has a feature built specifically to close that gap.

1. Concept overview

Harborview Consulting logs every hour its analysts bill, in one table:

hours_logged(client_name, hours, week_ending)

Someone on the finance team asks a fair question: which clients logged more total hours than the average client, across every logged week? It's answerable in one query — grouping by client, then comparing each client's total against the average of those totals. Here's a correct way to write it:

SELECT client_name, SUM(hours) AS total_hours FROM hours_logged GROUP BY client_name HAVING SUM(hours) > ( SELECT AVG(client_total) FROM ( SELECT SUM(hours) AS client_total FROM hours_logged GROUP BY client_name ) AS client_totals );

Every line of that is correct SQL. It's also genuinely hard to trust at a glance: to know what the HAVING clause is even comparing against, you have to find the innermost parentheses first, work out what client_total means, then work out what AVG(client_total) means, then carry that back up three lines to the comparison that started the whole thing. You read it from the inside out — the opposite of how the words appear on the page.

Here's the exact same logic, rewritten as a CTE:

WITH client_totals AS ( SELECT client_name, SUM(hours) AS total_hours FROM hours_logged GROUP BY client_name ) SELECT client_name, total_hours FROM client_totals WHERE total_hours > (SELECT AVG(total_hours) FROM client_totals);

Nothing about the underlying logic changed. What changed is that the per-client totals now have a name, client_totals, given to them up front — before anything else happens. The final query reads like a sentence: get the client totals, then keep the ones above the average of those totals. You never have to hold a nested, anonymous block in your head to know what you're comparing against, because it already has a name.

Why this matters: a query being correct and a query being readable are genuinely separate properties, and code review treats them that way. A reviewer (or an instructor grading a project rubric) can run both versions above and get the identical result — but only one of them can be trusted at a glance, without tracing parentheses. Writing SQL other people can review quickly is a real, specific skill, not a stylistic nice-to-have.

Where you're coming from, where this is headed: you already know how to aggregate rows with GROUP BY and filter an aggregate with HAVING, and you already know what a subquery is — a query nested inside another query. This reading is entirely about giving that nested query a name and moving it to the top, so it reads top to bottom. Once that clicks, the same WITH syntax scales up to naming several steps in a row, each one building on the step named before it.

4. A CTE, by itself first

Before rewriting anything, look at a CTE with nothing to compare it to. Here are five real rows from hours_logged:

Alden Retail92026-06-13

Casa Nova Design62026-06-06
WITH heavy_weeks AS ( SELECT client_name, hours FROM hours_logged WHERE hours >= 15 ) SELECT COUNT(*) FROM heavy_weeks;

The WITH clause defines heavy_weeks as its own small query — just rows where hours >= 15 — before the real question (SELECT COUNT(*)) ever runs.

5. The same query, side by side

Back to the full question from section 1: which clients logged more total hours than the average client. Here are both versions again, next to each other.

Version A: Nested subquery

SELECT client_name, SUM(hours) AS total_hours FROM hours_logged GROUP BY client_name HAVING SUM(hours) > ( SELECT AVG(client_total) FROM ( SELECT SUM(hours) AS client_total FROM hours_logged GROUP BY client_name ) AS client_totals );

Version B: CTE

WITH client_totals AS ( SELECT client_name, SUM(hours) AS total_hours FROM hours_logged GROUP BY client_name ) SELECT client_name, total_hours FROM client_totals WHERE total_hours > (SELECT AVG(total_hours) FROM client_totals);

6. Rewrite it yourself

A different question, same table: which weeks had more total hours logged, across all clients, than the average week? Here's the nested subquery version:

SELECT week_ending, SUM(hours) AS week_total FROM hours_logged GROUP BY week_ending HAVING SUM(hours) > ( SELECT AVG(week_sum) FROM ( SELECT SUM(hours) AS week_sum FROM hours_logged GROUP BY week_ending ) AS week_sums );

Complete the CTE rewrite below by typing the two missing keywords.

____ week_sums AS ( SELECT week_ending, SUM(hours) AS week_total FROM hours_logged GROUP BY week_ending ) SELECT week_ending, week_total FROM week_sums ____ week_total > (SELECT AVG(week_total) FROM week_sums);
Need a hint?

Blank 1 is the keyword that starts every CTE definition. Blank 2 filters week_total in the final query — but notice the final query doesn't have its own GROUP BY. week_total is already a plain column at that point, not a fresh aggregate, so the clause that only works on aggregates isn't the one you need here.

10. How this shows up in interviews

Being handed a query with a CTE and asked to explain what it does — or read it out loud, step by step — is a common warm-up in SQL technical screens. So is the reverse: being handed a nested subquery and asked "how would you make this easier to review?"

"Why would you use a CTE instead of a subquery here?" is also a direct, honest question about writing maintainable code. There often isn't a performance difference between the two — the real answer is about which one a teammate can trust and review faster, which is exactly the judgment this reading practices.

11. Reflection

12. Summary & critical thinking

Two ideas carried this whole reading: a CTE and a subquery can compute the exact same result, and the only thing that changes is whether that intermediate step gets a name and moves to the top of the query, or stays anonymous and nested. Naming it is what turns "read this inside out" into "read this top to bottom."

New situation: a nonprofit's donor database has a query finding donors who gave more than the average donation total, written as a subquery nested three levels deep. A teammate reviewing your pull request asks you to make it easier to review. What's the first thing you'd do?

13. Thinking ahead

Everything here involved naming exactly one intermediate step. Some business questions need more than one — a per-client total, then a rank among clients, then a filter on that rank, each step feeding the next. Chaining several named steps together, each one building on the step named just before it, uses this exact same WITH syntax, just repeated more than once inside one query.
