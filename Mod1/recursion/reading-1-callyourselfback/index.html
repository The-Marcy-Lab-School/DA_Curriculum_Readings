Call Yourself Back

This reading isn't required for any current project. But recursion changes how you see a whole category of problems, from searching a nested folder structure to walking a tree of comments on a webpage, and it's one of the most reliable topics an interviewer will reach for. Picture looking for a file on your laptop: you open a folder, and inside it there's another folder, and inside that one there's yet another folder, until finally you find the file. You didn't write a new search process for each level. You did the exact same thing, over and over, on a smaller piece of the problem each time. That's the whole idea behind recursion, and it's what this reading is about.

1. Introduction

Go back to that file search for a second. Say you're looking for report.pdf, and it's buried inside Documents, which contains Projects, which contains 2026, which finally contains the file. A file explorer doesn't have four different pieces of code, one for each level of nesting. It has one piece of logic: "look inside this folder; for anything that's a file, check if it's the one I want; for anything that's itself a folder, do this exact same check inside it." That single instruction, applied to itself, is enough to search a folder tree that's four levels deep, or forty.

Now stretch that idea to a function. What if a function, in the middle of doing its job, could pause and call itself again to handle a smaller version of the same problem, then use that answer to finish its own job? The first time you hear that description it can sound like nonsense, or like an infinite loop waiting to happen: if search_folder() calls search_folder(), what stops it from calling itself forever? That question is exactly the right one to ask, and answering it is what this whole reading builds toward.

Why this matters: a huge share of real data and code isn't flat. Folders contain folders. A comment on a post can have replies, and those replies can have their own replies. A JSON object can have a value that is itself another JSON object. Recursion is the natural way to process anything that's shaped like "the same structure, repeated inside itself," and interviewers know it: "write a recursive function" or "walk me through the base case" shows up constantly in technical screens, for data roles and software roles alike.

Where you're coming from, where this is headed: you already know how to repeat an action with a loop, checking a condition each time around. Recursion repeats an action too, but instead of a loop checking a condition, it's a function calling itself and checking when to stop. Once that clicks, you'll have a second, genuinely different tool for "do this over and over" problems, one that fits nested, branching structures far more naturally than a loop ever could.

2. Concept overview: a function that calls itself

Start as small as possible. Here's a function that counts down from a number to zero:

def countdown(n): if n == 0: print("Liftoff!") return print(n) countdown(n - 1) countdown(3)

Predict first: what happens when countdown(3) runs?

Read countdown closely and two very different jobs are happening inside it. Most of the time, it prints the current number and then calls itself with a smaller number, n - 1, getting one step closer to zero. But when n actually reaches 0, it does something completely different: it prints "Liftoff!" and returns, without calling itself again at all. That second branch is the only reason this doesn't run forever.

Those two jobs have names, and every working recursive function needs both of them:

  • The base case is the condition under which the function stops calling itself and just returns an answer directly.
  • The recursive case is everything else: the function does a small piece of work, then calls itself again with an input that's closer to the base case.

Here's the same shape in a more useful example: computing a factorial. The factorial of 4, written 4!, means 4 × 3 × 2 × 1, which is 24. Notice that 4! = 4 × 3!, and 3! = 3 × 2!, and so on, all the way down to 1! = 1. That last fact, that the factorial of 1 is just 1 with no further multiplying needed, is the base case waiting to happen.

5. The call stack, growing and unwinding

Here's the part that makes recursion feel less like magic: when factorial(4) calls factorial(3), Python doesn't throw away factorial(4)'s work. It pauses factorial(4) exactly where it is, remembers everything it needs to finish later, and starts a brand new call to factorial(3) on top of it. That "pause and remember" record is a stack frame, and the whole pile of paused, waiting calls is the call stack.

Every call is real and every call is still "alive," just paused, waiting for the one above it. Once factorial(1) hits the base case and returns 1 without calling anyone else, there's nothing left waiting above factorial(2). It resumes exactly where it paused, finishes its own multiplication, and returns its own answer to factorial(3). That's the unwind: the stack shrinks back down in the exact reverse order it grew, and each frame disappears once it hands its answer to the one below it.

7. Which happens first: the call, or the return?

Look again at the recursive case: return n * factorial(n - 1). It's tempting to read code left to right and assume n * happens before factorial(n - 1). Put these four events in the order they actually happen for one recursive call, then use the self-check button to confirm.

  • Python evaluates factorial(n - 1), which means making that recursive call.
  • The current call pauses on this line, waiting for that recursive call to fully finish and return a value.
  • Once a value comes back, Python multiplies it by n.
  • The current call returns that product to whichever call is waiting on it.
The recursive call always finishes completely, all the way down to a base case and all the way back up, before the line that made it can move on to its own multiplication and return. Nothing about "call yourself" skips that waiting.

9. When there's no way out: stack overflow

Every recursive function you've seen so far has a base case that the recursive case is guaranteed to reach eventually, because each call moves the input strictly closer to it: n - 1 counts down toward 1, an empty list is what numbers[1:] eventually produces. Drop the base case, or write a recursive case that never actually approaches it, and the calls never stop pausing and stacking on top of each other.

def countdown_broken(n): print(n) countdown_broken(n - 1) # no base case at all countdown_broken(3)

10. Real-world recursion: folders, threads, and nested data

The folder search from the introduction is one real example, but it's far from the only one. Three shapes show up constantly in real software, and all three are naturally recursive because each one is "the same structure, nested inside itself":

  • File systems. A folder can contain files and other folders, and those folders can contain more folders. Searching, counting every file, or computing total size all recurse into each subfolder the same way.
  • Nested comment threads. A comment on a post can have replies, and each reply can have its own replies. Rendering a whole thread means rendering a comment, then recursively rendering each of its replies the exact same way.
  • Nested JSON objects. A JSON object's value can itself be another JSON object (or a list of them). Pulling every value out of a deeply nested API response means checking each value: if it's a plain value, use it; if it's itself an object, recurse into it.

Now try writing the recursive step yourself. Here's a simplified search_folder in pseudocode:

def search_folder(folder, target_name): for item in folder.contents: if item.is_file and item.name == target_name: return item # base case: found it if item.is_folder: found = ____(item, target_name) # what goes here? if found: return found return None # base case: not in this branch

12. How this shows up in interviews

Recursion is one of the most common topics in a technical interview, in two different forms. The first is direct: "write a recursive function to do X," often factorial, summing a list, or reversing a string. The second is a follow-up question, no matter which approach you used: "what's the base case here, and how do you know it's actually reached?" Interviewers ask that second question because a recursive function without a guaranteed base case is a real, ship-blocking bug, not just an academic detail.

A very common interview moment is being handed a recursive function with a bug in its base case, like a factorial function that checks n == 0 but is only ever called on positive integers starting at 1, or one with no base case at all, and being asked to find the problem by tracing it out loud. Narrating the call stack, "this call is waiting on that call, which is waiting on that one," is exactly the skill practiced in section 6 above, and it's what separates a confident answer from a guess.

For software-engineering-leaning roles, expect a follow-up about cost too: recursion that calls itself once per element, like sum_list above, uses one stack frame per call, so a very long list can use a meaningful amount of memory that a loop-based version wouldn't.

14. Summary & critical thinking

Every working recursive function rests on the same two pieces: a base case that stops the calling, reachable without fail, and a recursive case that does a little work and moves strictly closer to that base case. The call stack is what makes it possible: each call pauses and waits rather than disappearing, so once the base case answers, every waiting call above it can finish in reverse order, all the way back to the original call.

New situation: you need a function that counts how many items are in a nested list, like [1, [2, 3, [4]], 5], where a list can contain more lists inside it to any depth. What should the base case be?

15. Thinking ahead

Nested structures with no fixed depth, folders inside folders, comments inside comments, are everywhere once you start looking, and a tree is exactly that shape formalized: a node that can have child nodes, each of which can have their own children. Walking a tree top to bottom, searching it, or adding up every value inside it almost always reads more naturally as recursion than as a loop, for the same reason the folder search did here. If a tree structure comes up next, the base case and recursive case habit practiced in this reading, and the "trust that the smaller call works" leap of faith behind it, is the exact foundation that idea builds on.
