One Job at a Time

A fitness tracker sends a week of daily step counts to a short Python script. One function has already checked every record: each has a day name and a whole-number step count, and the bad records were set aside. Now the user wants a weekly summary: total steps, and how many days met their step goal. Should the checking function also build that summary, or should the summary get a function of its own?

1. Concept overview

The checking function in the step tracker is validate_days. Checking that data has the right shape and values before anything uses it is called validation. The job of validate_days ends once it decides which records are valid.

A second function, summarize_steps, starts where validate_days stops. It receives only valid records, so it never asks whether a record is good. That question was already answered. Reporting useful information from data that already passed validation is called summarizing.

Before writing any code, decide the function's contract: what goes in, what its one job is, and what comes out.

INTwo parameters: days, a list of valid (day, steps) tuples, and goal, the daily step goal.
ONE JOBSummarize the week: total steps, and the number of days that met the goal.
OUTA return value: a summary dict. Printing it is a separate job.

The OUT box matters. summarize_steps returns its result instead of printing it. Another function can then print the summary, save it to a file, or compare it with last week's summary. Each of those is its own job, and none of them requires a change to summarize_steps. A function with one job like this is a single-purpose function. You can describe its job in one sentence.

To add up a week of steps, summarize_steps uses an accumulator: a variable set before a loop and updated on every pass. After the loop ends, the accumulator holds the answer.

days = [ ("Mon", 6200), ("Tue", 9120), ("Wed", 8000), ("Thu", 4300), ("Fri", 10450), ] total = 0 for day, steps in days: total += steps print(total)
38070

total starts at 0. Each pass adds one day's steps. When the loop runs out of days, total holds the week's steps.

Why this matters: one long function that checks, summarizes, and prints usually works at first. Trouble starts with the first change request. A new kind of summary means editing the same function that does the checking, so a small edit can break the checks. Reviewers flag this often, in take-home tasks and in code reviews.

Where you're coming from, where this is headed: you already know how to write a function with parameters and a return value, and how to write a function that checks records. This reading adds a second function that works only on records that passed. Splitting work into small functions, each with one job, is how larger programs stay easy to change: each new request gets a new function instead of a longer old one.

9. Run it yourself: change the goal


Pick a goal. The file below changes to use that goal in its call. Then run it and compare. Only the goal argument changes. The function itself stays the same.



 

days = [
    ("Mon", 6200),
    ("Tue", 9120),
    ("Wed", 8000),
    ("Thu", 4300),
    ("Fri", 10450),
]

def summarize_steps(days, goal):
    total = 0
    goal_days = 0
    for day, steps in days:
        total += steps
        if steps >= goal:
            goal_days += 1
    return {"total": total, "goal_days": goal_days}

summary = summarize_steps(days, 8000)
print(summary)

12. Debug the extra check


A teammate writes this version of summarize_steps:


days = [
    ("Mon", 6200),
    ("Tue", 9120),
    ("Wed", 8000),
    ("Thu", 4300),
    ("Fri", 10450),
]

def summarize_steps(days, goal):
    total = 0
    goal_days = 0
    for day, steps in days:
        try:
            steps = int(steps)
        except ValueError:
            print(f"Skipping {day}: steps is not a number")
            continue
        total += steps
        if steps >= goal:
            goal_days += 1
    return {"total": total, "goal_days": goal_days}

print(summarize_steps(days, 8000))


{'total': 38070, 'goal_days': 3}


validate_days already guarantees every step count is a whole number. What is the design problem with the teammate's version of summarize_steps?

14. How this shows up in interviews




"Can you split this into two functions?" is common code review feedback in data and software roles. A reviewer flags a function that validates and summarizes because a change to one part can break the other. It is also harder to test: you can't test the summary without also passing data through the checks buried in the same function.


Take-home rubrics often score this directly, with a line like "each function has a single, clear job."




An interviewer shows you a 90-line function that validates records, summarizes them, and emails the summary. They ask how you'd improve it. What's the strongest answer?












15. Summary & critical thinking


Once one function has validated the data, a second function can summarize it without re-checking anything. That summarizing function uses accumulators to build its results and returns them, so other functions can print or save them. A new kind of job gets a new function instead of a longer old one.


New situation: a podcast team already validates its episode records: a title and a listen count. summarize_episodes(episodes) returns the total listens and the most-listened title. A teammate now wants the host to get that summary by email every Monday. What should the team do?


















16. Thinking ahead


The one-job habit grows with a program. A longer pipeline chains several small functions, each doing one job and passing its return value to the next. Later, related data and the functions that act on it get bundled into a single object. That is the same one-job idea applied to a bigger piece of code.
