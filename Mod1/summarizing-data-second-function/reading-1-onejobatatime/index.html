One Job at a Time

A car rental company already runs every incoming vehicle-return record through a function that checks it's usable: a real vehicle ID, a fuel reading between 0 and 100. That checking is done and the records are accepted. Now the operations team wants something different from that same batch: a readable report of what came back, which vehicles need fuel before their next rental, and how many vehicles were processed today. Should the function that already checked the data grow to also report on it, or does reporting deserve a function of its own?

1. Concept overview

Picture that return desk. A separate function has already walked through every incoming record and confirmed each one is usable: a real vehicle ID, a fuel percent between 0 and 100. That function's job ends the moment it says accepted or not. Now a second function needs to start exactly where the first one leaves off, working only with records already known to be good: print a formatted listing of every vehicle, flag any vehicle whose fuel is low enough to need refueling before its next rental, and report how many vehicles came back in total.

Before writing a single loop, this new function needs its own contract: what does it receive, what is its one job, and what does it hand back?

INThe list of already-accepted return records: vehicle ID and fuel percent.
ONE JOBReport on the accepted batch: a listing, a low-fuel alert, and a total count.
OUTNothing returned. The job itself is printed output.

That last box is worth pausing on. The validating function's contract was to hand back a list of problems. This function's contract is different: its whole job can be a side effect, printed text, and that's a perfectly complete contract as long as it's decided on purpose, not left as an accident of whatever code got written first.

Why this matters: "write a function that summarizes a batch of already-checked records" is one of the most common second steps in a data or software take-home task, right after a validation function. A shaky answer almost never comes from the loop itself, it comes from the reporting function quietly re-checking things the earlier function already guaranteed, or from mixing reporting with a second unrelated task like logging or notifying someone.

Where you're coming from, where this is headed: you already know how to design a function's contract, and you already know how to write a function that validates a batch and hands back a list of problems. This reading is about writing a second function that starts exactly where that one leaves off: accepted data in, a report out. Once separating those two responsibilities feels automatic, the same instinct keeps paying off as a program grows: instead of one function that keeps absorbing every new requirement, each new job gets its own small function, chained to the ones before it.

12. Debug the responsibility leak

A teammate writes this version of the reporting function:

def report_vehicle_returns(returns): for vehicle_id, fuel_percent in returns: try: fuel_percent = int(fuel_percent) except ValueError: print(f"Skipping {vehicle_id}: fuel percent not a number") continue print(f"{vehicle_id}: {fuel_percent}% fuel")

validate_returns(records) already guarantees every fuel_percent is a valid number before this function ever runs. What's the design problem with the code above?

14. How this shows up in interviews

A shockingly common piece of code review feedback, in data and software roles alike, is some version of "can you split this into two functions?" A function that both validates and reports, or that reports and also logs to a database, is exactly the kind of thing a reviewer flags, not because the code is wrong, but because a change to one responsibility now risks breaking an unrelated one, and because no one can test the reporting logic without also setting up valid data for the validation logic buried inside it.

Take-home assessments score this directly, too. Plenty of data-role take-home rubrics include a line like "functions have a single, clear responsibility," precisely because a sprawling one-function solution is one of the most common ways an otherwise-correct take-home loses points.

An interviewer hands you a 90-line function that validates, reports, and emails a summary, and asks how you'd improve it before shipping. What's the strongest answer?

15. Summary & critical thinking

One habit carried this whole reading: once a function has approved a batch of data, a second function can report on it freely, a listing, an alert, a count, without re-checking what the first function already guaranteed. Any genuinely new kind of job that shows up later deserves its own function rather than growing an existing one.

New situation: a tutoring service already has a validated batch of session records (tutor ID, minutes tutored). A second function is asked to print a listing of every session, flag any session logged over 90 minutes for a supervisor to double check, and print the total number of sessions logged today. Which description best fits this second function?

16. Thinking ahead

The contract-first, one-job habit practiced here keeps scaling as a program grows. A pipeline can chain three or four small functions together instead of two, each one still doing exactly one job, feeding the next. Eventually, related data and the functions that act on it stop getting passed between separate functions altogether and get bundled together into a single object instead, which is the same one-responsibility instinct applied to an entire unit of code rather than just one function.
