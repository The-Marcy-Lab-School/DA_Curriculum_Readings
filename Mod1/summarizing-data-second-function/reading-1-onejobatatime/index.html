One Job at a Time

A fitness tracker counts your steps each day. A Python program gets one week of those counts. One function already checked the data and kept only the good days. Now you want a weekly summary: total steps, and how many days you met your step goal. Should the checking function do that too, or should the summary get its own function?

Your goal: write a second function with one job, summarizing, that returns its result. Small one-job functions are easier to change, because each new request gets a new function.

2. One job for each function

A function is a named block of code that runs when you call it. The step tracker already has one: validate_days. Validation is checking that data has the right shape and values before anything uses it. validate_days keeps only the good days and returns them as a list of tuples, like [("Mon", 6200), ("Tue", 9120)]. Its job ends there.

A second function, summarize_steps, starts where validate_days stops. It gets only good days, so it never asks whether a day is good. Summarizing means reporting useful facts, like a total, from data that was already checked.

Before writing any code, decide three things: what goes in, what the one job is, and what comes out.

INTwo parameters: days, a list of good (day, steps) tuples, and goal, the daily step goal. A parameter is a name in the function's first line that gets a value when the function is called.
ONE JOBSummarize the week: total steps, and the number of days that met the goal.
OUTA return value: a summary dict. The return value is what a function hands back to the code that called it. Printing it is a separate job.

summarize_steps returns its result instead of printing it. Then another function can print the summary, save it to a file, or compare it with last week's. Each of those is a new job, and none of them needs a change to summarize_steps. A function with one job like this is a single-purpose function: you can say what it does in one sentence.

Count jobs, not outputs: a function that returns two results about the same data still has one job. Drag each function into the zone that fits (on a phone, tap a chip and then tap a zone). Then press the self-check button.

validate_days(records) keeps the records that have a day name and a whole-number step count, and returns them. summarize_steps(days, goal) adds up the steps, counts the days that met the goal, and returns both in a dict. sync_week(records) checks each step count, prints a list of the week, and posts the total to a group chat. summarize_and_save(days) builds the weekly summary and also writes it to a file.

3. Add things up with an accumulator

To add up a week of steps, summarize_steps uses an accumulator: a variable set before a loop and updated on every pass. After the loop ends, the accumulator holds the answer.

Reminder: +=

total += steps is short for total = total + steps. It takes the old total, adds steps, and stores the result back in total.

Here are the five days used in every file on this page.

4. Trace it, then change the goal

trace_steps.py is summarize_steps with one print added inside the loop, so you can watch both accumulators change on each pass.

# The same five days as in total_steps.py days = [("Mon", 6200), ("Tue", 9120), ("Wed", 8000), ("Thu", 4300), ("Fri", 10450)] def summarize_steps(days, goal): total = 0 goal_days = 0 for day, steps in days: total += steps if steps >= goal: goal_days += 1 print("after", day, "total =", total, "goal_days =", goal_days) return {"total": total, "goal_days": goal_days} summary = summarize_steps(days, 8000) print(summary)

5. Don't check twice

A teammate writes this version of summarize_steps. It uses try/except to skip any day whose steps aren't a number.

New in this file: continue

continue skips the rest of the loop body for this pass and moves on to the next day.

# The same five days as in total_steps.py days = [("Mon", 6200), ("Tue", 9120), ("Wed", 8000), ("Thu", 4300), ("Fri", 10450)] def summarize_steps(days, goal): total = 0 goal_days = 0 for day, steps in days: try: steps = int(steps) except ValueError: print("Skipping", day, "because steps is not a number") continue total += steps if steps >= goal: goal_days += 1 return {"total": total, "goal_days": goal_days} print(summarize_steps(days, 8000))
{'total': 38070, 'goal_days': 3}

validate_days already makes sure every step count is a whole number. What is the design problem with the teammate's version?

The fix is the version in summarize_steps.py in section 3: it trusts the days it gets and only summarizes them.

7. Wrap-up

  • Once validate_days has checked the data, summarize_steps can summarize it without checking again.
  • An accumulator starts before the loop, changes on every pass, and holds the answer after the loop.
  • summarize_steps returns its result, so a new job, like printing or saving, gets a new function instead of a longer old one.

New situation: the step tracker's app now wants to email each user their weekly summary every Monday. summarize_steps already returns the summary dict. What should the team do?

In interviews: "Can you split this into two functions?" is common feedback on code, so practice saying each function's job in one sentence.

Where this goes next: a longer program chains several small functions, each passing its return value to the next. Later, related data and the functions that work on it get bundled together into one object.
