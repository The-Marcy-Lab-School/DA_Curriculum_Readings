One Job at a Time

A community fridge app has already checked that today's inventory records are usable. Now a coordinator asks, “What do we actually have, what is running low, and how many items are listed?” Should the code check everything again—or trust the earlier step and summarize?

1. Vocabulary: tools for today's thinking

Flip each card before moving on.

2. Recall: what should happen first?

A row arrives as ("Rice", "many"), but the second value is required to be an integer. Which job should catch that problem?

3. Two stages, two responsibilities

Stage A: Validate

Ask: “Is this data acceptable?”

Examples: correct structure, expected types, required rules.

Stage B: Summarize

Ask: “What useful report can I make from accepted data?”

Examples: readable listing, alerts, totals.

Key idea: a summary function can print a listing, an alert section, and a total while still having one job: report on the accepted data.

4. Trace a fresh listing

Assume this data has already passed validation:

supplies = [
    ("Rice", 7),
    ("Beans", 2),
    ("Soap", 5),
    ("Pasta", 1),
]

def report_supplies(supplies):
    for name, count in supplies:
        print(f"{name}: {count} units")

6. Why a second loop can still be one job

Suppose the function first loops to print every record, then loops again to print only records below a threshold.

Does the second loop automatically mean the function now has two jobs?

Distinction: checking count < 3 to decide whether an already-valid record belongs in an alert is filtering/reporting. Checking whether count is even a valid integer belongs to validation.

11. Required bridge to lecture/lab

You just practiced the core design habit for the upcoming lesson: validation decides whether data is acceptable; summarizing reports on data that is already accepted. You also traced formatted output, an alert condition, and a total using len().
