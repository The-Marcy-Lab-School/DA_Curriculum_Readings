Looks Right. Is It?

A TV streaming app emails each viewer a monthly summary: minutes watched and episodes finished. An AI tool wrote the code that builds it. The code runs and prints neat numbers. Then viewers write in to say their numbers are wrong. Code that runs is not always code that is correct. Here you learn to catch the difference.

Skills you'll practice in this reading:

Attention to Detail — independently catching a planted bug, edge case, or inconsistency that a surface-level read-through would miss.

Your goal: decide what the output should be before you run the code, then check what it really prints. That habit catches bugs a quick look misses, and "find the bug in this function" is a common interview task. Every bug here sits in a loop, function, or class you already know how to write.

1. Quick recall

Two skills you already have come up in this reading: what range() gives a loop, and what a bare except: does.

Recall: for i in range(3): print(i). What prints?

Reminder: an except: with no error name after it is a bare except:. It catches every error.

Recall: a function wraps its work in try, and its bare except: block returns 0. A mistake in the try block raises an error. What happens?

2. Expected vs. actual: the session that never got counted

The summary code reads each viewer's watch history: one number per viewing session, in minutes. Before you run any code, work out what it should print. Add the five sessions in [50, 42, 95, 38, 61] by hand and you get 286. That is the expected behavior: what the code should do. What the code really prints is the actual behavior. Any gap between the two is a bug.

New in this file: range(start, stop) counts from start up to, but not including, stop. So range(2, 5) gives 2, 3, 4. sessions[i] is the item at position i, and positions count from 0.

Expected behavior: 286. Predict: what does month_total.py actually print?

sessions = [50, 42, 95, 38, 61]
total = 0

for i in range(1, len(sessions)):
    total += sessions[i]

print(total)
236

Click through the loop one pass at a time to see which session it skips.

The code ran without crashing, but the total is wrong. That is a logic error. This one is an off-by-one error: the loop runs one time too few, so it skips the first session. Looping over the items themselves leaves no position math to get wrong:

sessions = [50, 42, 95, 38, 61]
total = 0

for minutes in sessions:
    total += minutes

print(total)
286

3. Bugs that crash: scope and attributes

Some bugs stop the program with a traceback. These are easier to find, because the traceback names the line. Read it from the last line up.

The count that vanishes

A session of 40 minutes or more counts as a finished episode. Four of the five sessions reach 40.

Expected behavior: prints 4. Predict: what happens when count_finished.py runs?

def count_finished(sessions):
    finished = 0
    for minutes in sessions:
        if minutes >= 40:
            finished += 1

count_finished([50, 42, 95, 38, 61])
print(finished)
Traceback (most recent call last):
  File "count_finished.py", line 8, in <module>
    print(finished)
          ^^^^^^^^
NameError: name 'finished' is not defined

This is a scope bug: code uses a variable where it does not exist. finished is created inside count_finished, so it exists only inside that function. The fix has two parts: the function returns finished, and the last line prints what comes back.

def count_finished(sessions):
    finished = 0
    for minutes in sessions:
        if minutes >= 40:
            finished += 1
    return finished

print(count_finished([50, 42, 95, 38, 61]))
4

The attribute that was never there

Ana watched 286 minutes this month. The hours method should turn that into hours.

Expected behavior: prints about 4.77. Predict: what happens when viewer_hours.py runs?

class Viewer:
    def __init__(self, name, minutes_watched):
        self.name = name
        self.minutes_watched = minutes_watched

    def hours(self):
        return self.minutes_watch / 60

ana = Viewer("Ana", 286)
print(ana.hours())
Traceback (most recent call last):
  File "viewer_hours.py", line 10, in <module>
    print(ana.hours())
          ~~~~~~~~~^^
  File "viewer_hours.py", line 7, in hours
    return self.minutes_watch / 60
           ^^^^^^^^^^^^^^^^^^
AttributeError: 'Viewer' object has no attribute 'minutes_watch'. Did you mean: 'minutes_watched'?
Need a hint?

Compare the attribute name that __init__ sets with the one that hours reads, letter by letter.

This is an undefined attribute: code uses an attribute the object never got. An object has only the attributes that were set on it, and a name that is one letter off counts as a different attribute.

Fill in the blank so hours reads the attribute that __init__ set.

class Viewer:
    def __init__(self, name, minutes_watched):
        self.name = name
        self.minutes_watched = minutes_watched

    def hours(self):
        return self.____ / 60

ana = Viewer("Ana", 286)
print(ana.hours())
4.766666666666667
  1. Look at the lines in __init__ that start with self..
  2. Find the one that stores the minutes.
  3. Type the name that comes after self., spelled exactly the same. You can leave out self..
  4. Press Check. When it's right, the Run button shows what the file prints.

Why: hours can only read an attribute by the exact name __init__ gave it.

4. A bug that hides: the bare except:

One session record is missing its end time. That is an edge case: an unusual input, like an empty list, a 0, or a missing value, that normal tests miss.

Expected behavior: the code tells you the end time is missing. Predict: what happens when session_minutes.py runs?

def session_minutes(session):
    try:
        return session["end"] - session["start"]
    except:
        return 0

print(session_minutes({"show": "Night Shift", "start": 1200}))
0

The bare except: caught the KeyError and returned 0. A 0 looks like a real answer, so the session's minutes quietly disappear from the summary. The fix names the error it expects and reports what went wrong:

def session_minutes(session):
    try:
        return session["end"] - session["start"]
    except KeyError:
        print("Missing end time for", session["show"])
        return None

print(session_minutes({"show": "Night Shift", "start": 1200}))
Missing end time for Night Shift
None

Now the problem shows up in the output. Any other mistake in the try block, such as a typo, still raises its own error instead of hiding behind a 0.

5. After the fix: refactor

Once the code is correct, you may want to tidy it. A refactor changes how code is organized without changing what it does. summary_before.py writes the same loop twice. summary_after.py moves that loop into one function.

sessions = [50, 42, 95, 38, 61]

total = 0
for minutes in sessions:
    total += minutes
print("Minutes:", total)

total = 0
for minutes in sessions:
    total += minutes
print("Hours:", total / 60)
Minutes: 286
Hours: 4.766666666666667
def total_minutes(sessions):
    total = 0
    for minutes in sessions:
        total += minutes
    return total

sessions = [50, 42, 95, 38, 61]
print("Minutes:", total_minutes(sessions))
print("Hours:", total_minutes(sessions) / 60)
Minutes: 286
Hours: 4.766666666666667

The two outputs match line for line. That is how you confirm a refactor: run the same case before and after, and compare.

7. Wrap-up

  • Work out the expected behavior first, by hand, on a small case. Then run the code and compare.
  • A scope bug or an undefined attribute crashes, and the traceback points at the line. Read its last line first.
  • An off-by-one error or a bare except: prints a believable wrong answer. Only your expected answer catches it.

New situation: a viewer counted 12 finished episodes this month. The summary email says 11. The code never crashed. What should you do first?

In interviews, "find the bug in this function" is a common task. Talk it through in three steps: observe the wrong output, isolate the line, and confirm the fix by rerunning the case that failed.

The same habit works when you review a teammate's code or check code an AI tool wrote for you.

Why: naming the line, what it does now, and what it should do is how you report a bug so someone else can fix it.
