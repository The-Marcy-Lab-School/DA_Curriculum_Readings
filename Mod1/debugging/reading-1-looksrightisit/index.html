Looks Right. Is It?

A streaming service emails each viewer a monthly recap: minutes watched, episodes finished, and hours of viewing. A teammate used an AI tool to write the script that builds the recap. The script runs and prints a tidy summary. Then viewers start writing in to say their numbers are wrong. Code that runs is not the same as code that is correct. This reading builds the habit that catches the difference: decide what the output should be, then check what the code actually does.

1. Concept overview

The recap script reads each viewer's watch history: one number per viewing session, in minutes. One viewer's history is [50, 42, 95, 38, 61]. The script should add all five sessions and print 286. That is the expected behavior. The script prints 236. That is the actual behavior. Any gap between expected and actual behavior is a bug.

This bug is a logic error: the code runs without crashing, but the result is wrong. Nothing on screen warns you. You catch it only by working out the expected answer first and comparing.

Why this matters: a wrong number in a recap, a report, or a paycheck raises no error. People just trust it. "Find the bug in this function" is also a common interview task, and interviewers watch your method more than your answer.

Where you're coming from, where this is headed: you already write loops, functions, and classes. Every bug in this reading lives in one of those tools, used almost correctly. The habit you build here is to decide the expected behavior before you trust the actual behavior. It works on any code you did not write, including code an AI tool writes for you.

4. Bug hunt: the session that never got counted

sessions = [50, 42, 95, 38, 61] total = 0 for i in range(1, len(sessions)): total += sessions[i] print(total)
236

Expected behavior: the total of all five sessions, 286.

Predict the actual behavior. What does this code print?

Click through the loop one pass at a time to see which session it skips.

This is an off-by-one error. range(1, len(sessions)) starts at index 1, so sessions[0] never gets added. Writing for minutes in sessions: visits every item with no index math to get wrong.

5. Bug hunt: the count that vanishes

A session of 40 minutes or more counts as a full episode. count_finished should count those sessions.

def count_finished(sessions): finished = 0 for minutes in sessions: if minutes >= 40: finished += 1 count_finished([50, 42, 95, 38, 61]) print(finished)
Traceback (most recent call last):
  File "count_finished.py", line 8, in <module>
    print(finished)
          ^^^^^^^^
NameError: name 'finished' is not defined

What happens when this code runs?

This is a scope bug. It crashes, which makes it easier to find than a logic error: the traceback names the line. The fix has two parts. count_finished ends with return finished, and the caller prints what comes back: print(count_finished([50, 42, 95, 38, 61])).

6. Bug hunt: the attribute that was never there

class Viewer: def __init__(self, name, minutes_watched): self.name = name self.minutes_watched = minutes_watched def hours(self): return self.minutes_watch / 60 ana = Viewer("Ana", 286) print(ana.hours())
Traceback (most recent call last):
  File "viewer_hours.py", line 10, in <module>
    print(ana.hours())
          ~~~~~~~~~^^
  File "viewer_hours.py", line 7, in hours
    return self.minutes_watch / 60
           ^^^^^^^^^^^^^^^^^^
AttributeError: 'Viewer' object has no attribute 'minutes_watch'. Did you mean: 'minutes_watched'?

What happens when ana.hours() runs?

Need a hint?

Compare the attribute name that __init__ sets with the one that hours reads, letter by letter.

This is an undefined attribute. An object has only the attributes that were actually set on it. A name that is one letter off counts as a different attribute.

7. Bug hunt: the error nobody sees

def session_minutes(session): try: return session["end"] - session["start"] except: return 0 print(session_minutes({"show": "Night Shift", "start": 1200}))
0

One session record is missing its end time: {"show": "Night Shift", "start": 1200}. What happens when session_minutes runs on it?

9. Order the steps: a repeatable way to hunt a bug

Put these steps in the order you would follow when code runs but its output looks wrong. Click a step again to remove it, then press "Check my order." This self-check is not graded.

  • Write down the expected behavior for a small case, before running anything.
  • Run the code and record the actual behavior.
  • Trace the code line by line to find where actual first splits from expected.
  • Change the one line responsible.
  • Rerun the same case, plus an edge case, and confirm the actual behavior now matches.

12. How this shows up in interviews

"Find the bug in this function" is a common interview task. You get code that runs and an input that gives a wrong answer. Interviewers listen for your method more than your answer.

One clear way to talk it through is observe, isolate, validate:

  1. Observe the symptom: what the code printed, and what it should have printed.
  2. Isolate the line: trace until the actual behavior splits from the expected behavior.
  3. Validate the fix: rerun the case that failed and show it now matches.

For data roles, the same skill shows up as "This report total looks off. How would you check it?" Start with one small case you can work out by hand.

14. Summary & critical thinking

Every bug in this reading was a gap between expected and actual behavior. The scope bug and the undefined attribute crashed, so the traceback pointed at them. The off-by-one error and the silent except printed a wrong number with no warning. You catch those only by deciding the expected answer first, then tracing to the line where the two split.

New situation: a museum's ticket-scan script prints a daily visitor count and never crashes. The front desk counted 412 scans by hand. The script says 411. What should you do first?

15. Thinking ahead

Deciding the expected behavior first keeps mattering past a single script. It is how you review a teammate's code, check a function an AI tool wrote, and test your own project before you demo it to someone who will try an input you did not.
