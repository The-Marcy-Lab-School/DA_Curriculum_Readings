Looks Right. Is It?

A small accounting firm's expense-reimbursement script runs clean: no red error, no crash, a confident-looking summary printed at the end. Every function has a sensible name. Nothing about it looks suspicious. It is also quietly wrong in four different ways. This reading is about training the habit that catches code like that: reading with suspicion instead of trust, and proving correctness instead of assuming it.

1. Concept overview

Picture the firm's script: process_reimbursements reads a list of employee expense reports, adds up the total owed, flags any report over the daily cap for manual review, and logs report IDs so nobody gets paid twice for the same expense. Someone (maybe a coworker, maybe an AI tool) wrote it quickly, and it works — it runs top to bottom without a single exception. That's exactly the problem. "It ran" and "it's correct" are two completely different claims, and this script's fluent variable names and clean output are doing a very good job of hiding the gap between them.

Why this matters: a wrong reimbursement total doesn't announce itself. Nobody gets a stack trace when an employee is shorted twelve dollars or the firm quietly overpays a duplicate claim; the script just prints a plausible-looking number and everyone moves on. This exact situation, code that runs cleanly but does something quietly wrong, is also one of the most common formats for a technical interview: a take-home debugging exercise, or a live "find the bug" round where you're handed a working-looking function and asked what's actually wrong with it.

Where you're coming from, where this is headed: you already know how to write loops, conditionals, functions with parameters and default values, classes, and try/except blocks. Every bug in this reading lives inside one of those familiar tools, used almost correctly. This reading is about turning that same knowledge inward: reading code you didn't write with healthy suspicion, forming a prediction before you trust an output, and tracing to find exactly where reality and expectation split apart. That instinct, verify before you trust, is what separates code that merely runs from code you can actually ship.

2. Recall before hunting for bugs

Four skills get reused heavily below: default argument values, comparison operators, range()-based loops, and what a try/except block actually does when it catches an error. Test each one before moving on.

Coding check:

def greet(name="friend"): return "Hi, " + name print(greet())

What prints?

Coding check: budget = 500, spent = 500. What does spent > budget evaluate to?

Recall: for i in range(3): print(i). What prints?

Critical thinking: a function is wrapped in try/except, and the bare except: block returns 0 for any error at all. If a real bug trips that except, what happens to the program?

None of this changes once the bugs below get harder to spot. Default arguments, comparisons, loop ranges, and except blocks all still work exactly as they do here; the trick is noticing when they're used just slightly wrong.

4. Bug hunt: the report that never got counted

reports = [120, 340, 85, 610, 275] total = 0 for i in range(len(reports) - 1): total += reports[i] print(total)

The script is supposed to total all five reports. Predict first: what does this actually print?

5. Bug hunt: the comparison sitting on the fence

DAILY_CAP = 500 def exceeds_cap(amount): return amount > DAILY_CAP

The requirement says any report at or above the cap should be flagged for review. Which test amount is the strongest evidence that exceeds_cap doesn't match that requirement?

Boundary values are bug magnets. Whenever you see >, >=, <, or <=, test the value sitting exactly on the line.

6. Bug hunt: the list that remembers too much

def flag_duplicate(report_id, seen=[]): seen.append(report_id) return seen

The script calls this function once for every report it processes, in order: report 101, then report 102, then report 101 again (a genuine duplicate submission).

Predict first: what does the third call, flag_duplicate(101), actually return?

Need a hint?

A default value like [] is created exactly once, when Python first reads the def line, not fresh on every call. Every call that doesn't pass its own seen argument shares that same one list.

This one is much easier to hold in your head one call at a time. Click through it below.

7. Bug hunt: the error nobody sees

def get_reimbursement(report): try: return report["amount"] * report["rate"] except: return 0

Report 104 is malformed: {"id": 104, "amount": 200}, with no "rate" key at all. What happens when get_reimbursement runs on it?

8. Fill in the blank: fix the shared list

The standard fix for a mutable default argument replaces the mutable value with a safe placeholder, then builds the real list fresh inside the function body if none was passed in.

def flag_duplicate(report_id, seen=____): if seen is None: seen = [] seen.append(report_id) return seen

  • Change exactly one suspected line, based on that evidence.
  • Rerun the case that first exposed the problem, including the edge case, and confirm it now matches.

12. How this shows up in interviews

A take-home debugging exercise, a script with a handful of planted bugs and a request to find and fix them, is one of the most common formats for an early technical screen in a data role, precisely because it tests something a resume can't: whether you actually read code critically or just trust that it looks fine.

Live "find the bug" rounds are just as common: an interviewer hands you a working-looking function, tells you it produces a wrong answer for some input, and watches how you look for it. They're listening for the method, predicting an expected result and tracing toward it, not a lucky guess, and a boundary-value test like the one in section 5 is exactly the kind of instinct that stands out.

For software-engineering-leaning roles specifically, expect a direct follow-up like "why is a mutable default argument dangerous" or "what's wrong with a bare except:". Being able to explain the mechanism, not just recite "don't do that", is what the interviewer is actually checking for.

Interview-style question: you're handed a function that runs without error but returns a wrong-looking result for one specific input. What's the strongest first move?

14. Summary & critical thinking

Two habits carried this whole reading: forming a prediction before you trust an output, and tracing evidence-first when reality and expectation disagree, rather than editing several lines at once and hoping. Neither habit cares what the code looks like on the surface; both care whether it's actually doing what it claims.

New situation: a small veterinary clinic's scheduling script prints a clean daily appointment count and never crashes, but the front desk says today's count is one short. What should you do first?

15. Thinking ahead

The same instinct, verify before you trust, keeps mattering well past a single script: it's exactly what's needed the moment you review a pull request that isn't yours, the moment you accept a function an AI tool generated for you, and the moment right before you demo your own project to someone who will absolutely try an input you didn't think to test.
