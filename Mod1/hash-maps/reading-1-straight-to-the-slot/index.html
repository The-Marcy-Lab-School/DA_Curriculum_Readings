Straight to the Slot

At an arcade, you win paper tickets and trade them for prizes. A game card saves your tickets. Scan it at the prize counter, and your balance shows up right away, whether the arcade has 50 cards or 50,000. The scanner doesn't check every card. It works out where your balance is stored. That trick is called hashing.

3. From key to slot

A hash map (also called a hash table) stores key/value pairs. In the arcade, the key is the card number and the value is the ticket balance. A Python dict is a hash map. Inside, it keeps a row of numbered storage spots called slots (or buckets).

To pick a key's slot, the hash map runs the key through a hash function. A hash function turns a key into a number, and it gives the same number for the same key every time. That number is the key's hash code. Then the hash map divides the hash code by the number of slots and keeps the remainder. The remainder is always a slot number, because it is always smaller than the number of slots.

New in this file: % gives the remainder after dividing. 17 % 5 is 2, because 5 goes into 17 three times (15) with 2 left over. hash() is Python's own hash function. For a whole number, it gives back the same number.

Predict: card_slot.py prints two lines. What is the second line?

slots = 8 card = 26 code = hash(card) print(code) print(code % slots)
26
2

To look up card 26 later, the hash map does the same math, gets slot 2, and checks only that slot. It never looks at the other cards. So a dict lookup takes about the same time for 50 cards or 50,000.

4. When two keys collide

The arcade has many more cards than slots, so sooner or later two keys land in the same slot. That is a collision. Card 26 and card 34 both land in slot 2, because 34 % 8 is also 2. Collisions are normal, so every hash map has a plan for them.

One common plan is chaining: each slot holds a small list, and a new key that lands in a busy slot joins that list. Nothing gets written over.

arcade_table.py builds a tiny hash map with chaining. slots is a list of 8 empty lists, one per slot. put adds a (card, balance) pair to the list in the card's slot. get checks only the pairs in that one slot.

Predict: what does print(slots[2]) show?

slots = [[], [], [], [], [], [], [], []] def put(card, balance): index = card % len(slots) slots[index].append((card, balance)) def get(card): index = card % len(slots) for saved_card, balance in slots[index]: if saved_card == card: return balance return None put(26, 30) put(59, 12) put(34, 75) print(slots[2]) print(get(34))
[(26, 30), (34, 75)]
75

get(34) checked the two pairs in slot 2 and never looked at card 59. A short chain keeps a lookup fast.

Long chains slow a lookup down, because get has more pairs to check in one slot. The load factor tells you how crowded a table is: the number of stored pairs divided by the number of slots. arcade_table.py holds 3 pairs in 8 slots, a load factor of 3 / 8, or about 0.4. When the load factor gets too high, the hash map does a resize (also called a rehash): it makes a bigger row of slots and works out a new slot for every key. Python's dict does this on its own.

The arcade's table now holds 40 cards in 8 slots. What is the load factor, and what should the hash map do?

5. Two prizes for exactly 50 tickets

At the prize counter, each prize costs some tickets. A player has exactly 50 tickets and wants two prizes that use all 50. Which two prices add up to 50? Coding interviews ask this problem so often that it has a name: Two Sum.

The slow way checks every pair of prices:

prices = [35, 10, 20, 15, 30] tickets = 50 for i in range(len(prices)): for j in range(i + 1, len(prices)): if prices[i] + prices[j] == tickets: print(prices[i], prices[j])
35 15
20 30

The prize list doubles from 5 prices to 10. About how many times more pairs does prize_pairs_slow.py check?

The fast way walks through the list once. For each price, it works out the other price it would need, then asks whether it has already seen that price.

New in this file: in works on a set the same way it works on a list. A set is a hash map that stores keys with no values, so needed in seen jumps to one slot instead of checking every item.

prices = [35, 10, 20, 15, 30] tickets = 50 seen = set() for price in prices: needed = tickets - price if needed in seen: print(needed, price) seen.add(price)
35 15
20 30
  1. Find the loop step where price is 15.
  2. Work out needed = tickets - price with tickets as 50. Type only the number, like 12.
  3. Press Check. You get 2 tries. Why: on this step, needed is already in seen, so this is where the file finds its first pair.

Both files print the same pairs. prize_pairs_fast.py looks at each price once, so when the list doubles, its work only doubles.

7. Wrap-up

  • A hash function turns a key into a hash code, and the remainder after dividing by the number of slots picks the slot.
  • A lookup does the same math and checks one slot, so it stays fast as the table grows.
  • Collisions are normal. Chaining keeps both pairs, and a resize keeps the chains short.

New situation: the arcade adds a "Find my card" screen. A player types a card number, and the screen shows the ticket balance. The arcade has 50,000 cards. Which way of storing the balances keeps the screen fast?

In interviews: after you pick a dict or set to solve a problem, expect the follow-up "why is that lookup fast?", and the answer is the hash function and the slot.

Where this goes next: chaining keeps a few pairs together in one slot. Other structures are built entirely from items linked one after another, which gives up fast lookup by key in exchange for cheap inserts in the middle.
