Choose, Repeat, Trace

A personal budgeting app reads yesterday's transactions one at a time. For each one it asks the same question: is this amount over $75? If the amount is over $75, the app flags that transaction for review. If it is not, the app files that transaction as routine. So the app is doing two jobs at once. It picks a path for each transaction, and it asks the same question again for the next transaction, until the list runs out. Picking the path is a conditional. Controlling the repeats is a loop.

1. Concept overview

Start with that budgeting app and a single transaction of $42. The app asks one question about it: is 42 more than 75? The answer is no, so the app files the transaction as routine and never touches the flag-for-review path at all. Code shaped like that is a conditional: it checks a condition and runs exactly one matching branch.

One transaction is never the whole job. The app asks that same question about every transaction on the list, in order, until no transactions are left. That repeating is a loop. Each single pass through it, one transaction and one answer, is an iteration. The instructions that run during a pass, the ones that check the amount and print a label, are the loop body.

Why this matters: a loop that visits every item, plus a conditional that decides what to do with that item, is the shape behind almost every program that handles a list. Filtering transactions, flagging bad records, pulling out the rows a person needs to look at: all the same shape. An interviewer will hand you six lines of it and ask what it prints, usually before any harder question.

Where you're coming from, where this is headed: you already know how to compare two values and how to store a list of them. This reading adds control over what happens to each item and over how many times something repeats. Once a single loop and a single conditional feel easy to trace, the next step is putting one loop inside another, and then wrapping the whole pattern in a reusable piece of code you can point at any list.

Predicting that output by hand is the skill worth building first. Python follows the same steps in the same order every time it runs a snippet, so a careful read of the code tells you exactly what it will print before you run it.

4. if / elif / else: exactly one path runs

Python reads an if/elif/else chain from top to bottom and stops at the first branch whose condition is True. An elif is checked only when every earlier branch in its own chain was False. An else runs only when no condition in the chain was True. Exactly one branch runs per chain, so tracing a conditional comes down to finding that one branch.

The savings-tracker snippet starts with $620 set aside. Write your prediction down before you reveal or run anything.

saved = 620 if saved >= 1000: print("goal reached") elif saved >= 500: print("halfway there") else: print("just starting")

5. A for loop repeats once per item

A for loop takes a list and runs its body once per item in that list. The number of items decides the number of iterations, so you can count iterations without running anything.

categories = ["Groceries", "Rent", "Streaming"] for category in categories: print(category)

6. range(): watch the stopping boundary

range(n) produces exactly n numbers: it starts at 0 and stops one step before n. So range(3) produces 0, 1, and 2. The stop value itself stays out.

7. Off-by-one errors: wrong by exactly one

The budgeting app now reviews a whole week instead of a single day: seven days, seven checks. Here is the week-review snippet someone wrote for it.

for day in range(6): print("checking day", day + 1)

Running the week-review snippet prints this:

checking day 1 checking day 2 checking day 3 checking day 4 checking day 5 checking day 6

Six lines, not seven. range(6) produces 0 through 5, so day + 1 reaches 6 and stops. Day 7 never gets checked, and any spending on day 7 is missing from the week's review. A mistake with that shape is an off-by-one error: a loop that runs one iteration too many or one too few, because its start or stop boundary sits a single step away from what was intended.

Python raises no error here. The week-review snippet runs, prints, and finishes normally, so nothing on screen says anything is wrong. That leaves one reliable way to catch it: trace the first iteration and the last iteration by hand, then compare both against what you meant. The first should be day 1, and the last should be day 7.

for day in range(____): print("checking day", day + 1)
Need a hint?

Count the numbers you need on the screen, not the numbers range() hands out. The last line should read checking day 7, and day + 1 is what prints, so work backward to the last value day itself has to hold.

15. How this shows up in interviews

"Trace this code and tell me what prints" is one of the most common opening questions in both data and software engineering interviews. Interviewers listen for how you reason through it: reading top to bottom, naming the exact branch that runs, saying what each iteration does. The reasoning counts for as much as the final answer.

An off-by-one error is the classic follow-up. You get a snippet that runs one iteration too short or too long, and you have to say exactly which boundary is wrong, out loud, without running it.

For data roles, a loop visiting every row with a conditional deciding what to do with each row is the mental model behind almost every "clean this messy column" or "filter these records" prompt, long before you touch a library built for it.

Interview-style: a loop iterates over 6 items. Inside, a conditional only prints when an item is over 50. Exactly 2 of the 6 items are over 50. How many lines print in total?

16. Summary & critical thinking

Three habits carried this whole reading:

  1. Read an if/elif/else chain top to bottom and name the one branch that runs.
  2. Count a loop's iterations one pass at a time, rather than guessing the total.
  3. Check the first and the last iteration against what you meant, which is where an off-by-one error shows itself.

17. Thinking ahead

A loop that visits every item, with a conditional deciding what happens to each one, is a shape that gets reused immediately. Put one loop inside another and every single pass of the outer loop sets off a full run of the inner one, which is where counting iterations and watching boundaries starts to matter much more. After that comes packaging the whole pattern into one reusable piece of code you can point at any list.
