Try It, Catch It, Keep Going

A small hotel's booking script reads each night's online requests from a text file, one request per line. Most lines are clean. Then one guest types "4 nights" where the script expects a plain number. The script stops at that line, and every request after it goes unbooked. try and except let the script attempt the risky step, handle that one failure, and keep going.

1. Concept overview

Each request line looks like "Okafor|2|DLX": the guest's name, the number of nights, and a room code. The script splits the line, turns the nights into a number with int(), looks up the nightly rate for the room code, and books the stay.

Then a request arrives as "Batista|4 nights|STD". int("4 nights") can't turn that text into a whole number, so Python raises an exception: an error event that stops the program unless code catches it. The requests after Batista's are fine, but the script never reaches them.

Error handling means deciding, in code, what should happen when an operation fails. In Python you write it with try and except. The try block holds the risky step. The except block runs only if that step raises the exception named after except. When the except block finishes, Python moves on to the first line after the whole try/except.

Error handling has a partner job, validation: checking input against your rules before you use it. Keep the two jobs separate. Validation asks, "Does the input meet our rules?" Error handling asks, "What should happen if an operation fails?" Section 14 has you tell them apart.

Why this matters: real input is never all clean. Guests mistype, forms get copied wrong, and exports arrive with stray text. A script that stops at the first bad line loses every good line after it, and someone has to notice and rerun it. That is why interviewers and code reviewers so often ask, "What happens if this value isn't a number?"

Where you're coming from, where this is headed: you already know how to check a value before you use it, for example with if text.isdigit():. Error handling is a second tool for the same problem. You attempt the real operation and keep a plan ready for the specific way it can fail. Later, the same habit grows into deciding, for a whole function, which failures to catch and which ones should stay visible as bugs.

4. Check first, or try first?

Both approaches protect a program from bad input. Check first inspects the value before using it: if nights_text.isdigit():. Try first runs the real operation inside try and handles the failure in except.

A script must turn the text in nights_text into an integer. int() raises ValueError when the text isn't a whole number. Which approach handles that failure directly?

6. Trace a successful attempt

nights_text = "3" try: nights = int(nights_text) print("Nights:", nights) except ValueError: print("Could not read the number of nights.") print("Request finished.")

7. Trace a caught failure

nights_text = "4 nights" try: nights = int(nights_text) print("Nights:", nights) except ValueError: print("Could not read the number of nights.") print("Request finished.")

Which line inside try fails this time?

print("Nights:", nights) never runs here. Once int(nights_text) raises, Python leaves the try block at that line. It does not come back to finish it.

8. Count what a crash costs

This loop books every request in requests. It has no try/except.

requests = ["Okafor|2|DLX", "Hale|1|STD", "Batista|4 nights|STD", "Lindqvist|3|DLX", "Moreau|2|STD"] for request in requests: guest, nights_text, room = request.split("|") nights = int(nights_text) print("Booked", guest, "for", nights, "nights")

How many "Booked" lines print before the traceback?

When a script crashes partway through a batch, count how many records it handled before it stopped. That number tells you how much of the batch never ran. Here, two good requests were lost along with the bad one.

9. Two risky steps, two except blocks

request = "Lindqvist|3|PH" rates = {"STD": 120, "DLX": 180} try: guest, nights_text, room = request.split("|") nights = int(nights_text) total = nights * rates[room] print(guest, "owes", total) except ValueError: print("Nights is not a whole number for", guest) except KeyError: print("Unknown room code for", guest)

This try block holds two risky steps: turning nights_text into a number, and looking up room in rates. Each failure gets its own except block and its own message.

rates has no "PH" key. Which except block runs?

14. Validation or error handling?

The hotel books stays of 1 to 30 nights. Two requests break that rule in different ways:

  • "Hale|45|STD": int("45") works and gives 45.
  • "Okafor|2 or 3|DLX": int("2 or 3") raises ValueError.

Which tool catches the request for 45 nights?

The "2 or 3" request is the opposite case. No if on the number can run, because there is no number yet. except ValueError handles it.

18. How this shows up in interviews

Take-home exercises and live-coding rounds are graded on more than the sample input. A common follow-up is, "What happens if this field is missing, or this value isn't a number?" A solution that crashes on that question looks unfinished.

In code review, a bare except: is a known red flag. It catches every exception, so it also hides real bugs, such as a typo that raises NameError. Naming the exception you expect shows you thought about how your code can fail.

Interview-style question: a reviewer asks why your function uses except ValueError: instead of a bare except:. What's the strongest answer?

19. Summary & critical thinking

Two habits carried this reading. First, name the specific way an operation can fail before you attempt it. Second, trace a try/except by asking, "Did this line raise, and if so, which except matches?" An except block is never a step that always runs.

New situation: a school's enrollment script reads seats_left[course] for each sign-up. Some sign-ups name a course that isn't in seats_left. What's the right plan?

20. Thinking ahead

The same habit, naming how something can fail before it fails, keeps coming back as code grows. A script reads a file that might not exist. A function receives data from a source you don't control. Right now it's one try/except around a couple of lines. Later you'll decide up front, for a whole function, which failures to catch and which ones should surface as real bugs.
