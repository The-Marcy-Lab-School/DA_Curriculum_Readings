Try It, Catch It, Keep Going

A neighborhood food-share program logs every evening's donation drop-offs to a text file, one line per volunteer entry. Most lines are clean. Then one volunteer mistypes a number, and if the program isn't ready for that, the whole run stops right there — every donation entered after that one bad line never gets recorded. try and except are how you tell Python: attempt the risky step, and if this specific kind of failure happens, handle it and keep going.

1. Concept overview

Picture the food-share program's evening routine. A volunteer named Priya drops off 8 boxes for the produce shelf. A volunteer named Sam drops off 5 boxes for the bakery shelf. Each entry gets typed into a log file as name|shelf_code|box_count — something like "Priya|2|8". A small program reads every line, looks up which shelf shelf_code points to, converts box_count to a real number, and records the donation.

Then a volunteer named Marcus fat-fingers his entry: "Marcus|2|eight". int("eight") cannot produce a number; there is no sensible integer hiding inside that word. If the program has no plan for this, Python raises an exception, and unless something catches it, the program halts immediately. Every donation logged after Marcus's line, including Dana's and anyone who dropped off after her, never gets recorded, even though those lines were perfectly fine.

That's the whole idea. try marks the block containing the operation you're taking a chance on. except marks the block that runs only if a specific kind of failure — an exception — actually happens inside that try. Nothing else about the rest of the program changes: the lines before the risky operation already ran, and once the matching except finishes, execution moves on to whatever comes after the whole try/except structure.

Why this matters: almost no real program only ever receives clean input. A take-home exercise, a production script, an interview live-coding round — all of them eventually hand your code something malformed, and the difference between code that's "done" and code that's actually reliable is whether it can survive that moment without taking the rest of the run down with it.

Where you're coming from, where this is headed: you already know how to check a value before using it, something like if text.isdigit():, and only proceed if it looks safe. Error handling is a second tool for the same underlying problem: instead of inspecting first, you attempt the real operation directly and have a specific plan ready for exactly the ways it can fail. Once this clicks, the same reflex, naming the ways something can go wrong before it goes wrong, is what separates a first draft from code you'd actually trust.

4. Check first, or try first?

Both approaches solve the same underlying problem: something might not work, and you want to survive that. Check first inspects a value before touching it (if text.isdigit():). Try first attempts the real operation directly and has a plan ready for how it can fail.

A program needs to convert incoming text to an integer, and Python already has a specific, well-known way that conversion can fail. Which approach directly handles that real failure?

5. What Python actually does inside try/except

This part is easy to get slightly wrong the first time: an except clause is not a backup step that always runs after try. It only runs if its specific exception actually happens.

1. TRY

Python runs the risky line(s) inside try.

then
2. DID IT RAISE?

No exception: the rest of try finishes, except is skipped entirely.
Matching exception: the rest of try is abandoned mid-line, and execution jumps straight into that except.

3. CONTINUE

Whichever path was taken, once it finishes, execution continues at the first line after the entire try/except structure — not inside it.

6. Trace a successful attempt

count_text = "8" try: boxes = int(count_text) print("Boxes:", boxes) except ValueError: print("Could not read box count.") print("Log line finished.")

7. Trace a caught failure

count_text = "eight" try: boxes = int(count_text) print("Boxes:", boxes) except ValueError: print("Could not read box count.") print("Log line finished.")

Which line inside try never finishes successfully this time?

Notice print("Boxes:", boxes) never runs at all here — once int(count_text) raises, the rest of that try block is abandoned mid-step, not paused and resumed.

8. Two risky operations need two routes

entry = "Marcus|9|8" shelves = ["Produce", "Bakery", "Canned Goods", "Dairy"] try: name, shelf_code, count_text = entry.split("|") shelf = shelves[int(shelf_code)] boxes = int(count_text) print(name, "donated", boxes, "boxes to", shelf) except IndexError: print("Shelf code out of range for", name) except ValueError: print("Box count is not a number for", name)

This one try contains two different risky ideas: looking up a shelf by position, and converting text to a number. Different failures deserve different handlers, in whichever order they're written.

17. How this shows up in interviews

Take-home exercises and live-coding rounds are graded on more than "does it work on the sample input." A common follow-up is simply: "what happens if this field is missing, or this value isn't a number?" A solution that crashes on that question reads as unfinished, no matter how clean the happy-path code looks.

In production code review, a bare except: is a well-known red flag, not a shortcut — it can silently swallow a real bug (a typo, a missing import) right alongside the failure you actually meant to handle, which makes the next bug much harder to find. Naming the specific exception you expect is read as a sign you've actually thought about how your code can fail, not just how it succeeds.

Interview-style question: a reviewer asks why your function catches except ValueError: instead of a bare except:. What's the strongest answer?

18. Summary & critical thinking

Two habits carried this whole reading: naming the specific way an operation can fail before you attempt it, and tracing a try/except by asking "did this exact line raise, and if so, which except matches it" rather than assuming every except is a guaranteed fallback step.

New situation: a community clinic's intake script reads patient_records["insurance_id"] for every walk-in, but some walk-ins don't have insurance on file at all. What's the right instinct?

19. Thinking ahead

The same reflex practiced here — naming the specific way something can fail, before it fails — keeps showing up as code gets bigger: a function that returns data from an unreliable source, a script that reads a file that might not exist, an API call that might time out. Right now it's one try/except around a couple of lines; later it becomes a habit you apply while designing an entire function, deciding up front which failures are worth catching and which ones should be allowed to surface as real bugs.
