Try It, Catch It, Keep Going

A concert check-in app receives a ticket code from a scanner. Most codes convert cleanly. One malformed code should not make the entire check-in station crash. Error handling is how we tell Python: try the risky step—and if this specific failure happens, handle it.

You already know validation can inspect a value before a risky operation. Error handling gives you another pattern.

3. CONTINUE

After a matching handler runs, execution continues after the block.

Important: except ValueError is not a backup block that always runs. It runs only if a ValueError happens inside that try.

5. Trace a successful try

text = "27"

try:
    seats = int(text)
    print("Seats:", seats)
except ValueError:
    print("Could not read seat count.")

print("Check-in continues.")

What prints?

6. Trace a caught failure

text = "twenty"

try:
    seats = int(text)
    print("Seats:", seats)
except ValueError:
    print("Could not read seat count.")

print("Check-in continues.")

Which line inside the try never finishes successfully?

When the conversion raises ValueError, Python stops the rest of the try, jumps to the matching except, then continues after the whole try/except structure.

7. Error map: name the failure

ValueError

int("blue")
Right kind of operation, unusable value.

TypeError

"score" + 4
Types do not work together for that operation.

NameError

print(total_points) when that name was never defined here.

IndexError

parts[3] when the list has only two items.

9. Two errors need two routes

entry = "Ava|Balcony|oops"

try:
    parts = entry.split("|")
    section = parts[1]
    seats = int(parts[2])
    print(section, seats)
except IndexError:
    print("Missing part")
except ValueError:
    print("Bad seat count")

The same try contains two risky ideas: accessing a position and converting text to an integer. Different failures deserve different handlers.
