Two Ways to Introduce an Object

A nonprofit's donor-tracking script stores each supporter as a Donor object. 1. Concept overview

Picture a small nonprofit, Bright Path Community Fridge Network, that tracks every supporter with a Donor class: a name and a running total of what they've given. A case manager debugging the donation script drops into the Python shell and types the donor's variable name to sanity-check it. Instead of anything useful, Python hands back a memory address. Meanwhile, the same organization's website needs to list donors on a public thank-you page in a sentence a visitor would actually want to read. Same object, two completely different jobs.

Both boxes on the right come from the exact same object, with the exact same data. Nothing about the Donor changed. What changed is which method Python was asked to call to describe it.

Why this matters: almost every real Python codebase you'll touch, in a data role or a software engineering one, has classes whose default printout is useless. Fixing that with a couple of short methods is one of the fastest ways to make your own debugging sessions less painful, and "what's the difference between __str__ and __repr__?" is a genuinely common interview question, not just a classroom exercise.

Where you're coming from, where this is headed: you already know how to write __init__ to set an object's starting attributes. This reading assumes that part is solid and adds two more methods on top of the same kind of class: one Python calls automatically in some situations, and one it calls in others. Once "the method Python picks depends on context" clicks here, it's the same reasoning you'll use later for methods that control how objects compare to each other or sort against each other.

4. Which method fires? Context decides

The key question is never "which method is better." It's what is asking Python to describe the object, right now?

print(obj), str(obj), an f-string like f"{obj}"

All three ask for the human-readable view. If __str__ is defined, Python uses it. If it isn't, Python falls back to __repr__ instead.

repr(obj), and any object shown inside a list, dict, or tuple

This always calls __repr__ directly, no fallback needed. A container has to show something for each item it holds, so Python always reaches for the more detailed view.

6. Add __str__

class Donor: def __init__(self, name, total_given): self.name = name self.total_given = total_given def __str__(self): return f"{self.name} has given ${self.total_given} total" maya = Donor("Maya Chen", 500) print(maya)

What prints now?

7. Add __repr__ too

class Donor: def __init__(self, name, total_given): self.name = name self.total_given = total_given def __str__(self): return f"{self.name} has given ${self.total_given} total" def __repr__(self): return f"Donor('{self.name}', {self.total_given})" maya = Donor("Maya Chen", 500) print(repr(maya))

This code calls repr() explicitly. What prints?

9. The real gotcha: a list of objects

This is where most learners mix the two methods up. A container has to show something for every item it holds, so it always reaches for that item's __repr__, whether or not __str__ exists.

donors = [Donor("Maya Chen", 500), Donor("Andre Bell", 120)] print(donors)

16. How this shows up in interviews

"What's the difference between __str__ and __repr__?" is one of the most common Python OOP interview questions, for data roles and software engineering roles alike. A strong answer names the audience difference and the fallback behavior, not just a definition memorized from a slide.

Interviewers are also listening for a real habit: do you drop into the REPL to sanity-check an object mid-debugging session, and does typing a bare variable there actually tell you anything? A well-written __repr__ is what makes that check worth doing at all, which is why "always implement __repr__ on your classes" is such widely repeated advice among working Python developers.

The same thing shows up beyond interviews, in every log line and stack trace a larger codebase produces: the difference between a useful error message and a useless one is often just whether someone bothered to write __repr__ on the class involved.

Interview-style question: if you can only implement one of __str__ or __repr__, which should you pick, and why?

19. Thinking ahead

Giving an object more than one way to describe itself is the first example of a bigger idea: dunder methods let a class opt into behavior that would otherwise be undefined for it. The same pattern shows up again soon: __eq__ decides how == compares two objects of your own class, __lt__ and its relatives decide how sorted() orders them, and most real-world libraries you'll eventually use, like database and web frameworks, expect a working __repr__ on every model class so their own tooling and logs stay readable.
