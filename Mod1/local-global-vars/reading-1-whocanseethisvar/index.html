Who Can See This Variable?

A city parking enforcement office runs a small program that calculates the fine for every ticket. Inside one function, a variable holds the fine amount for a split second, does its job, and then is gone completely. Meanwhile, a different variable, set once outside any function, stays available to the whole program for as long as it runs. Two variables, two completely different lifespans, and mixing up which is which is one of the most common early debugging traps in Python.

1. Concept overview

The parking office's clerk writes one function to calculate every fine:

def calculate_fine(base_fine, minutes_over): fine = base_fine + (minutes_over * 2) return fine ticket_total = calculate_fine(40, 10)

While calculate_fine is running, it has its own private set of names: the parameters base_fine and minutes_over, and the variable fine created inside its body. The moment the function hits return fine and hands that value back, all three of those names disappear entirely, as if the function were a room that gets torn down the instant its work is done. Only the returned number, now stored in ticket_total, survives outside. This region where a name can be seen and used is called its scope, and a name that lives and dies inside one function call has local scope.

Not every variable works this way. daily_fine_cap is created outside every function, directly in the main body of the script. A variable defined at that level has global scope: it's created once when the program starts and stays available for the rest of the program's run, including from inside any function that wants to read it.

Why this matters: a function that quietly depends on a global variable will pass every test its original author runs, then throw a NameError the moment a teammate imports it into a different file that doesn't happen to define that same global. Reviewers and interviewers watch for exactly this pattern, because it's one of the most common ways "working" code turns out to be fragile the moment it's reused.

Where you're coming from, where this is headed: you already know how to define a function with parameters and hand a value back with return. This reading is about a question that sits underneath all of that: at any given line of code, which variable names actually exist, and which have already vanished? Once that's automatic, you're ready for ideas that lean on it constantly — functions that call other functions, and eventually classes, where every object keeps its own private copy of the same variable names.

6. A function can read a global without being told to

daily_fine_cap = 150 def calculate_fine(base_fine, minutes_over): fine = base_fine + (minutes_over * 2) return min(fine, daily_fine_cap) ticket_total = calculate_fine(90, 40)

What does calculate_fine actually need in order to run correctly here?

Key design idea: the call calculate_fine(90, 40) looks complete, but it hides a real dependency. Nothing about that call reveals that the function also needs daily_fine_cap to already exist somewhere outside it, with a reasonable value.

7. Predict: the UnboundLocalError trap

A second function tries to count tickets as it goes.

tickets_issued = 0 def issue_ticket(): tickets_issued = tickets_issued + 1 return tickets_issued

Need a hint?

The line tickets_issued = tickets_issued + 1 assigns to tickets_issued. That assignment, anywhere in the function body, is what decides its scope for the entire function, from the very first line.

14. How this shows up in interviews

A scope bug, especially a function that accidentally relies on a global variable, is one of the most common early debugging traps a code reviewer sees, and interviewers know it. A live coding round often includes a moment like: "this function works in my file, why does it break in yours?" The honest answer is almost always the same one practiced in section 6: the function secretly depended on a variable that existed only in the original script.

For software-engineering-leaning roles, expect a direct follow-up: "how would you fix this so it doesn't happen again?" The strong answer is the redesign from section 8, passing the needed value in as a parameter, not adding global to patch over the symptom.

For data roles, the same trap shows up as a transformation function that quietly reads a shared config variable or a DataFrame defined elsewhere in a notebook, instead of receiving it as an argument. That makes the function impossible to unit test in isolation, which is exactly what a reviewer is checking for when they ask you to write a small, testable function.

Interview-style question: a teammate's function passes every test in their own script, but raises a NameError the moment it's copied into a different file. What's the most likely cause?

16. Summary & critical thinking

Three ideas carried this whole reading: a local variable is created fresh with every function call and destroyed the moment that call returns, a global variable is created once and lasts for the whole program, and assigning to a name anywhere inside a function makes Python treat that name as local for the entire function body, which is exactly what causes an UnboundLocalError when the assignment comes after an attempted read.

New situation: a food pantry's program has a function boxes_for_household(household_size) that creates a local variable num_boxes inside its body and returns it. Right after the call result = boxes_for_household(4), a teammate tries to log num_boxes directly, on its own line, to send an alert. What happens?

17. Thinking ahead

The habit of asking "which names exist at this exact line, and for how long" keeps paying off well past this reading: it's exactly what's needed to reason about one function calling another, and later, about a class where every object keeps its own private copy of the same variable names, invisible to every other object of that same class.
