1. Concept overview

Start as small as possible: a single box holding one value, with a spot reserved for a connection to whatever comes after it, currently empty. That single box is a node. A node holds a value, plus a reference to whatever node should come next. Nothing follows it yet, so that reference is empty, written in Python as None.

Now add a second node. Python does not automatically know "this one comes second" the way it does with list indexes. Someone has to say so explicitly: the first node's "what comes next" reference gets pointed at the second node. That single connection is the entire relationship between them. Neither node's location in memory changed. They could be anywhere at all. What makes them a chain is only that one reference.

Keep going: add a third node the same way, point the second node at it, and there is a genuine chain: three separate nodes, each one aware only of the single node immediately after it, connected purely by references rather than by sitting next to each other.

That is the core difference from a Python list. A list is one contiguous block: Python can compute exactly where element 7 lives with simple arithmetic on the starting address, no matter how big the list is. A linked list has no such shortcut. Each node can live anywhere, and the only way to reach the fifth node is to start at the first one and follow "next" four times. That is called traversal, and it is the price a linked list pays for something a list cannot offer as cheaply: changing what sits in the middle without moving anything else around it (more on that soon).

Here is that exact three-node chain in Python, built with a small class that holds a value and a "next" reference:

class Node: def __init__(self, value): self.value = value self.next = None head = Node("Song A") second = Node("Song B") head.next = second third = Node("Song C") second.next = third # head -> "Song A" -> "Song B" -> "Song C" -> None

Compare that to the one-line list version, queue = ["Song A", "Song B", "Song C"]. The list version is shorter to write and lets you jump straight to queue[2]. The linked version took more setup and can only be reached by starting at head. Cheap random access versus cheap insertion and removal is the entire trade-off, and it is why both structures exist side by side rather than one replacing the other.

Why this matters: linked lists rarely show up as the actual container you reach for day to day in a typical data workflow, but the thinking behind them, knowing exactly what a variable points to and what happens when that reference gets reassigned, shows up constantly in interviews and underneath tools used every day: version control history, database indexes, and how a program's memory actually gets managed all lean on this same node-and-reference idea. "Reverse a linked list," specifically, is one of the single most commonly asked warm-up problems in software engineering interviews, at companies of every size.

Where you're coming from, where this is headed: you already know how to store a sequence of values in a Python list and loop over it from front to back. A linked list keeps that same "sequence of values, one after another" idea, but swaps contiguous memory and index math for something more explicit: nodes that only know about their own immediate neighbor. Once following one "next" reference at a time feels natural, the same idea scales up directly: give a node a second reference, one forward and one backward, and it becomes a doubly linked list.

5. Where linked lists show up in real software

Two real products lean on exactly this node-and-pointer shape.

An Up Next queue, the one from the top of this reading, does not need random access nearly as often as it needs to insert a song wherever a listener taps "play next," or drop whichever song just finished playing. Both of those touch only the node right next to the change.

A browser's back and forward history gives every visited page its own node, connected to the page before it and the page after it, with the browser also tracking a "current page" pointer somewhere inside that chain. Clicking back moves the current pointer one node earlier without deleting anything. Clicking forward moves it one node later. Visit a brand-new page while sitting a few pages back in history, though, and everything that used to be "forward" from there gets cut loose, because it no longer reflects what actually happened. Hold onto that detail. It resurfaces at the very end of this reading.

7. The classic interview problem: reverse a linked list

Here is the problem, stated the way an interviewer would say it: given the head of a singly linked list, reverse it in place so the last node becomes the first, without building a brand-new list. This is one of the most frequently asked warm-up problems in technical interviews, and it rewards exactly the pointer-tracking habit this reading has been building.

The standard approach walks the chain once, using three separate pointers: prev (the reversed portion built so far), curr (the node currently being flipped), and a temporary next_node that saves where the chain used to continue before that connection gets overwritten. That temporary pointer is the entire trick. Look at the exact instant it matters:

Here is the full function, with one line hidden. That hidden line is the actual reversal: the moment curr's pointer gets redirected backward instead of forward.

def reverse_linked_list(head): prev = None curr = head while curr: next_node = curr.next ____________________ prev = curr curr = next_node return prev # prev is the new head

10. How this shows up in interviews

Linked lists are an interview staple for a specific reason: they are simple enough to explain in thirty seconds, but tracing pointer changes accurately under a bit of pressure genuinely separates candidates. "Reverse a linked list," the exact problem practiced above, shows up constantly, sometimes asked directly, sometimes as a warm-up before a harder follow-up.

The other question that comes up just as often is cycle detection: given a linked list, determine whether it loops back on itself somewhere instead of ending at None. The classic answer is Floyd's tortoise-and-hare technique: move one pointer one node at a time and a second pointer two nodes at a time. If the list has a cycle, the faster pointer eventually laps the slower one and they land on the same node. If it does not, the faster pointer simply reaches None first.

Interviewers are listening for the reasoning as much as the final answer. Being able to say out loud "I need to save the next reference before I overwrite it, or I lose the rest of the list" is a stronger signal than getting the code right by memorization alone.

12. Summary & critical thinking

Two ideas carried this whole reading: a node is only a value plus a reference to what comes next, and following that chain of references, one at a time, is the only way in, whether you are building it, searching it, or reversing it.

New situation: a text editor's undo history keeps a chain of past document states with a "current state" pointer sitting somewhere in the middle, since a user might undo a few steps and still be able to redo forward again. If the user makes a brand-new edit while sitting a few undos back in that history, what should happen to the states that were "ahead" of the current pointer, the ones redo would have reached?

13. Thinking ahead

Everything here used a singly linked list: one value, one forward pointer. Give a node a second reference, one pointing backward as well as forward, and it becomes a doubly linked list, which is exactly what lets a browser move backward through history as cheaply as forward, without re-walking the whole chain from the start every time. Push the idea further, and a node that holds several "next" references instead of exactly one is how a hierarchy, like folders nested inside folders, gets represented at all. And the very act of walking a chain by repeatedly asking "what does this node point to next" is a small preview of a much bigger idea: a function that solves a problem by calling a smaller version of itself on whatever is left of the chain.
