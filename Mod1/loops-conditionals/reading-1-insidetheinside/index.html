1. Concept overview

Picture the game from the intro: 3 worlds, 4 checkpoints in each. To reach every checkpoint, you don't write one loop — you play checkpoints 1, 2, 3, 4 of World 1, then checkpoints 1, 2, 3, 4 of World 2, and so on. That's nesting: one repeating structure (checkpoints) living entirely inside another repeating structure (worlds), where the inner one runs to completion once for every single pass of the outer one.

Now add the key. At each checkpoint, the game asks "is the player carrying a key?" — and only if the answer is yes does it ask a second question, "is it the right color?" That second question is a nested conditional: a decision living inside another decision, reachable only when the outer decision came out true.

Nesting loops and nesting conditionals are the whole reading. Two rules do almost all of the work: an inner loop always finishes every one of its passes before the outer loop advances, and an inner conditional is only ever reached if execution actually enters the outer branch that contains it.

Why this matters: almost any real dataset has structure inside structure — rows that each have several fields, categories that each have their own items. Tracing a nested loop or a nested conditional accurately is exactly what "process every row, then check several things about that row" requires, and it's a near-guaranteed interview trace question.

Where you're coming from, where this is headed: you already know how to trace a single loop and a single conditional on their own. This reading is entirely about combining two of them. Once this clicks, you're ready for the same shape at a larger scale — looping over nested data structures, and eventually functions that call themselves.

15. How this shows up in interviews

"What does this nested loop print?" is one of the most common warm-up questions in technical screens, for data roles and software engineering roles alike. Interviewers are listening for how you trace it, not just the final number — narrating "the inner loop finishes before the outer one advances" out loud is exactly what they want to hear.

Nested conditionals show up as "spot the bug" questions: you're handed a snippet where an inner message never fires, and asked to find why, live. Tracing from the outside in — the same habit practiced in section 13 — is the expected method, not guessing.

This is also the first building block of a later concept: nested loops over the same-size input are the classic reason a piece of code is "order n-squared" — an interviewer will often follow up a nested-loop trace question by asking exactly that.

Interview-style question: three outer passes, three inner passes each, one print per inner pass. How many total lines print?

17. Summary & critical thinking

Two reasoning habits carried this whole reading: counting a nested loop by following complete inner runs, and tracing a nested conditional from the outside in to find which branch is actually reachable.
