When the Crowd Grows

An airline's check-in kiosk does one job all day: find this traveler's booking. When the airline held 200 bookings, checking them one by one took no time at all. Now it holds 200,000. The way the kiosk searches decides whether the answer still comes back right away, or takes longer with every booking added. Big-O is the language for describing that difference.

1. Concept overview

A small regional airline starts with one daily flight and about 200 bookings. When a traveler types in a confirmation code, the kiosk checks the first booking, then the second, then the third, until one matches. That method is a linear scan. With 200 bookings, even checking every one is quick.

Over a few years the airline adds routes, and the kiosk now searches 200,000 bookings. The kiosk's code has not changed. It still checks one booking at a time. But its worst case went from 200 checks to 200,000. The work grows with the number of bookings, and that number is the input size.

A second method avoids that growth. The kiosk stores each booking under its confirmation code, so typing the code jumps straight to the right booking. That is a direct lookup. It takes about the same small amount of work with 200 bookings or 200,000. A Python dictionary finds values this way, by a key. You don't need to have used one yet. The idea is what matters here.

Both methods are algorithms: step-by-step methods for solving a problem. Big-O notation describes how an algorithm's work grows as its input grows. The linear scan is O(n), read "O of n": its work grows with n, the number of items. The direct lookup is O(1): its work stays about the same. The chart plots both as the airline grows from 200 to 200,000 bookings.

At 200 bookings, both lines start at the same point. That is why a small test can fool you: both methods feel instant. The difference only shows as the input grows. How an algorithm behaves as its input grows is called its scale, and code that stays fast as data grows "scales well."

Why this matters: "Explain Big-O" is a common early interview question. On the job, it is how you defend a choice, such as storing records by ID when a program has to find them thousands of times a day.

Where you're coming from, where this is headed: you already write loops and functions that check items one at a time. This reading gives you words for what that habit costs as data grows. The same question comes back every time you choose how to store data: does finding one item stay flat, or grow with the data?

14. How this shows up in interviews

"Explain Big-O" is a common early interview question for data and software roles. A typical opener is "What's the time complexity of this lookup, and why?" Interviewers want the reasoning: what n is, what the worst case is, and whether the work grows or stays flat. A memorized label is not enough.

A common follow-up: "You need to check whether an item is in a collection thousands of times. Would you use a list or a dictionary?" A strong answer says a dictionary keeps each check close to O(1), while a list makes each one O(n), and that difference adds up when the check repeats thousands of times.

Interview-style question: you need to check membership in a growing collection thousands of times inside a loop. What's the strongest choice?

16. Summary & critical thinking

Two habits carried this reading. First, name what n is before judging an algorithm's cost. Then ask whether that cost grows with n or stays flat. A fast run on a small input doesn't answer that question.

New situation: a stadium's entry scanners check each ticket code against the night's valid tickets. Ticket sales keep growing, from 5,000 seats to 60,000.

17. Thinking ahead

This question comes back every time you choose how to store data: does finding one item stay flat, or grow with the data, and how often will it run? It also comes back when one loop sits inside another. That pattern grows in its own way, and it gets its own Big-O name.
