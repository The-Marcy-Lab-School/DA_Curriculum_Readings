Lookups Matter

A payments company blocks every transaction from an account already flagged for fraud. Each transaction runs one check against the list of flagged accounts. In testing there were 20 flagged accounts, and the check felt instant. In production there are 400,000, and the same check makes payments time out. Nobody changed the logic. What changed is how many accounts the check has to look through, and how those accounts are stored.

1. Concept overview

The fraud team stores each flagged account as a record: the account number and the reason it was flagged. The team tried two ways to answer the question "is this account flagged?"

Way 1: linear search

flagged = [ {"account": "6614", "reason": "chargeback"}, {"account": "2203", "reason": "stolen card"}, {"account": "4471", "reason": "chargeback"}, ] def find_flag_linear(flagged, account): for record in flagged: if record["account"] == account: return record return None print(find_flag_linear(flagged, "4471")) print(find_flag_linear(flagged, "9004"))

Output

{'account': '4471', 'reason': 'chargeback'} None

find_flag_linear is a linear search. It checks the records one at a time, in order, until one matches. To find "4471", it checked all three records, because "4471" is last. To learn that "9004" is not flagged, it also checked all three. Nothing let it stop early. A missing value is the worst case for a linear search: the most work the search can do.

The number of records is the input size, written n. With 3 records, the worst case is 3 checks. With 400,000 records, it is 400,000 checks for every transaction. When the work grows in step with n, the cost is O(n).

Way 2: dictionary lookup

flags_by_account = {record["account"]: record for record in flagged} print(flags_by_account.get("4471")) print(flags_by_account.get("9004"))

Output

{'account': '4471', 'reason': 'chargeback'} None

flags_by_account is a dict keyed by account number. .get("4471") jumps straight to that key instead of walking through the records. .get() returns None when the key is missing, so both ways give the same answers. This is a dictionary lookup. It takes about one step whether the dict holds 3 accounts or 400,000. That cost is O(1) average-case.

The dict has a cost too. Building flags_by_account loops over every record once, which is O(n). The team pays that cost once, when the service starts. After that, every transaction gets the fast lookup.

Why this matters: a search that slows down as data grows is a common real performance bug. It passes small tests and fails under real traffic. Interviewers also ask about it directly: "Why did you use a dict here instead of a list?"

Where you're coming from, where this is headed: you already know how to loop over a list and read a dict by key. This reading adds one question to ask about any search: how does its cost grow as the data grows? That question is about complexity, and it comes up any time two working solutions get compared.

4. The mystery slowdown

The fraud check passed every test with 20 flagged accounts. With 400,000, the same line, if account_number in flagged_accounts:, starts timing out. Nobody changed the logic. What is the most likely cause?

Big-O is not a stopwatch. O(1) does not mean instant, and O(n) does not mean slow. On a list of 20 accounts, both searches finish so fast you may not measure a difference. Big-O tells you how the cost changes as the data grows.

12. How this shows up in interviews

"Why did you use a dict here instead of a list?" is a common question in interviews and code reviews when a search runs inside a loop. Interviewers want the reason: a linear search is O(n), a dictionary lookup is O(1) on average, and the gap grows with the data.

For data roles, the question often comes up as deduplication: "How would you check whether you have already seen this ID in a dataset that keeps growing?" Name a dict or set, and say why.

For software roles, expect a follow-up: "When would you keep the linear search?" A strong answer names both sides. A linear search needs nothing extra to build, but every search slows as the list grows. A dict costs one pass to build, and then each lookup is fast.

Interview-style question: why did switching from find_flag_linear to flags_by_account.get() fix the fraud check's slowdown? Pick the strongest answer.

14. Summary & critical thinking

A linear search checks items one at a time, so its worst case grows with input size: O(n). A dictionary lookup jumps to a key, so its cost stays about flat: O(1) average-case. Both return the same answers. The difference shows up at scale, which is why you ask how a search grows before you trust it on real data.

New situation: an online store checks whether a coupon code was already used. The check runs thousands of times a day, and the list of used codes keeps growing. Which design keeps the check fast?

15. Thinking ahead

The question "how does this cost grow?" applies to more than searches. Any time you compare two working solutions, such as two ways to remove duplicates or to match records from two tables, complexity tells you which one will hold up as the data grows.
