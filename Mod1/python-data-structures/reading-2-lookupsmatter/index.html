Lookups Matter

When someone calls a help line, the screen shows the caller's name. The program finds it by looking up the phone number in a list of saved callers. With 20 saved callers, the name appeared at once. With 400,000, people wait several seconds before anyone knows who is calling. The fix is to store the callers a different way.

2. Search a list, one record at a time

The help line saves each caller as a record: a phone number and a name. Here is a short version of the list, with a function that searches it.

Predict: what does find_caller_linear.py print?

callers = [
    {"phone": "555-0142", "name": "Ana Ruiz"},
    {"phone": "555-0178", "name": "Sam Lee"},
    {"phone": "555-0113", "name": "Kim Park"},
]

def find_caller(callers, phone):
    for record in callers:
        if record["phone"] == phone:
            return record["name"]
    return None

print(find_caller(callers, "555-0113"))
print(find_caller(callers, "555-0199"))
Kim Park
None

find_caller is a linear search: it checks records one at a time, in order, until one matches. To find "555-0113", it checked all three records, because that number is last. To learn that "555-0199" is not saved, it also checked all three. That is the worst case: the number is last, or not there at all.

The number of records is the input size, written n. In the worst case, a linear search checks all n records, so its work grows in step with n. Big-O writes that as O(n). A description like this, of how the work grows as the input grows, is the code's complexity. It answers a question about scale: what happens to the cost when the data gets much bigger? With 400,000 saved callers, one ring can mean 400,000 checks.

3. Build a dict once, with a loop

A dict stores each value under a key. If the key is the phone number, the program can jump straight to the caller's name. build_caller_dict.py builds that dict from the same list.

New in this file: callers_by_phone[record["phone"]] = record["name"] is the d[key] = value you already know. It adds one phone number as a key, with that caller's name as its value. The loop runs this line once for each record.

Predict: what is the last line of output from build_caller_dict.py?

callers = [
    {"phone": "555-0142", "name": "Ana Ruiz"},
    {"phone": "555-0178", "name": "Sam Lee"},
    {"phone": "555-0113", "name": "Kim Park"},
]

callers_by_phone = {}
for record in callers:
    callers_by_phone[record["phone"]] = record["name"]

print(callers_by_phone)
print(callers_by_phone["555-0113"])
{'555-0142': 'Ana Ruiz', '555-0178': 'Sam Lee', '555-0113': 'Kim Park'}
Kim Park

Building the dict has a cost. The loop visits every record once, which is O(n). The help line pays that cost one time, when the program starts. After that, every call gets the fast lookup.

When a linear search is still fine: if you search only once, or the list is tiny, building the dict costs about as much as the search it replaces. A dict pays off when you search many times, or when the list keeps growing.

4. Look up a key: square brackets or .get()

A dictionary lookup finds a value by its key. It takes about one step whether the dict holds 3 callers or 400,000. Big-O writes that as O(1) average-case. O(1) means the work stays about the same as n grows. "Average-case" means a rare lookup can take a little longer.

Square brackets, as in callers_by_phone[phone], are one way to look up a key. They work when the key is in the dict. A help line also gets calls from new numbers.

callers_by_phone = {"555-0142": "Ana Ruiz", "555-0178": "Sam Lee", "555-0113": "Kim Park"}

print(callers_by_phone["555-0199"])
Ana Ruiz
Traceback (most recent call last):
  File "lookup_brackets.py", line 4, in <module>
    print(callers_by_phone["555-0199"])
          ~~~~~~~~~~~~~~~~^^^^^^^^^^^^
KeyError: '555-0199'

A new caller is normal, so the program should not crash. The .get() method looks up a key the same way, but it returns None when the key is missing.

callers_by_phone = {"555-0142": "Ana Ruiz", "555-0178": "Sam Lee", "555-0113": "Kim Park"}

for phone in ["555-0178", "555-0199"]:

6. Wrap-up

  • A linear search checks records one at a time. Its worst case grows with the input size: O(n).
  • Build a dict once with a loop. That costs O(n), one time. Each dictionary lookup after that is O(1) on average.
  • Square brackets raise a KeyError for a missing key. .get() returns None, so your code can handle it.

New situation: the help line adds a feature. When a call comes in, the screen should say "Called before today" if this number already called today. The program keeps every number that called today, and that collection grows all day. Which design keeps the check fast?

In interviews, "Why did you use a dict here instead of a list?" is a common question. A good answer names both costs: the one-time O(n) build and the O(1) lookups after it.

The same question, "how does the cost grow?", helps you compare any two working solutions, such as two ways to remove repeated rows from a dataset.
