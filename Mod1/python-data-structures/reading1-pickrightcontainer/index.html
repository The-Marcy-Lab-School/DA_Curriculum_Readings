Pick the Right Container

A food delivery app juggles four kinds of data every night. A courier's list of stops changes as new orders come in. A finished delivery's record should never change. Each order code has to point to the courier carrying it. And the app has to know which orders were already refunded, so no order gets refunded twice. Python gives you four containers for jobs like these, and each one follows different rules.

1. Concept overview

Start with a courier's route for the evening. The stops come in order. A new stop gets added at the end, and a stop can move up the route when its food is getting cold. The route has to keep its order and change freely. In Python, that is a list: an ordered, changeable collection written with square brackets, [ ].

Next, a delivered order. Once order D-5520 is dropped off at 7:42 PM, that record is final. If code changed it by accident, the app's delivery history would no longer match what happened. That is a tuple: an ordered collection that cannot change after it's created, written with parentheses, ( ).

Then the lookup. A customer asks where order D-5521 is. The app should not check every active order to find out. It should go straight from the order code to the courier's name. That is a dictionary, or dict: a collection of pairs, written with curly braces, { }. Each pair has a key, the label you look up by, and a value, the data stored under that key. Here the key is the order code and the value is the courier's name. Each key appears only once.

Last, refunds. The app only needs to know whether an order has already been refunded. Adding the same order code a second time should change nothing. That is a set: a collection of unique values with no fixed order, also written with curly braces.

All four are data structures: containers that hold many values under one name, each with its own rules about order, duplicates, and change. A container you can change after you create it is mutable. One you can't change is immutable. Lists, dictionaries, and sets are mutable. Tuples are immutable.

Why this matters: "Which data structure would you use here?" is a common early interview question for data roles. Outside interviews, the wrong choice causes real bugs. If refunded orders are tracked in a list, nothing stops the same order from going in twice, so a refund report can count one order two times. A list also gets slower to search as it grows.

Where you're coming from, where this is headed: you already store single values in variables and repeat steps with loops. This reading is about storing many values at once and picking the container whose rules fit the job. The choice also affects speed: some containers find an item in one step no matter how much they hold, and others slow down as they grow.

6. A curly-brace surprise

True or false: writing refunded = {} creates an empty set.

Empty curly braces make an empty dictionary. Python had dictionaries before it had sets, so {} was already taken. An empty set needs a built-in function instead.

mystery = {} print(type(mystery))

7. Hashable or not?

Which value can be a dictionary key?

Python stores each dictionary key and set value by its hash, a fixed fingerprint. That only works if the value can never change. Strings, numbers, and tuples of hashable values are immutable, so they are hashable. Lists, dicts, and sets are mutable, so they can't be dictionary keys or set values.

Tricky case: pair = (1, [2, 3]). The tuple itself can't be reassigned.

9. Order the steps: how a set catches a duplicate

Click the steps in the order Python follows when you add a value to a set. Click a step again to remove it, then press "Check my order." This is a self-check, not graded. These steps also explain why a set doesn't keep the order you added things in.

  • Python computes a hash of the new value.
  • Python uses that hash to find where an equal value would already be stored.
  • If a matching value is already there, the add does nothing: no duplicate is created.
  • If nothing matches, Python stores the new value at that hash-based spot.

13. How this shows up in interviews

"Which data structure would you use for this, and why?" is a common warm-up in data-role interviews. Interviewers listen for the reason. Name the rule that matters: order, change, lookup by key, or uniqueness.

For data roles, a common trap is tracking "values already seen" in a list while cleaning a dataset. It works on small data. But the list gets slower to search as it grows, and duplicates slip in if one comparison is written wrong. Naming a set as the fix, without being asked, is a strong signal.

For software roles, expect follow-ups like "Why can't a list be a dictionary key?" A strong answer uses hashability and immutability, not "because Python says so."

Interview-style question: the app checks whether a promo code was already used. The check runs thousands of times a night, and the collection of used codes keeps growing.

15. Summary & critical thinking

Four questions carried this reading. Does order matter? Does the data need to change after it's created? Do you look items up by a label instead of a position? Must every item be unique? Answer them, and the right container usually follows.

16. Thinking ahead

The same four questions matter as data gets more complex. Most real records are stored as a list of dicts, one dict per row. A dict of lists groups related items under one key. And speed becomes part of the choice: some containers find an item in one step no matter how much they hold, while others slow down as they grow.
