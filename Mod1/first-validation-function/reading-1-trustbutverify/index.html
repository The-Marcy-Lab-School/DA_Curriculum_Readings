What Goes In, What Comes Out

Every evening, a community food bank's loading dock logs each donation drop-off as a single line of text: who dropped it off, and how many pounds came in. Most nights the log is clean. Some nights a volunteer forgets to write down a weight, or a driver scribbles "heavy" instead of a number. Before any of that data gets summarized into a weekly report, something has to look at every line and decide, one at a time, whether it's usable or whether a human needs to look at it. That single job, and only that job, belongs to one function — and this reading is about designing that function well, not just making it run.

1. Concept overview

Picture that loading dock's log file. Every line should look like "DROPOFF|D118|42": an action, a donor ID, and a weight in pounds, separated by |. Before anyone tallies tonight's total weight or emails a thank-you receipt, one function needs to walk through every line and answer a narrow question: is this line usable, and if not, exactly why? Nothing else. Not printing a summary, not tallying pounds, not deciding what to do about a bad line — just checking, and reporting back.

Two design decisions have to be made before a single line of the loop gets written: what does this function need to receive (its input), and what will it hand back to whoever calls it (its output)? Those two answers, together, are the function's contract — a promise the rest of the program can rely on without needing to know how the checking actually happens inside.

INThe list of raw log lines, exactly as they came off the dock.
ONE JOBDecide whether each line is usable, and why not if it isn't.
OUTA list of problem descriptions — empty if every line was fine.

Why this matters: "write a function that checks a batch of records" is one of the most common warm-up and take-home tasks in a data or software interview, and a shaky answer almost always comes from skipping this contract step, not from getting the loop wrong. A function that quietly mixes in printing, tallying, or deciding what happens next is much harder to test, reuse, or hand off to a teammate than one with exactly one clearly stated job.

Where you're coming from, where this is headed: you already know how to define a function with parameters and a return value, and you already know how to loop through a collection and branch on a condition inside it. This reading is entirely about combining those two skills inside one well-designed function. Once deciding a function's contract before writing its body feels automatic, the same habit keeps paying off: it's exactly how you'd design a second function that does something different with this one's output, or decide when a value needs to be handled the moment it fails rather than checked for in advance.

7. Structure check, then value check

With the contract decided, here's the batch this reading uses. A valid line always has exactly 3 fields: action, donor ID, weight.

donations = [ "DROPOFF|D118|42", "DROPOFF|D204", "DROPOFF|D205|heavy", "DROPOFF|D207|9" ]

Which line fails the structure check — not the value check?

A structure check has to run first: if a line doesn't have 3 fields at all, checking fields[2] for its value could fail before the value check ever gets a chance to run.

Writing both checks well needs two small tools. str.isdigit() checks whether a string is made entirely of digits:

"42".isdigit() [Output] True "heavy".isdigit() [Output] False

And enumerate() hands a loop two things per pass instead of one: a position counter, and the item itself.

for line_number, line in enumerate(donations, start=1): print(line_number, line)

def find_donation_problems(records): problem = None for line_number, line in enumerate(records, start=1): fields = line.split("|") if len(fields) != 3: problem = f"Line {line_number}: expected 3 fields, got {len(fields)}" elif not fields[2].isdigit(): problem = f"Line {line_number}: weight '{fields[2]}' is not a number" return problem

12. How this shows up in interviews

"Write a function that validates a batch of records" is one of the most common warm-up or take-home tasks in a data or software technical screen. Interviewers are rarely grading whether the loop compiles on the first try — they're watching whether you state the contract out loud before writing any code ("this takes a list of strings, and returns a list of problem descriptions") and whether validation logic stays separate from anything that prints, tallies, or decides what happens next.

A very common follow-up: "how would you test this without running the whole file?" The expected answer is the exact isolation habit practiced in section 10 — call the function directly with a small, made-up batch and check what it returns.

13. Summary & critical thinking

One habit carried this whole reading: decide a function's contract, its one job, its input, and its exact return value, before writing the loop and conditionals that make that contract true. A structure check runs before a value check, and a returned list of specific problems is what makes a function testable on its own, in isolation from the rest of the program.

New situation: a community theater's box office logs each ticket sale as a line: "SALE|show_id|seat_count". You're asked to write a function that checks a batch of these lines the same way. Before writing any code, what's the first design decision to make?

14. Thinking ahead

The same contract-first habit scales in two directions from here. Sometimes the next step is a second function with a completely different job that consumes this one's returned list — summarizing, reporting, or alerting on data this function already approved, while staying just as narrowly scoped itself. Other times a value fails in a way a plain if check can't safely catch in advance at all, like a conversion that raises an error the instant Python attempts it, which calls for handling the failure directly at the moment it happens rather than checking for it beforehand.
