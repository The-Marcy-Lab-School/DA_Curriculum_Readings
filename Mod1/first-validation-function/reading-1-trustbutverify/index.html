What Goes In, What Comes Out

A high school's front office types each course enrollment form into a text file, one form per line. Most lines are fine. Some are missing a field. Some have "10th" where the grade level should be a plain number. Before anyone builds class lists from the file, one function checks every line and reports which lines can't be used, and why. That function has one job, and this page walks through designing it.

1. Concept overview

Each line in the office's file should look like "S-2041|10|Biology": a student ID, a grade level, and a course, separated by |. A file like this, with one record per line, is a batch file. A program checks it one line at a time.

Validation means checking data against rules before you use it. It answers one question: does this input meet our rules? The office has three rules for each line:

  1. The line has exactly 3 fields.
  2. The grade level is a whole number.
  3. The grade level is between 9 and 12.

A line that passes every rule is valid input. A line that breaks any rule is invalid input. Some invalid lines are also malformed input: they don't have the right shape at all. "S-2042|Chemistry" has 2 fields instead of 3, so the program can't even find the grade level to check it.

Before writing the loop, decide two things: what the function receives (its input) and what it hands back (its output). Together they are the function's contract. The rest of the program relies on the contract without needing to know how the checks work inside.

INThe list of form lines, exactly as the office typed them.
ONE JOBDecide whether each line is valid, and say why if it isn't.
OUTA list of problem messages, empty if every line is valid.

Why this matters: "write a function that checks a batch of records" is a common warm-up and take-home task in data and software interviews. Weak answers usually skip the contract, not the loop. A function that also prints, counts, or decides what happens next is harder to test, reuse, or hand to a teammate than a function with one stated job.

Where you're coming from, where this is headed: you already know how to write a function with parameters and a return value, and how to loop over a list with an if inside. Here you combine them in one function. The same contract-first habit applies when a second function uses this one's output. It also applies when a value can only be checked by attempting an operation and handling the failure.

7. Structure check, then value checks

Here is the batch the rest of this reading uses. A valid line has exactly 3 fields: student ID, grade level, course.

forms = [ "S-2041|10|Biology", "S-2042|Chemistry", "S-2043|10th|Algebra", "S-2044|14|Art", "S-2045|9|History" ]

Which line fails the structure check?

The structure check runs first. On "S-2042|Chemistry", a value check on fields[1] would treat "Chemistry" as the grade level and report the wrong problem. Reading fields[2] would raise an IndexError and stop the program.

"S-2044|14|Art" has 3 fields, and "14".isdigit() is True. Is this line valid input?

Two small tools make these checks easy to write. str.isdigit() checks whether a string is made only of digits:

"10".isdigit() [Output] True "10th".isdigit() [Output] False

enumerate() gives a loop two things on each pass: a position counter and the item itself.

for line_number, form in enumerate(forms, start=1): print(line_number, form)

10. Debug: why is the report empty?

A teammate wrote this version of find_enrollment_problems:

def find_enrollment_problems(forms): problems = [] for line_number, form in enumerate(forms, start=1): fields = form.split("|") if len(fields) != 3: problems.append(f"Line {line_number}: expected 3 fields, got {len(fields)}") elif not fields[1].isdigit(): problems.append(f"Line {line_number}: grade '{fields[1]}' is not a number") elif int(fields[1]) < 9 or int(fields[1]) > 12: problems.append(f"Line {line_number}: grade {fields[1]} is outside 9-12") return problems

Called on the five-line forms batch from section 7, what does the teammate's version return?

This bug raises no error. On the real file it reports no problems, so everyone trusts a bad file. If you call the function by itself on a tiny made-up batch, the bug shows up right away.

12. How this shows up in interviews

In a technical screen, interviewers rarely grade whether your loop runs on the first try. They watch whether you state the contract out loud before coding ("this takes a list of strings and returns a list of problem messages"). They also watch whether the checking stays separate from printing, counting, and deciding what happens next.

A common follow-up is, "How would you test this without running the whole file?" The expected answer is the habit from section 10: call the function by itself on a small made-up batch and check what it returns.

13. Summary & critical thinking

One habit carried this reading: decide a function's contract (its one job, its input, and its exact return value) before writing the loop and conditionals. Inside the function, the structure check runs before the value checks. Returning a list of specific problems is what lets you test the function by itself.

New situation: a bank exports card payments, one per line: "card_last4|amount_cents|merchant_type". You're asked to write a function that checks a batch of these lines. What's the first design decision?

14. Thinking ahead

The contract-first habit grows in two directions. Sometimes a second function takes this one's returned list and does a different job with it, such as summarizing or reporting, while staying just as narrow. Other times a value can't be checked safely in advance. A conversion might raise an error the moment Python attempts it. Then you handle the failure when it happens, instead of checking for it beforehand.
