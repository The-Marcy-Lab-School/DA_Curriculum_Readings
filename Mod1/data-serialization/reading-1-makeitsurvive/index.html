Make It Survive

A school's rooftop weather station measures rain and wind every hour. A short Python script keeps each hour's numbers in a dictionary. The script works all day. Then the laptop restarts overnight, and in the morning every reading is gone. The sensor measured the rain, but the numbers only lived inside the running script. To keep data after a program closes, the program has to write that data to a file, in a format it can read back later.

1. Concept overview

While the weather script runs, the hourly numbers sit in a dictionary in memory: rain = {6: (0.4, 12), 7: (1.2, 18)}. Each key is an hour of the day. Each value is a tuple: millimeters of rain, then wind speed in km/h. The dictionary is real and usable while the script runs. When the script stops, on purpose or because the laptop shuts down, every variable it was holding disappears.

To survive, the dictionary has to be written to a file as text, and rebuilt from that text later. Turning a Python value into text you can save is serialization. Its everyday name is saving. Rebuilding a Python value from that saved text is deserialization, or loading. The rules for how the text is laid out in the file are its format. This reading uses three formats: JSON, CSV, and TXT.

The file never holds the dictionary itself. It holds a text version of the data, and loading builds a brand-new dictionary from that text. The diagram follows rain through one save and one load in JSON. Two things come back different.

JSON keys are always strings, so every integer key comes back as a string. JSON has no tuple type, so every tuple comes back as a list.

The script builds rain, but the laptop restarts before anything is written to a file. What does the script have the next morning?

Why this matters: a value that comes back with a different type does not crash anything. A script that looks up hour 7 as an integer finds nothing once every key has become a string. The script gives wrong answers, and no error warns anyone. Catching that means checking what a loaded value really is, not what it looks like.

Where you're coming from, where this is headed: you already know how to build dicts, lists, and tuples while a program runs. This reading covers what happens when that data leaves memory and comes back. The same question, "what type does this loaded value have?", comes up whenever a program reads data that another program saved, and whenever a program checks each line of a file before using it.

4. Three shapes, three formats

All three formats store plain text. They differ in the shape of data each one fits. Here is one hour's reading saved as three files:

{"hour": 7, "rain_mm": 1.2}
hour,rain_mm 7,1.2
7:00 rain 1.2 mm

JSON labels every value. CSV writes the labels once, in the header row. TXT uses whatever layout you choose.

JSON

Shape: nested keys, values, and arrays.

Fits: one record with structure inside it, like a sensor with a list of today's alerts.

CSV

Shape: flat rows and columns, every row the same.

Fits: a table someone will open in a spreadsheet.

TXT

Shape: any line-by-line layout you choose.

Fits: a simple log that only your own script writes and reads.

5. Writing a file: the mode matters

open() takes a mode that says what you plan to do with the file:

  • "w" (write) empties the file first, then writes. If the file doesn't exist, Python creates it.
  • "a" (append) keeps what is already there and adds to the end.
  • With no mode, open() reads the file ("r").

The weather script should add one line to rain_log.txt every hour. Here is the first version someone wrote. The real script runs once an hour. In this file, each pass of the loop stands in for one of those hourly runs, and the last two lines print what the file holds afterward.

hour_lines = ["6:00 rain 0.4 mm\n", "7:00 rain 1.2 mm\n", "8:00 rain 0.9 mm\n"] # Each pass of the loop stands in for one hourly run. for hour_line in hour_lines: with open("rain_log.txt", "w") as f: f.write(hour_line) with open("rain_log.txt") as f: print(f.read())

6. Reading it back


f.read() returns the whole file as one string. Every value read from a text file starts as a string, even one that looks like a number. Your code decides when that text becomes a number.


This file writes 1.5 and nothing else to rain_total.txt, then reads it back.


with open("rain_total.txt", "w") as f:
    f.write("1.5")

with open("rain_total.txt") as f:
    total = f.read()

print(total * 2)

Try it: save in one run, load in the next


Real programs split the round trip across two runs. save_rain.py writes the hourly dictionary to rain.json. load_rain.py runs later and rebuilds it.


import json

rain = {6: (0.4, 12), 7: (1.2, 18)}

with open("rain.json", "w") as f:
    json.dump(rain, f)

print("Saved", len(rain), "hours to rain.json")


import json

with open("rain.json") as f:
    rain = json.load(f)

print("Loaded:", rain)
print("Hour 7:", rain["7"])

15. Summary & critical thinking


Two habits carry this whole reading. First, a file holds a text version of your data, never the live object. Second, check what type each loaded value has instead of assuming it matches what you saved.

16. Thinking ahead


Any time data passes through a file, it comes back as text first, and your code rebuilds it. That holds for a database row, a response from a website, and a file another team's script wrote. The question is always the same: what type does this value have right now? Answering it line by line, before the data gets used, is the job of a validation function.
