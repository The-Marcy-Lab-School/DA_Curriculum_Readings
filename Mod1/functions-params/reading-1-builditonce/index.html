Build It Once, Use It Again

A small electric co-op sends every household a bill each month. Every bill uses the same math: the electricity a household used, times the price of electricity. You could retype that math for each household. Or you could write it once, give it a name, and reuse it for every bill. That named, reusable piece of code is a function.

1. Concept overview

Electricity is measured in kilowatt-hours (kWh). This month, one household used 300 kWh, another used 520, and a third used 160. The co-op charges everyone $0.25 per kWh. Without a function, the billing script repeats the same two lines for each household. Only the number changes.

The box on the right is a function: a named, reusable block of code. You define it once. Then you call it as many times as you need, with different values each time. Here is energy_cost in Python, called twice:

def energy_cost(kwh_used, price_per_kwh): return kwh_used * price_per_kwh print(energy_cost(300, 0.25)) print(energy_cost(520, 0.25))
75.0
130.0

The values passed in at a call, like 300 and 0.25, are arguments. The names in the def line that receive them, kwh_used and price_per_kwh, are parameters. The return line hands the answer back to the line that called the function. That line can then store the answer, add it to a total, or print it. The answer is the return value.

Why this matters: a formula copied into four places is a common source of bugs. The price changes, someone updates three of the copies, and the fourth keeps charging the old price. With a function, the formula lives in one place, so there is one place to fix it. Code reviewers and interviewers check for this early.

Where you're coming from, where this is headed: you already know how to store values in variables, write loops and conditionals, and print results. Here you name a set of steps once and reuse it with different inputs. The next idea builds on this one: which variables a function can see while it runs, and which ones the rest of the program can't see.

15. How this shows up in interviews

When an interviewer or code reviewer sees the same few lines repeated, they often ask, "Can you turn this into a function?" A function with real parameters, instead of a hardcoded value in a copied block, shows good habits even in a simple exercise.

For software engineering roles, expect a follow-up like "What does this function return if that condition is never met?" Reviewers look for a function with no return. That is the bug from section 10: something prints, so the call looks like it worked, but the caller gets None.

For data roles, the same idea shows up as "Write a function that takes a column name and a threshold and returns the matching rows." The interviewer wants a solution that works for any column, not only the one in the example.

Interview-style question: a reviewer asks, "What happens if I call your function twice with two different inputs?" Which answer shows you designed it correctly?

16. Debugging habit + reflection

total_kwh should add up three monthly meter readings.

def total_kwh(readings): total = 0 for reading in readings: total = total + reading return total print(total_kwh([310, 285, 340]))
310

The three readings add up to 935, but the function returns 310 with no error. What is wrong?

17. Summary & critical thinking

This reading covered three ideas. You define a function once and call it as many times as you need. Parameters let each call pass in different arguments without changing the function's code. return hands a value back to the caller, while print only shows it on screen.
