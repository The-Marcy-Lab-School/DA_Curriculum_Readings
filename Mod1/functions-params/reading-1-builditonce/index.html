Build It Once, Use It Again

A community health clinic bills dozens of patients a day. Every visit needs a co-pay calculated from the patient's insurance plan and visit type. Someone could type that math fresh into every patient's chart, or copy-paste the same few lines over and over. Or someone could write the calculation once, give it a name, and reuse it for every single patient. That reusable, callable piece of code is a function, and this reading is about how to build one from scratch.

1. Concept overview

Picture the clinic's front desk. A patient with a basic plan and an office-visit fee owes one amount. A patient with a specialist plan and a longer visit owes a different amount. Both amounts come from the exact same math: take a base fee, multiply it by a rate that depends on the plan, and that's the co-pay. Without a function, a receptionist's script might repeat those same three lines near-verbatim for every patient it bills that day, only the numbers plugged in changing each time.

That single box on the right is the whole idea of a function: a named, reusable block of code that gets defined once and then called as many times as needed, each time with different input values. Those input values are called arguments, and inside the function's own definition, the names that receive them are called parameters. Instead of a fee getting hardcoded into three separate blocks, one parameter named base_fee stands in for whatever fee gets passed in on a given call. And instead of the function just displaying its answer on screen, it can return that answer, handing the actual value back to whatever line called it, so that value can be saved, billed, or added into a running total.

Why this matters: "can this be a function?" is one of the very first things a code reviewer or an interviewer notices in a piece of code. A duplicated formula that lives in four separate places is a real, common source of bugs: the billing rule changes, someone updates three of the four copies, and the fourth quietly keeps charging the old rate. A function fixes that by construction. There's exactly one place the rate lives, so there's exactly one place to fix it.

Where you're coming from, where this is headed: you already know how to write a sequence of steps that runs top to bottom, store values in variables, and print results. This reading is about naming a sequence of steps once and reusing that name with different inputs, instead of writing (or copying) the steps again every time. Once defining and calling a function feels automatic, the next idea builds directly on it: figuring out exactly which variables a function can see while it runs, and which ones stay invisible to everything outside it.

def make_id_tag(patient_name): return "PATIENT: " + patient_name label = make_id_tag("Rosa Delgado")

Which statement is correct?

A parameter is written in the def line itself. An argument is the actual value handed over at one specific call.

15. How this shows up in interviews

"Can you turn this into a function?" is one of the very first things an interviewer or a code reviewer says when they see the same few lines repeated. Writing a clean function with real parameters, instead of hardcoding one value and duplicating the block, is often the single clearest signal of a candidate's habits in an otherwise simple exercise.

For software-engineering-leaning roles specifically, expect a live follow-up like "what does this function return if that condition is never met?" Reviewers are trained to look for a function that quietly falls through without an explicit return, since that's exactly the bug practiced in section 10: the call looks like it worked because something printed, but the caller receives None.

For data roles, the same idea shows up as "write a function that takes a column name and a threshold and returns the filtered rows," rather than one script hardcoded to a single column. The interviewer is checking whether the solution generalizes past the one example in front of them.

Interview-style question: a reviewer reads your function and asks, "what happens if I call this twice with two different inputs?" What answer shows you designed it correctly?

17. Summary & critical thinking

Three ideas carried this whole reading: a function is defined once but called as many times as needed, parameters let each call plug in different arguments without touching the function's own code, and return hands a real value back to the caller while print only displays something on screen.

New situation: a small bakery needs to calculate an order total from an item's price and quantity, for dozens of different orders throughout the day, and then add each total into a running daily sales figure. Which design fits?

18. Thinking ahead

Defining and calling a function is the foundation for everything functions do later: deciding exactly which variables a function can see while it runs and which ones stay invisible outside it, catching a function that silently returns the wrong thing when a real bug slips into a bigger program, and combining several small functions so each one has exactly one job. All of that starts from the same two moves practiced here: define it once, and call it with whatever input a given situation actually needs.
