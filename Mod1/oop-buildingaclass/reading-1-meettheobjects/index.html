Meet the Objects

A personal budgeting app lets one user track several savings goals at once: an emergency fund, a vacation fund, a fund for a new laptop. Every goal needs the same three pieces of information — a name, a target amount, and how much has been saved so far — but each goal's numbers have to stay completely separate from every other goal's numbers, for every user. Three plain variables can hold one goal's data. The moment a second goal shows up, that approach falls apart. This reading is about the tool Python gives you instead: defining a class once, then creating as many independently-stored objects from it as you need.

1. Concept overview

Picture that budgeting app. A user sets up a goal called "Emergency Fund," with a target of $5,000 and $4,200 saved so far. Tracking that with three plain variables — name, target_amount, saved_amount — works fine, right up until the same user adds a second goal, "Vacation Fund," with its own target and its own saved amount. Now you either overwrite the first goal's variables or start inventing name_2, target_2, saved_2, hoping you never mix up which number belongs to which goal. Multiply that by every user and every goal they create, and plain variables stop being a plan at all.

A class solves this by defining the shape of a "savings goal" exactly once: it always has a name, a target amount, and a saved amount, and it can always report whether it's fully funded. Python then lets you create as many independently-stored objects from that one definition as you need. Each object keeps its own values for those three pieces of data, completely separate from every other object built from the same class.

Nothing about the class definition changes between goal_a and goal_b. What changes is that each object stores its own separate copy of name, target_amount, and saved_amount. Update one object's saved amount, and the other object never notices.

Why this matters: "design a class for X" is one of the most common early interview and take-home prompts in both data and software engineering roles, and modeling a real-world thing as a class is a skill you'll use in nearly every project going forward. It also fixes a real, common bug: tracking several similar real-world items with a pile of separate variables (or separate lists that have to be kept in sync by hand) is exactly how one item's data quietly ends up overwriting another's.

Where you're coming from, where this is headed: you already know how to write a function that takes parameters, and how a dict groups related values together under labeled keys. A class combines both ideas: a special method called __init__ runs once per object and stores its parameters as labeled attributes, the same way a dict stores values under keys, except now that data travels together with the actions (methods) that make sense for it. Once defining a class and creating a few independent objects from it feels automatic, two ideas build directly on top of it: giving an object a cleaner way to describe itself when it gets printed, and comparing two different ways of finding one specific object out of many, by how their cost grows as the amount of data grows.

4. Read the shape of a class

class SavingsGoal: def __init__(self, name, target_amount, saved_amount): self.name = name self.target_amount = target_amount self.saved_amount = saved_amount def is_funded(self): return self.saved_amount >= self.target_amount goal_a = SavingsGoal("Emergency Fund", 5000, 4200)

Trace the creation call: "Emergency Fund" flows into the parameter name, then self.name = name stores it as an attribute on this new object. The same thing happens to 5000 and 4200, landing on target_amount and saved_amount.

What is the value of goal_a.name?

14. How this shows up in interviews

"Design a class for X" is one of the most common early interview and take-home prompts in both data and software engineering roles: model a parking ticket, a hotel reservation, a shipment, whatever fits the role, as a class from scratch. Interviewers are listening for your reasoning on which attributes belong on every object versus which values should be computed by a method instead, and whether you can prove, not just claim, that two objects don't interfere with each other.

This also shows up constantly outside interviews: any time a codebase represents a real-world thing (a user, an order, a device) with a class, someone had to make the exact same attribute/method decisions this reading practiced.

Interview-style question: you're asked to design a class representing a single parking ticket. Which response makes the strongest case that you understand independent objects?

16. Summary and critical thinking

Two ideas carried this whole reading: a class defines a shape once, and __init__ turns the values passed into a new object into that object's own stored attributes, kept completely separate from every other object's attributes.
