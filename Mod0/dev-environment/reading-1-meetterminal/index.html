1. Concept overview

A terminal is a window where you type instructions to your computer instead of clicking icons. Every single thing you'd normally do with a mouse, open a folder, look inside a file, check whether a program is installed, has a typed equivalent. Type an instruction, called a command, press enter, and the computer prints back whatever the command produced. That printed result is the output. There's no dragging, no double-clicking, no visual folder tree staring back at you, just text going in and text coming back out.

The working directory is whichever folder the terminal currently considers "here." Every command that doesn't spell out a full location acts on the working directory by default, which is why the very first habit worth building is checking where "here" actually is before doing anything else. A location can be written two ways: a relative path describes where to go starting from the working directory (donations means "the donations folder, right where I already am"), while an absolute path spells out the entire route from the very top of the filesystem (/home/robin/foodbank-intake/donations), and works no matter where you currently are.

Why this matters: almost every real data or software job hands you a project folder on day one and expects you to find your way around it without anyone walking you through a mouse tour. Commands are also exact and repeatable in a way clicking isn't: the same typed command does the identical thing every time, which is exactly what lets you automate a task later instead of clicking through it by hand forever.

Where you're coming from, where this is headed: you already know how to find a file by clicking through folders, that's the same idea, just a different interface. Once typing a location instead of clicking it feels normal, you're ready for the next layer built entirely on top of it: version control tools track changes to files inside a project folder, and data tools open, read, and combine files that you first have to be able to find.

3. Three commands, three questions

Almost all terminal navigation comes down to answering three questions, over and over, in whatever order the moment calls for.

pwd

"Where am I?" Prints the working directory. Changes nothing.

ls

"What's here?" Lists what's inside the working directory. Changes nothing.

cd NAME

"Take me there." Moves the working directory into NAME. Prints nothing on its own.

6. Checking your tools

A command doesn't have to move you anywhere or list a folder to be useful. git --version and code --version ask a completely different question: "is this tool actually installed and reachable from here?" A real version number answers that question with confidence; an error answers it too, just not the one you wanted.

12. How this shows up in interviews

Technical interviews and take-home exercises routinely assume you can open a shared repository and move around it from the terminal, without asking anyone to screen-share their file explorer for you. It's often the very first thing an interviewer or a new manager notices: whether your first move after opening an unfamiliar project is to run ls, or whether you sit there waiting for someone to click through it for you.

Onboarding at almost any data or software role starts the same way: clone a project, open a terminal, and run a handful of commands before you ever touch an actual editor. Being visibly comfortable at that stage, including staying calm and reading an error message instead of freezing, is a small thing that reads as real hands-on experience rather than only ever having used a graphical interface.

Interview-style question: you're asked to open a shared project and locate one specific file, without touching the mouse. What's the fastest way to build real confidence you're in the right place before you open anything?
