What Shape Is This Data?

You're the new data analyst for a city's public works department. Every morning, the same three kinds of files land in your inbox describing yesterday's resident service requests: a spreadsheet, a folder of typed-up field notes, and a JSON export from the city's reporting app. None of them look the same, and none of them can be opened with the same approach. Before you touch any of them, you have to answer one question first: what shape is this data actually in?

1. Concept overview

Picture the three files from the intro. The first, requests.csv, lists one row per service request with the exact same five columns every time: request_id, category, ward, days_open, status. That consistency is what makes something structured data: a fixed set of fields, repeated exactly the same way, record after record.

The second file, field_notes.txt, is nothing like that. It's just paragraphs a repair crew typed up after each visit, in whatever length and order they wrote them. There's no request_id column to sort by and no fixed number of sentences per entry. That's unstructured data: real information, but with no predefined fields to slot it into automatically.

The third file, app_reports.json, sits in between. Every entry has an id and a category, like a structured record would. But the extra details vary: one report includes a tags list and a photo_count, another has neither. There's real organization here, keys and nested details, just not the same rigid columns for every row. That in-between shape is semi-structured data.

Why this matters: a file's shape is the very first decision point in almost any real data task, before you write a query, before you clean a column, before you pick a chart. A structured table calls for a spreadsheet or a SQL query. Free text calls for search or language tools. A semi-structured export usually needs something in between, like a script that expects some keys to be missing. Guess the shape wrong, and you've reached for the wrong tool before you've even started.

Where you're coming from, where this is headed: you already know how to run pwd, ls, and cd to find your way around a filesystem. This reading adds a few new commands for actually looking inside a file, plus a repeatable way to decide its shape from real evidence instead of a guess. That same habit, gathering evidence before classifying, comes back every time you clean, combine, or query a dataset you didn't build yourself.

6. New commands for inspecting a file

You already know pwd, ls, and cd for finding your way around a filesystem. Classifying a file's shape takes three more commands, for actually looking inside it.

cat

Meaning: print a file's entire contents.

Why use it? Read a short file quickly, before deciding anything about its shape.

cat field_notes.txt

grep

Meaning: search a file's text for lines matching a word or pattern.

Why use it? Find one specific thing inside free-flowing text, without reading the whole file.

grep noise field_notes.txt

wc

Meaning: count things in a file. wc -l counts lines; wc -w counts words.

Why use it? A structured file's natural unit is usually rows (lines). An unstructured file's natural unit is usually words.

wc -l requests.csv

13. How this shows up in interviews

Data-role interviews ask about this distinction directly, sometimes as a plain definitional question, sometimes as "here's a sample file, what would you do with it?" It's often the very first filter for which tool an interviewer expects you to reach for: a SQL query, a text-search or NLP approach, or something that expects a flexible set of keys.

A common follow-up is being handed a real (but unfamiliar) file and asked to justify a classification out loud, using specific evidence from the file rather than a guess based on its name or extension. That's the exact habit practiced in sections 7 through 9.

14. Summary & critical thinking

Two habits carried this whole reading: telling structured, semi-structured, and unstructured data apart by their actual field consistency, and gathering real evidence (list, preview, search) before ever committing to a classification.

New situation: a nonprofit exports two files: a spreadsheet with one row per volunteer, using the same volunteer_id, hours, and date columns for every row, and a second file containing free-form thank-you notes volunteers typed into a text box. How would you classify each one?

15. Thinking ahead

This same judgment call resurfaces constantly: cleaning or combining datasets starts with knowing whether you're working with fixed columns or free text, SQL tables assume a structured schema going in, document-style databases are built specifically to hold semi-structured records, and natural-language tools exist specifically to turn unstructured text into something closer to structured signal.
