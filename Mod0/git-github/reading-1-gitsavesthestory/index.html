Git Saves the Story

A community environmental group is writing up a neighborhood tree survey together. Three different volunteers touch the same notes file over three weeks: one fixes a miscount, one adds a new column, one rewords a confusing sentence. Nobody wants to be the person who overwrites somebody else's fix by accident, and everybody wants to know what changed and why. That's the actual problem Git solves, and it's what this reading is about: what a repository, a commit, and a remote actually are, underneath the commands.

1. Concept overview

Picture the tree-survey write-up. Without any tool watching it, three volunteers editing the same file over three weeks tends to end in files named notes_final.md, notes_final_v2.md, and notes_ACTUALLY_final.md — and nobody can say for sure which one has the corrected tree count and which one still has the mistake. Git exists to make that mess unnecessary. Instead of piling up renamed copies, you keep one project and save a sequence of meaningful checkpoints of its history, each one able to say exactly what changed.

Each circle is a commit: a saved snapshot of the project at one moment, with a message describing what changed. Read left to right, the four commits are the story of this file. The first three have already been sent to GitHub, so anyone with access to that remote copy can see them. The fourth one, marked HEAD because it's the most recent snapshot, only exists on the volunteer's own computer so far. It's a real, saved commit, but GitHub doesn't know about it yet.

Why this matters: that gap between the fourth commit and the GitHub box is one of the most common early mistakes in a real project. Someone commits their work, assumes it's automatically backed up and visible to their team, and finds out days later that it never left their own laptop. Understanding that a commit and a push are two separate actions, done at different times, is the single idea that prevents that mistake. It's also one of the first things a manager or teammate checks when they look at a shared project: does the commit history actually explain what happened, or is it one vague dump at the end?

Where you're coming from, where this is headed: you already know something like this from ordinary software. A word processor's version history and an "undo" button both save you from losing earlier work. Git formalizes that same idea, on purpose, for an entire folder of files, and adds one extra piece: a remote copy that other people can see and add to. Once this mental model is solid, every specific command you type later is really just "operate on one of these three things: my files, my saved history, or the remote copy."

4. Git and GitHub are related, but not the same

Git

A program that runs on your own computer. It tracks the history of files inside a repository. Nothing about it requires the internet.

GitHub

A website that can host a copy of a Git repository, so a project can be shared, backed up, and worked on by more than one person.

Editing a file does not automatically make that change part of your next commit. Placing a change into the staging area is a separate, deliberate step.

8. Commit messages are for future humans

A commit message should tell a future reader, including a future version of the person who wrote it, what changed and roughly why, without forcing them to open every file to find out.

14. How this shows up in interviews




"Walk me through what happens when you run git add, commit, and push" is a genuinely common early-interview and take-home-review question, for data roles and software roles alike. Interviewers use it to check that a candidate understands the local-versus-remote split, not just that they can recite the three command names in order.


A second common angle is reading someone else's commit history and being asked "what would you have done differently here?" A history of five commits all named update or fix is an honest red flag, and being able to say why, specifically, is exactly the judgment this reading has been building.


One thing this reading has not covered yet, in the interest of staying honest: merge conflicts, which come up once two people's changes to the same file collide. That's a real, common follow-up question once someone confirms they understand commits and remotes, but it depends on ideas, like branches, that this reading deliberately left out to stay focused.




Interview-style question: an interviewer shows you a project with one giant commit message that says "final version" and asks what's wrong with it. What's the best answer?

16. Summary & critical thinking


Two ideas carried this whole reading: a commit is a saved snapshot with a message, not a live view of your files, and a repository's local history and its remote copy are two separate things that only stay in sync when you actually push.


New situation: a small nonprofit's volunteer coordinator keeps a shared spreadsheet of upcoming events, emailed back and forth as attachments, and two people just edited it at the same time without knowing. What would change if that spreadsheet lived in a Git repository instead?














17. Thinking ahead


The mental model from this reading, a local repository, a saved sequence of commits, and a remote copy, is the exact foundation that branches, pull requests, and merge conflicts all get built on top of later. Every one of those ideas is really just a more advanced way of asking the same question this reading kept coming back to: what does the current commit history actually say happened, and where does the remote copy stand relative to it?
