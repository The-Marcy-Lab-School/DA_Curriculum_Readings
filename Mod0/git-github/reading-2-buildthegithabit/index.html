Build the Git Habit

You keep a math study guide in a git repository. In one afternoon you fix a wrong test date, add a section on fractions, and fix a typo in the README. Saving all three as one commit called "updates" feels quick, but it makes the history hard to use later. You already know how to commit. This reading is about how often.

1. One big commit or three small ones

2. Recall before you start

Staging and committing, and the difference between a commit and a push, are prerequisite skills for this reading. Check both before moving on.

A classmate says, "I edited the file, so git commit will save it, right?" What's missing?

You made a commit but haven't pushed. Where is that commit right now?

3. Small commits make a useful history

An atomic commit holds exactly one focused change, like "fix the test date." It doesn't mix in a new section or an unrelated typo. Commit granularity means how much one commit covers, from one small edit to a whole day of mixed work. Smaller is usually easier to read later.

git log is the list of every commit already saved in the repository. Adding --oneline shows each commit on one short line: its ID, then its message.

Predict: you made the three small commits from the picture, after a first commit called "Start the study guide." In what order does git log --oneline list them?

git log --oneline
$ git log --oneline
2be44a6 Fix a typo in the README
d48a131 Add a section on fractions
b6c0073 Fix the test date
2121428 Start the study guide

In what order does git log list the commits?

Now picture the other way. The same afternoon saved as one commit shows only this:

$ git log --oneline
51fe55a updates
e01019b Start the study guide

A week later, someone says the fractions section has a mistake. With the one-commit history, what's the problem?

4. Check what changed before you commit

git diff shows the exact lines you changed that aren't committed yet. A line starting with - was removed. A line starting with + was added. Lines with no sign are there to show where you are in the file.

Predict: you changed the test date in study_guide.md from October 12 to October 14, and you haven't staged it. What does git diff show?

git diff
$ git diff
diff --git a/study_guide.md b/study_guide.md
index b68f607..020e2d3 100644
--- a/study_guide.md
+++ b/study_guide.md
@@ -1,6 +1,6 @@
 # Math Study Guide

-Test date: October 12
+Test date: October 14

 ## Decimals
 Line up the decimal points before you add.

What does git diff show?

The top lines name the file and give git's own labels for the two versions. You can skip them for now.

After you stage and commit that fix, git status has a short way of saying everything is saved. Predict: what does it print?

git add study_guide.md git commit -m "Fix the test date" git status
$ git add study_guide.md
$ git commit -m "Fix the test date"
[main b6c0073] Fix the test date
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git status
On branch main
nothing to commit, working tree clean

What does git status print after the commit?

Working tree clean means every change in your folder is already committed. Nothing is waiting to be staged.

5. Commit as you go, with a clear message

Commit cadence means how often you save a commit while you work. A good habit is one commit each time you finish one change you could describe in a short sentence. If something breaks later, you have a recent checkpoint and a clear record of each step.

Your turn: write a commit message

You just added the new fractions section to study_guide.md.

  1. Type a message for that one change. Start with an action word, like Add or Fix.
  2. Use at least 3 words, and name what changed, like the section's topic. Leave out the quotes and the git commit -m part.
  3. Press Check. You get 2 tries. Many different messages can be right.

Why: a reader six weeks from now should know what changed without opening the file.

6. Try it yourself: a simulated terminal

This pretend terminal is open in /Users/sam. The study-guide repository already has one commit and is connected to GitHub. Two files have changes waiting: study_guide.md (the new test date) and README.md (a typo fix). You'll save them as two separate commits. Press Enter after each command.

  1. Type cd study-guide. Nothing prints.
  2. Type git status. You should see both files listed as "modified."
  3. Type git add study_guide.md. Nothing prints. Only this one file is staged.
  4. Type git commit -m "Fix the test date". You should see "1 file changed."
  5. Type git add README.md. Nothing prints.
  6. Type git commit -m "Fix a typo in the README". You should see a second commit.
  7. Type git log --oneline. You should see three commits, newest first.
  8. Type git push. You should see both new commits go up to GitHub.
You're in /Users/sam. Start with step 1.
Something didn't work?

"not a git repository" means you're not inside study-guide yet, so run step 1. You can also run git diff or cat README.md at any point to look at the changes.

8. Wrap-up

  • An atomic commit holds one focused change. Small commits let you find exactly when something changed.
  • git diff shows the lines you changed. git status says "working tree clean" when everything is committed.
  • Commit each time you finish one change you can describe, with a message that names it.

New situation: a classmate who shares the study guide plans to edit it all week and make one commit on Friday, "so the history looks clean." What's the problem with that plan?

Interviewers sometimes open a candidate's GitHub and read the commit list, and small, clearly named commits show how you work.

Next, this habit pays off once you're looking back through a project with weeks of history, trying to find when one thing changed.

Step 1: Make a repo on your GitHub account (one time only — collapse this afterward)
  1. On GitHub, click the + in the top-right corner, then New repository.
  2. Give it a name (something like data-analytics-readings) and click Create repository.
  3. On the new repo's page, click the green Code button and copy the HTTPS URL.
  4. In your terminal, clone it to your computer, pasting in the URL you just copied: 
    git clone https://github.com/YOUR-USERNAME/YOUR-REPO.git

You only do this once. For every reading after this one, start at Step 2.

Step 2: Save this reading's file into that repo (do this for every reading):

  1. Move into your repo folder: 
    cd YOUR-REPO
  2. Move the file you just downloaded out of Downloads and into that folder: 
    mv ~/Downloads/build-the-git-habit-reading.json .
  3. Save it to git and push it up to GitHub: 
    git add build-the-git-habit-reading.json
