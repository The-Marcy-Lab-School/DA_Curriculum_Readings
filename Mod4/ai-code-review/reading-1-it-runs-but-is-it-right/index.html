1. Introduction

Northway Telehealth is a telehealth company, which means its doctors see patients over video calls instead of in an office. Every visit creates a record in the company's database, an organized store of data that programs can ask questions of.

Rosa is an analyst there. She needs a small Python function that pulls one patient's appointment history out of that database, so she can check a report against the raw records. She is in a hurry. So she asks a free AI coding assistant to write it for her.

Ten seconds later, she has a function. She runs it with a real patient id number. Four rows come back. The dates look right. The visit types look right. Nothing turns red.

So it's finished, right?

Why this matters: "Do you have a checklist for reviewing AI-written code?" is now a real question asked in real junior data and engineering interviews. Employers ask it because everyone's AI tool produces code that runs. The thing they cannot tell from a resume is whether you read what it handed you. On the job, the same gap shows up in a quieter way: the code you accept from an AI tool ships under your name, and nobody in the room later asks whether a person or a tool typed it.

Where you're coming from, where this is headed: you already know how to read a Python function, and you know the shape of talking to a database from Python: open a connection, run a query, get rows back. This reading is about the step after that. You read a function someone else wrote, decide what is actually wrong with it, and write the specific fix. That habit carries into every code review you ever sit in, whether the author was a tool or a teammate.

One plain word about the data here. Patient appointment records are names, dates, and visit types belonging to real people's health histories. They are protected for good reason. A lookup function that can be talked into returning the whole table is a real problem on the day it ships, not a tidy-up task for later. This is a good place to practice careful review precisely because the stakes are easy to see.

3. The draft that runs

Here is exactly what Rosa typed into the AI assistant, and exactly what came back.

Rosa asked

"Write a Python function that takes a patient id and returns that patient's appointment history from our PostgreSQL database."

Two names in that request, defined: PostgreSQL is a widely used database system. SQL stands for Structured Query Language, the language you write in to ask a database for data. A single request written in SQL is called a query.

The AI replied

"Here's a clean function for that. It opens a connection, runs the lookup, and closes the connection when it's done."

 1  def get_appointment_history(patient_id):
 2      """Return every appointment for one patient.
 3      Raises an error if no patient with that id exists.
 4      """
 5      conn = psycopg2.connect(os.environ["DATABASE_URL"])
 6      cur = conn.cursor()
 7      query = (f"SELECT visit_date, visit_type FROM appointments "
 8               f"WHERE patient_id = '{patient_id}'")
 9      cur.execute(query)
10      rows = cur.fetchall()
11      conn.close()
12      return rows

A quick tour of what each part is, so nothing here is a mystery word:

  • Lines 2 to 4 are a docstring: a note inside the function describing what it does. Other people read it to learn how the function behaves.
  • Line 5 opens the connection, an open line of communication between the Python program and the database. psycopg2 is the Python library that lets Python talk to a PostgreSQL database. os.environ["DATABASE_URL"] reads the database address out of an environment variable, a setting stored on the computer rather than typed into the file. That keeps passwords out of the code, and it is the right thing to do.
  • Line 6 creates a cursor, the object you actually hand a query to.
  • Lines 7 and 8 build the query text. The f in front of each piece makes it an f-string, so whatever patient_id holds gets pasted right into the text.
  • Line 9 sends the query to the database. Line 10 collects every row it found. Line 11 closes the connection. Line 12 hands the rows back.

Rosa calls it with a real id and gets four rows of real appointments. Every claim the AI made about it sounds true. It does open a connection. It does run the lookup. And it does call conn.close(), right there on line 11.

True or False: a function that runs without any error and returns believable-looking rows has been verified as correct.

6. Problem one, up close: the query is built from raw input

Look at lines 7 and 8 again on their own.

query = (f"SELECT visit_date, visit_type FROM appointments "
         f"WHERE patient_id = '{patient_id}'")

Whatever patient_id holds gets pasted into the query text before the database ever sees it. The database does not receive a query plus a value. It receives one finished string and reads the whole thing as instructions.

With a normal id like 4102, the finished query is exactly what you would expect:

SELECT visit_date, visit_type FROM appointments
WHERE patient_id = '4102'

Now suppose patient_id does not arrive as a plain number. Suppose it arrives as this piece of text, typed into a search box on an internal tool:

4102' OR '1'='1

Paste that in the same way and the finished query becomes:

SELECT visit_date, visit_type FROM appointments
WHERE patient_id = '4102' OR '1'='1'

What does the database do with that second query?

Need a hint?

Read the condition after WHERE as two tests joined by OR. Ask yourself whether the second test, '1'='1', is ever false for any row.

That is SQL injection: text someone typed gets read as SQL commands instead of as data, and it changes what the query does. No error appears. The function returns a list of rows, exactly like it always does. It is just the wrong list.

The fix is a parameterized query. You leave a placeholder in the query text and hand the real value to psycopg2 separately, as a second argument to execute(). The driver then treats that value as data only. It can never become part of the SQL.

query = ("SELECT visit_date, visit_type FROM appointments "
         "WHERE patient_id = %s")
cur.execute(query, (patient_id,))

The (patient_id,) is a tuple holding one value. The trailing comma is what makes it a tuple rather than just a value in parentheses. And notice the placeholder has no quote marks around it. psycopg2 adds whatever quoting the value needs.

Run that same suspicious text through the parameterized version and nothing exciting happens. The database compares the literal text 4102' OR '1'='1 against real patient ids, finds no match, and returns zero rows. The query's job did not change. Whether raw input could rewrite it did.

7. Problem two, up close: the connection that stays open

Line 11 does call conn.close(), so the AI's claim that it "closes the connection when it's done" is technically true. It is only true on the happy path.

Trace what happens if line 9 raises an error. Maybe the database is briefly unreachable. Maybe a column name is wrong. Python stops running the function at that point and sends the error up to whoever called it. Lines 10, 11, and 12 never get a turn. The connection opened on line 5 is still open, and now nothing in the program has a reference to it.

One leaked connection is not a crisis. A function like this called inside a loop over a few hundred patients, on a day the database is having trouble, is exactly how a server runs out of connection slots and starts refusing everyone's work.

The shape that fixes it is try and finally. Python guarantees that a finally block runs, whether the code above it finished normally or blew up partway through.

conn = psycopg2.connect(os.environ["DATABASE_URL"])
try:
    cur = conn.cursor()
    cur.execute(query, (patient_id,))
    return cur.fetchall()
finally:
    conn.close()

Even the return does not skip it. Python runs the finally block on the way out.

8. Problem three, up close: a promise the code never keeps

Read line 3 of the draft one more time, slowly.

Raises an error if no patient with that id exists.

Now search the body of the function for the line that would do that. There isn't one. If no appointment matches the id, cur.fetchall() returns an empty list, and the function hands back that empty list without complaint.

This is a hallucination: the AI stated something that sounds confident and correct but is simply made up. It is not a wild invention like a fake library name. It is a small, plausible, completely wrong sentence sitting in the one place people go to find out how a function behaves.

Here is the cost, in Rosa's actual week. She looks up a patient, mistypes one digit of the id, and gets an empty list back. The docstring told her an unknown id raises an error. No error appeared. So she reasonably concludes this patient has no appointments on file, and writes that into a report. The real patient has eleven.

What is the honest fix for line 3?

Rosa's team picked the first option and wrote the plain truth: "Returns an empty list if this patient has no appointments on file." Now anyone who gets an empty list knows exactly what it means, and knows to double-check the id they typed.

9. The fixed function

Same function. Same inputs. Same rows on a normal call. Three specific things changed.

 1  def get_appointment_history(patient_id):
 2      """Return every appointment for one patient.
 3      Returns an empty list if this patient has no
 4      appointments on file.
 5      """
 6      conn = psycopg2.connect(os.environ["DATABASE_URL"])
 7      query = ("SELECT visit_date, visit_type FROM appointments "
 8               "WHERE patient_id = %s")
 9      try:
10          cur = conn.cursor()
11          cur.execute(query, (patient_id,))
12          return cur.fetchall()
13      finally:
14          conn.close()
  1. Lines 3 and 4: the description now matches what the code really does.
  2. Lines 7, 8 and 11: the value travels separately from the query text, so typed input can never become SQL.
  3. Lines 9, 13 and 14: the connection closes on every path out of the function, including the one where the query fails.

Notice what did not change. The variable names are fine. The function name is fine. Nothing here was about style. All three fixes were about what the code actually does while it is running.

10. Your AI code-review checklist

Everything above came from five questions asked in a deliberate order. Click the five checks below in the order you would actually run them, then check your order.

  • Does it run at all?
  • Does it do the right thing? Check one record by hand against the source.
  • Is the input handled safely, or pasted into something?
  • Does it clean up after itself, on the error path too?
  • Does every name and every claim in it actually exist?

The checklist, to keep:

  1. Does it run? The cheapest check, and the least informative. Running rules out only the failures loud enough to crash something.
  2. Does it do the right thing? Pick one record whose correct answer you already know and check it by hand against the source data.
  3. Is the input handled safely? Any value a user types, a form sends, or another script passes in belongs in a parameter, never pasted into a query string.
  4. Does it clean up after itself? Connections, files, and anything else opened should close on every path out, including the one where something failed.
  5. Does every name and claim actually exist? Check column names, method names, and the description. An AI can invent any of the three and sound exactly the same doing it.

Five questions, in that order, on anything an AI hands you. That order is the point: the cheap checks first, and the ones that catch real damage last, because those are the ones worth your remaining attention.

12. How this shows up in interviews

"Do you have a mental checklist for reviewing AI-written code?" and "tell me about a time you caught an AI tool making a mistake" are both live questions in junior data and engineering interviews right now. The reason they get asked is simple. Everyone's AI tool produces code that runs, so running is no longer evidence of anything. What an interviewer wants to hear is a process.

A weak answer is a feeling: "I look it over and if something seems off I rewrite it." A strong answer is an order of operations plus one real example. Name your checks in the order you run them, then tell a short, specific story: the line, what it actually did, and what you typed instead. The five checks in section 10 are a genuine answer to the first question, and the function you just reviewed is a genuine answer to the second.

The same question shows up on the engineering side with one extra beat. There, they will often push on the tradeoff out loud: reviewing every AI-written line as carefully as writing it yourself can erase the time the tool saved. The honest answer is that you spend your attention where the damage is, which is why raw input, cleanup, and invented names sit at the bottom of the checklist rather than the top.

Interview-style question: a teammate says an AI-drafted function is "obviously fine" because it ran once on a real id and returned rows. What is still missing from that check?

13. Summary & critical thinking

One idea carried this whole reading: "it runs" and "it is correct" are two different claims, and only one of them gets proven by clicking run. The AI's draft opened a connection, built a query, and returned rows, all of it fluent and all of it fast. It still pasted typed input into SQL, still leaked its connection the moment anything failed, and still described itself wrongly in the one place people look.

None of those three announced themselves. That is the part worth keeping: the problems that matter most are usually the quiet ones, and the only thing that finds them is a person reading the code on purpose, in an order they decided in advance.

New situation: you ask an AI assistant for a function that deletes a customer's saved payment method by customer id. It runs, and it deletes the right one in your test. Following the checklist, which check would you spend your attention on first?
