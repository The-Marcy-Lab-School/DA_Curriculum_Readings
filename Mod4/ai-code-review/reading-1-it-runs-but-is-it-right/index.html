It Runs. But Is It Right?

A library helper asks an AI assistant for a function that looks up one library card's borrowing history. Ten seconds later the function arrives. It runs, four real-looking rows come back, and nothing turns red. Is it finished? Running only proves it didn't crash. Checking the rest takes a careful read, in a set order.

1. A function that runs

Rosa helps with the data at Maple Street Library. Every book checked out is one row in a loans table, in a PostgreSQL database. Rosa needs a function that looks up one card's borrowing history for the front desk, and asks a free AI assistant to write it.

The next step is a code review: reading someone else's code closely enough to catch what is wrong with it before anyone relies on it.

3. The AI's draft

Rosa asked

"Write a Python function that takes a library card number and returns its borrowing history from our PostgreSQL database."

The AI replied

"Here's a clean function for that. It opens a connection, runs the lookup, and closes the connection when it's done."

New in this file: the text in triple quotes under def is a docstring, a note telling people what the function does. This file needs a running database, so the Run button shows what it prints against the library's real loans table.

Predict: Rosa runs loan_history.py with card 4102. What kind of value prints?

import os import psycopg2 def get_loan_history(card_number): """Return every book this card has checked out. Raises an error if no card with that number exists. """ conn = psycopg2.connect(os.environ["DATABASE_URL"]) cur = conn.cursor() query = f"SELECT title, branch FROM loans WHERE card_number = '{card_number}'" cur.execute(query) rows = cur.fetchall() conn.close() return rows print(get_loan_history("4102"))
[('Hatchet', 'Main'), ('Wonder', 'Main'), ('Holes', 'Eastside'), ('Matilda', 'Main')]

What kind of value prints?

Every claim the AI made sounds true: it opens a connection, runs the lookup, and calls conn.close(). A careful read still finds three problems.

4. Problem one: the query is built from raw input

The query = f"..." line pastes whatever card_number holds into the query text, and the database reads the whole finished string as SQL. Suppose someone types 4102' OR '1'='1 into the card-number box. build_query.py builds the query the same way the draft does.

card_number = "4102' OR '1'='1" query = f"SELECT title, branch FROM loans WHERE card_number = '{card_number}'" print(query)
SELECT title, branch FROM loans WHERE card_number = '4102' OR '1'='1'

Run build_query.py first. What does the database do with the query it prints?

Need a hint?

Read the part after WHERE as two tests joined by OR. Is '1'='1' ever false?

That is SQL injection: typed text gets read as SQL instead of as data, so it changes what the query does. No error appears. The function just returns the wrong rows, including other people's borrowing history.

The fix is a parameterized query: you leave a placeholder, %s in psycopg2, in the query text and hand the real value to cur.execute separately. The driver treats that value as data only.

Your turn: send the value separately

The new query text is query = "SELECT title, branch FROM loans WHERE card_number = %s", with no quote marks around %s.

  1. Type the line that runs the query: cur.execute(, then query, then a comma.
  2. After the comma, put card_number inside a one-item tuple: parentheses with a comma after the value, like (x,). The comma is what makes it a tuple.
  3. Close the execute call with ) and press Check. You get 2 tries. Why: the value travels on its own, so typed text can't rewrite the query.

5. Problem two: the connection that stays open

The AI said the function "closes the connection when it's done." That holds only when nothing goes wrong.

In loan_history.py, suppose cur.execute(query) fails because the database is briefly unreachable. Does conn.close() still run?

That leftover is a connection leak: a connection your code opened and never closed, so the server keeps holding it. Enough leaks use up the server's connection slots and block everyone's work. The fix: put conn.close() in a finally block, so it runs on every way out of the function, even after a return.

6. Problem three: a promise the code never keeps

Read the docstring again: "Raises an error if no card with that number exists." Now look for the line in the function that would do that. There isn't one.

At the front desk, Rosa mistypes one digit and calls get_loan_history("4012"). No loans match card 4012. What does the draft return?

This is a hallucination: an AI stating something that sounds confident and correct but is made up. The docstring said an unknown card raises an error. No error came, so Rosa tells the librarian the card has borrowed nothing, when the real card 4102 has four books out.

What is the honest fix for the docstring?

7. The fixed function

Three things changed: the docstring tells the truth, the value travels separately, and finally closes the connection every time.

import os import psycopg2 def get_loan_history(card_number): """Return every book this card has checked out. Returns an empty list if the card has no loans on file. """ conn = psycopg2.connect(os.environ["DATABASE_URL"]) query = "SELECT title, branch FROM loans WHERE card_number = %s" try: cur = conn.cursor() cur.execute(query, (card_number,)) return cur.fetchall() finally: conn.close() print(get_loan_history("4102")) print(get_loan_history("4012")) print(get_loan_history("4102' OR '1'='1"))
[('Hatchet', 'Main'), ('Wonder', 'Main'), ('Holes', 'Eastside'), ('Matilda', 'Main')]
[]
[]

The strange input now returns []: the database compares the whole text to real card numbers and finds no match. Here is the order of checks you just used:

  1. Does it run? This rules out only the loudest failures.
  2. Does it do the right thing? Check one record you already know by hand.
  3. Is input handled safely? Any typed value belongs in a parameter, never pasted into the query text.
  4. Does it clean up after itself? Connections should close on every path, including errors.
  5. Is every name and claim real? Check column names, method names, and the docstring.

9. Wrap-up

  • "It runs" and "it is correct" are two different claims. Only the first one is proven by clicking Run.
  • Pasting typed input into SQL allows SQL injection. A parameterized query with %s sends the value separately.
  • Close connections in finally, and check that every docstring and name matches what the code really does.
