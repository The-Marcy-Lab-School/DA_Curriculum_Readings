The Export Is Already Stale

An online plant shop saved its orders table to a file yesterday at 5:02 PM. This morning an analyst used that file to count the orders still waiting to ship, and the number was wrong. Nothing in the code was broken. The file was just old. The fix is to let Python ask the live database directly.

1. A saved file goes out of date

Fernhaven is an online plant shop. Every order is one row in an orders table, in a PostgreSQL database (often called "Postgres").

The file was right at 5:02 PM and behind by 5:03. Analysts ask the same questions every day, so a file someone must remember to re-save will sooner or later give a wrong number. You already know SQL and pandas. Connecting them means fresh rows every time the code runs.

3. The first way: a driver and a cursor

Fernhaven's database runs on a server, a computer that stays on all the time. Python needs a driver to talk to it: a library that speaks one specific database's language for you. The usual PostgreSQL driver is psycopg2.

  • A connection is an open, live link between your running program and the database. It stays open until something closes it.
  • A cursor is the psycopg2 object you send SQL through and read rows back from. It works on top of an open connection.

The files in this reading need a running database, so the Run button shows what each one prints against Fernhaven's real orders table.

New in this file: os.environ["DATABASE_URL"] reads a setting called DATABASE_URL that your computer stores outside the file. Section 5 explains why. cur.execute(sql) sends the query, and cur.fetchall() brings back every matching row. cur.description has one entry per column, and the first item in each entry, column[0], is that column's name.

Predict: what does the first print in open_orders_psycopg2.py show?

import os import psycopg2 import pandas as pd sql = "SELECT order_id, plant, status FROM orders WHERE status = 'open' LIMIT 3" conn = psycopg2.connect(os.environ["DATABASE_URL"]) cur = conn.cursor() cur.execute(sql) rows = cur.fetchall() print(rows) cols = [] for column in cur.description: cols.append(column[0]) open_orders = pd.DataFrame(rows, columns=cols) print(open_orders) conn.close()
[(5521, 'Snake plant', 'open'), (5524, 'Pothos', 'open'), (5530, 'Monstera', 'open')]
   order_id        plant status
0      5521  Snake plant   open
1      5524       Pothos   open
2      5530     Monstera   open

What does print(rows) show?

The driver sent back values with the labels stripped off. The for loop collected the column names, and pd.DataFrame(rows, columns=cols) put the two back together.

4. The second way: an engine and one call

SQLAlchemy is a Python toolkit for databases. Its engine is a reusable connection manager for one database: it knows where the database is and hands out a connection when you ask. Underneath, SQLAlchemy still uses psycopg2.

New in this file: from sqlalchemy import create_engine brings in one name from a library. with engine.connect() as connection: works like with open(...) as f:. You borrow a connection, and it is given back when the indented block ends, even if something inside fails.

Predict: compared with the table open_orders_psycopg2.py printed, what does open_orders_sqlalchemy.py print?

import os import pandas as pd from sqlalchemy import create_engine sql = "SELECT order_id, plant, status FROM orders WHERE status = 'open' LIMIT 3" engine = create_engine(os.environ["DATABASE_URL"]) with engine.connect() as connection: open_orders = pd.read_sql(sql, connection) print(open_orders)
   order_id        plant status
0      5521  Snake plant   open
1      5524       Pothos   open
2      5530     Monstera   open

What does open_orders_sqlalchemy.py print?

The cursor, the fetch, and the loop that collected names all turned into pd.read_sql(sql, connection), because pandas reads from a SQLAlchemy connection directly and brings the column names along.

5. Keep the password out of the file

A connection needs a password. The quick way is to type it into the file, and it works right away:

import psycopg2 conn = psycopg2.connect("postgresql://analyst:Spring2026@fernhaven-db/store")

Now the password is part of the file. Push it to GitHub and the password is on GitHub, and deleting the line later doesn't help, because git keeps old versions. An environment variable fixes this: a value your computer holds for a program, stored outside the code. You set DATABASE_URL once, the code reads it by name, and the password never appears in anything you commit.

6. Close what you open, every time

The website and other analysts connect to Fernhaven's database too. A PostgreSQL server has a connection limit, a fixed number of connections it allows at once (often 100). Past it, new requests are refused with an error like too many clients already. A script that runs all day without closing its connections fills those slots, and the error lands on someone else.

open_orders_psycopg2.py calls conn.close() on its last line. But if cur.execute(sql) fails, Python stops at that line and the close never runs. Python has a block for this.

New in this file: finally: pairs with try:. Python runs the finally block on the way out of the try, whether the try block finished or hit an error.

Predict: finally_demo.py stands in for a query that fails. Which lines print?

try: print("Running the query...") count = int("five") print("Got", count, "rows") finally: print("Closing the connection.")
Running the query...
Closing the connection.
Traceback (most recent call last):
  File "finally_demo.py", line 3, in <module>
    count = int("five")
ValueError: invalid literal for int() with base 10: 'five'

Which lines does finally_demo.py print before the error message?

The error still shows, so you learn what went wrong, but the connection gets closed first.

Here is the safe version of the Fernhaven file, with conn.close() in a finally block:

import os import psycopg2 import pandas as pd sql = "SELECT order_id, plant, status FROM orders WHERE status = 'open' LIMIT 3" conn = psycopg2.connect(os.environ["DATABASE_URL"]) try: cur = conn.cursor() cur.execute(sql) rows = cur.fetchall() cols = [] for column in cur.description: cols.append(column[0]) finally: conn.close() open_orders = pd.DataFrame(rows, columns=cols) print(open_orders)
   order_id        plant status
0      5521  Snake plant   open
1      5524       Pothos   open
2      5530     Monstera   open

8. Wrap-up

  • A live connection gets fresh rows every time the code runs. A saved file is only true for the moment it was saved.
  • With psycopg2, you use a cursor and add the column names yourself. With a SQLAlchemy engine, pd.read_sql does it in one call, and psycopg2 still does the talking underneath.
  • Keep the password in an environment variable, and close every connection in a finally block or a with block.

New situation: Fernhaven runs a short script every morning. It opens a connection, reads yesterday's orders, writes a report, and stops. The password is typed into the file, and the connection is never closed. Which review comment is more urgent, and why?

In interviews, "walk me through connecting a Python script to a database" is common, and a strong answer names both habits: where the password lives and how the connection gets closed.
