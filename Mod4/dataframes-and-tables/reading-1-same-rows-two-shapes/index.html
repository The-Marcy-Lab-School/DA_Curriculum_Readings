Same Rows, Two Shapes

An animal rescue keeps every adoption it has ever completed as one row in a database table. Today those same rows also have to show up inside Python, so they can be counted and charted. Nothing about the rows changes along the way. What changes is the container holding them, and the container decides which computer actually does the work.

1. Introduction

Second Chance Paws is a small animal rescue. It is a nonprofit, meaning it runs on donations and grants rather than profit, and its whole job is taking in stray and surrendered pets and finding them new homes. Every adoption it has ever completed is recorded once, in a table called adoptions, inside a database: a program that stores an organization's data and answers questions about it. Each row of that table is one adoption. The columns record which animal it was, what species, when the animal arrived, when it went home, and which town the adopter lives in.

The board of directors wants one small answer before its next meeting: how many adoptions did we complete for adopters in Riverton, broken out by species? You could get that answer by writing SQL (Structured Query Language, the language you write to ask a database for rows). You could also get it in Python using pandas, a library built for working with tables of data. Both paths end at the exact same three numbers. They do not run on the same computer.

The two boxes in that picture hold identical data. Three rows, three named columns, and one kind of value per column in both. The words differ: the database calls a whole-number column INTEGER, pandas calls it int64; the database calls a text column TEXT, pandas labels it object, which is simply how pandas prints "this column holds text." The real difference is the arrow. The top box lives on a server, a computer that runs all the time and holds the organization's data for everyone. The bottom box lives in your own computer's memory, the fast, temporary workspace a program uses while it is running.

Why this matters: almost every data analyst job description lists SQL and Python side by side, and the reason is this exact handoff. A very common interview question is "should this aggregation happen in SQL or in pandas?" There is also a practical stake with no interviewer involved: on a real table with millions of rows, pulling everything into Python so you can count it does not raise an error. It just leaves you staring at a frozen laptop for twenty minutes to produce three numbers the database could have handed you instantly.

Where you're coming from, where this is headed: you already know how to ask a database for rows with SELECT and narrow them with WHERE, and you already know how to keep only some rows of a table in pandas. This reading lines those two skills up against each other so the same question can be written either way on purpose, not by habit. Once a query result and a table in memory feel like one idea in two containers, connecting Python straight to a live database stops being a new subject and becomes a small next step.

A SQL table is three things at once: a set of rows, a set of named columns, and one declared type per column that the database itself enforces. Nobody can slip the word "soon" into adoption_date, because the column was declared to hold dates and the database refuses anything else.

Load those same rows into Python with pandas and you get a DataFrame: a table held in your computer's memory, with rows, named columns, and one type per column. Pull a single column out of it on its own, like adoptions["species"], and that one column is called a Series. The type pandas gives a column is called its dtype, short for data type. The part people get wrong: a DataFrame is a copy. When those rows land in pandas, the database still has its own originals, untouched. If you rename a column, drop a row, or fix a misspelled town name in the DataFrame, you have changed your copy and nothing else. The shelter's official record is exactly as it was. Think of it like copying a list off the office wall onto your own whiteboard: scribble all you want on the whiteboard, the wall still says what it said.

That cuts both ways. It means you can experiment freely without any risk of damaging real data, which is genuinely useful. It also means anything you "fixed" in pandas is fixed only for as long as that Python program is running. Close the program and the copy is gone.

5. The board's question, written twice

Back to the board's question: how many Riverton adoptions, by species? In SQL it is one statement, and the database does all of it.

SELECT species, COUNT(*) AS adoptions FROM adoptions WHERE adopter_town = 'Riverton' GROUP BY species;

In pandas it is two lines, and they do the same three jobs in the same order.

riverton = adoptions[adoptions["adopter_town"] == "Riverton"] riverton["species"].value_counts()

Line by line, the pieces line up:

  • WHERE adopter_town = 'Riverton' becomes adoptions["adopter_town"] == "Riverton". That comparison runs once per row and produces one True or False per row. Handing that back to adoptions[...] is what actually keeps the True rows.
  • SELECT species becomes riverton["species"], which pulls out that one column as a Series.
  • GROUP BY species plus COUNT(*) together become .value_counts(), which counts how many times each value shows up in that column.

One real difference is reading order. SQL names the columns first and filters lower down. pandas filters first and picks the column afterward. Same result, opposite reading direction, which is exactly why the translation feels awkward the first few times even when you understand both sides.

7. Where the work should happen

Six rows is a toy example, so the two versions feel equally good. Now picture the real table. Second Chance Paws has been operating for thirty years and shares its database with a regional network of shelters, so adoptions holds 4,000,000 rows. The board still wants the same three numbers.

Option 2 is not wrong in the sense of giving a wrong answer. It gives the right answer, eventually. The cost is that 4,000,000 rows have to travel across the network to your machine, and then all of them have to fit in your computer's memory at once, so that pandas can throw away almost all of them and report three numbers. The database was already sitting on those rows and is built to count them in place.

The useful habit is to shrink the data in SQL first, then analyze what comes back in pandas. A few hundred rows in a DataFrame is a pleasure to work with. Four million is a stalled laptop.

8. The tool that installs pandas: uv

pandas does not come with Python. It is a package, a bundle of code somebody else wrote and published so other people can install and use it. Getting packages onto your machine has traditionally meant two separate tools: pip, Python's original package installer, and venv, which creates an isolated environment so one project's packages do not collide with another project's.

uv is a single command line tool that does both of those jobs. It is made by a company called Astral, and it is described as a Python package and project manager, an alternative to reaching for pip directly. There are two reasons a project chooses it:

  1. Speed. Astral measures uv as being many times faster than pip at installing packages. That figure comes from the company's own published benchmark, so treat it as strong evidence rather than a neutral fact, but the everyday experience of it being noticeably quicker is easy to confirm yourself.
  2. Reproducibility. uv writes a lock file: a record of the exact version of every package that was installed. Anyone who sets the project up later gets those same versions instead of whatever happens to be newest that day.

That second reason is the one that matters most on a team. Analysis code that runs perfectly for you and crashes for a teammate is almost always a version difference nobody wrote down. A lock file writes it down. It does not stop you from upgrading anything; it just makes an upgrade a deliberate, visible change instead of something that quietly happens to you.

10. How this shows up in interviews

"Should this aggregation happen in SQL or in pandas?" is a standard question in data analyst interviews, and it is deliberately underspecified. The interviewer is not checking whether you can name a winner. They are checking whether you ask how big the table is before answering, because the size of the table is the whole answer.

A strong response names the missing information out loud, then commits: "How many rows are we talking about? If it is millions and I only need counts per species, the database should run the grouping and hand me a few rows. If I guess wrong and pull everything, I spend network time and memory on rows I am about to throw away. So I would aggregate in SQL, then shape and chart the small result in pandas."

A second question shows up almost as often: "explain what a DataFrame is to someone who only knows SQL." That one rewards building on what they already have. It is a table living in Python's memory, with rows, named columns, and one type per column, and it is a copy, so changing it never touches the original.

Interview-style question: you load a query result into a DataFrame, clean up three misspelled town names, and save your Python file. A teammate then queries the database directly and still sees the misspellings. Why?

11. Summary and critical thinking

Two ideas carried this whole reading. First, a database table and a pandas DataFrame hold the same thing: rows, named columns, and one type per column, just under two different vocabularies. Second, they do not live in the same place. The table sits on a server and the database does the work; the DataFrame is a copy in your own computer's memory and your own machine does the work. That second point is what turns "either tool works" into a real decision once the table gets big.

New situation: a city bike share program has a trips table with 9,000,000 rows. You need the average trip length for each of its 40 stations, for one month, so you can chart it. Which plan is the better first move?

12. Thinking ahead

Everything above assumed the rows had already made it from the database into Python somehow. The step that was skipped is the interesting one: opening a real connection from your Python program to a live database, sending a query across it, and receiving the result directly as a DataFrame with no file in between. That is where "shrink it in SQL first, analyze in pandas after" stops being advice and becomes something you write in a single block of code. The choice practiced here, deciding how much data crosses that line, is exactly the decision you make every time you write that block.
