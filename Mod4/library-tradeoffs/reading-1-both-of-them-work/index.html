Both of Them Work

A small movie theater runs one script every night at 2 AM. It counts yesterday's tickets for each movie and saves a report. Two teammates both know how to write it, with the same query and the same DataFrame at the end. One wants psycopg2. The other wants SQLAlchemy. Both of them work, so how do you choose?

1. Two teammates, one script

At Starlight Cinema, every ticket sold is one row in a tickets table, in a PostgreSQL database. Nia and Samir agree on the nightly script's query and its DataFrame. They disagree about one line near the top.

  • Nia wants psycopg2: one small library, little to learn, and errors straight from PostgreSQL.
  • Samir wants SQLAlchemy: it manages connections for you, and moving to a different database changes one line.

"What would make you pick SQLAlchemy over the raw driver?" is a common interview question. A strong answer names a fact about the script, not the library.

3. Stacked, not side by side

The two options are not two separate roads: SQLAlchemy uses psycopg2 underneath. psycopg2 is the driver, the library that speaks PostgreSQL's own language. Samir's option is the driver plus one more layer.

That extra layer is an abstraction layer: code that hides messier details behind a simpler set of things to call. Think of the popcorn button on a microwave. It picks the time and power for you, and most nights it does fine. On the bag that needs 15 more seconds, you have to take over. The layer saves you work and takes away some control.

SQLAlchemy also includes an ORM (object-relational mapper), a tool for working with rows as Python objects instead of writing SQL. Every example here skips it.

4. Tradeoff one: moving to a different database

Every database speaks its own version of SQL. In SQLAlchemy, a dialect is its translation for one specific database and its driver. SQLAlchemy's engine, its reusable connection manager, reads the start of the database address and picks the dialect and driver for you.

So moving to a different database means changing one line, the address. For example, you can test against SQLite, a small database stored in one file, then run against the real PostgreSQL database.

New in this file: engine.dialect.name is the database an engine is set up for, and engine.dialect.driver is the driver it will use. Making an engine doesn't connect yet, so no live database is needed.

What moves is the connection code. The SQL text does not become portable. A plain SELECT usually runs anywhere, but date functions, data types, and other details differ between databases, and no layer hides that.

5. Tradeoff two: reusing connections

Each new connection costs the server real work: PostgreSQL starts a separate running program for it, gives it memory, and checks the password before your query runs. Once, that is too small to notice. Thousands of times a day, it adds up. A connection pool fixes this: a small set of open connections kept ready and handed out when needed. Think of the front desk in an office building. Instead of printing a new visitor badge for every guest, the desk keeps a stack of badges and hands each one out again when it comes back.

A SQLAlchemy engine has a pool turned on by default. psycopg2 can pool too, but you set it up yourself. A pool only helps a script that connects again and again.

7. Pick a library, and say why

One more tradeoff is how much there is to learn. psycopg2 is small. SQLAlchemy has more parts, but pandas reads from it in one call.

9. Wrap-up

  • SQLAlchemy sits on top of psycopg2. The choice is how many layers you want, not which road you take.
  • The extra layer gives you a pool by default, a database address you can swap, and one error type. It costs some control and more to learn.
  • Pick by a fact about the script: how often it connects, how long it runs, whether it will move, and who looks after it.

New situation: Starlight changes the nightly report. Now it runs every time a staff member clicks "recount this showing," hundreds of times a day, opening a connection each time. What changed, and what does it do to the choice?

In an interview, say the pick first, then the fact about the script that decided it.

The same habit of looking underneath code that works applies next to code an AI assistant writes for you.
