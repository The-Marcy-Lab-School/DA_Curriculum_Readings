Write It Once

Terra Bean Coffee Roasters gets a shipment log emailed in from five different green-coffee suppliers every month. Every log has a supplier_name column, and every log spells the same five names a different way: extra spaces, ALL CAPS, a stray period, sometimes nothing typed at all. Fixing that by hand in a notebook cell works fine the first time. The second time, someone tweaks the fix slightly. The third time, someone forgets a step entirely, and now July's numbers are quietly wrong. Whether you already know how to drop, fill, or flag a single gap and how to write a function with a parameter and a return, the real skill here is combining both into one thing you write once, trust, and call again on every column and every new file that shows up with the same mess.

1. Concept overview

Picture the May shipment log open in a notebook. The supplier_name column has values like " BLUE MOUNTAIN COFFEE CO. ", "blue mountain coffee co.", and "Blue Mountain Coffee Co.", all meant to be the same supplier. A quick fix in one cell handles it:

df["supplier_name"] = df["supplier_name"].str.strip().str.title()

June's log arrives a few weeks later. Same mess, so the fix gets copied down and re-run, except this time a few rows came back completely blank, and nobody remembers to handle that, so fillna never gets added. July's log arrives, the fix gets copied a third time, and this time .str.title() gets swapped for .str.upper() by accident while someone's mid-scroll. Three notebook cells later, the same "clean this column" idea has three slightly different, undocumented implementations, and a report that groups shipments by supplier now shows fourteen suppliers instead of five.

None of that is a knowledge problem. Whoever wrote each fix already knew the right pandas methods. It's a repetition problem: the same logic, retyped by hand, drifts a little more every time it's retyped. The fix is the same one you already reach for anywhere else in Python when logic needs to run more than once: wrap it in a function, with a real parameter and a real return value, and call that function every time instead of retyping its body.

Why this matters: a take-home data project that fixes a column inline three separate times instead of writing one function is one of the fastest tells a reviewer or interviewer has that cleaning was done ad hoc, not deliberately. It's also a real, recurring cost: a monthly shipment log means this exact mess shows up again next month, and again the month after.

Where you're coming from, where this is headed: you already know how to decide whether a specific missing value should be dropped, filled, or flagged, and you already know how to write a function with a def, a parameter, and a return. Neither of those is new here. What's new is combining them: writing one function whose job is "take a raw column in, hand a clean column back," with the missing-value decision built into that same function instead of re-decided by hand every time.

13. How this shows up in interviews

A take-home data project that hardcodes the same cleaning logic inline two or three times, instead of writing one function and calling it, is one of the fastest, most common red flags a reviewer looks for. It signals the cleaning decisions weren't actually deliberate, they were retyped by feel each time, and it's exactly the kind of thing that shows up as drift the moment a new file arrives.

Interviewers will sometimes hand you a notebook with three near-identical cleaning cells and ask "how would you refactor this?" The strong answer names the actual contract: what should the function take in, what should it hand back, and does the missing-value handling belong inside that function or outside it, not just "put it in a function."

Interview-style question: you're reviewing a candidate's take-home project and see the exact same three-line cleaning snippet pasted into four different cells, each fixing a different column. What's the strongest note to leave?

15. Summary & critical thinking

One idea carried this whole reading: the same judgment you already use to clean one column by hand belongs inside a function with a real contract, a raw column in, a clean column out, so it gets written once and trusted every time after, instead of retyped and drifting.

New situation: a small logistics company receives a driver_name column from three different partner apps, each formatted differently, in a file that arrives daily. What's the strongest first move?

16. Thinking ahead

Once one column has a real cleaning function, the same shape keeps paying off: a second messy column in the same file often needs the exact same steps, and a file that arrives again next month can be cleaned by calling the function again, not by remembering what was typed by hand last time. The judgment stays the same. Only the reach of the code that carries it out gets bigger.
