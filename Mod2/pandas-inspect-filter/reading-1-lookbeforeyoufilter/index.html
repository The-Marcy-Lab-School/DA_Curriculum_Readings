Look Before You Filter

A regional food bank logs every donation drop-off in a spreadsheet: who gave it, what kind of food it was, how much it weighed, which pantry site received it. Before anyone can answer a real question about that data, it has to be loaded into a tool built for tables, not just scrolling text. That tool is pandas, and the object it hands back is called a DataFrame. This reading is about the very first thing every data analyst does with one: looking at it honestly before trusting it, then keeping only the rows that actually matter for the question being asked.

1. Concept overview

Priya coordinates data and operations for a three-site regional food bank. Every night, volunteers log each donation as one row in a shared spreadsheet: the donor type, the food category, the weight in pounds, and which pantry site received it. Priya's board wants to know something real this quarter: is donation weight spread evenly across sites, or does the network depend on a handful of huge corporate drop-offs? Before she can answer that with any honesty, she has to load the log into a tool that treats it as an actual table she can question, not just text on a screen. For almost every working data analyst, that tool is the pandas library, and the object it hands back is called a DataFrame.

A DataFrame is the spreadsheet, loaded into Python, as a real object: each row is one donation, each column is one recorded field about it, and every column holds one consistent type of value (all numbers, or all text, never mixed). Pull a single column out on its own — just the weights, say — and what's left is called a Series: a DataFrame is really a collection of Series that all share the same row index.

Why this matters: Priya's food bank is renewing a grant this quarter, and the renewal report needs an honest count and an honest picture of donation sizes. If she trusts whatever pandas loaded without ever actually looking at it, a real problem slides straight into her numbers unnoticed: a donation logged with no weight recorded yet, a column that loaded as text instead of numbers, a row count that's smaller than she expected because a file only half-loaded. Every experienced analyst runs the same handful of checks before touching real data, precisely because skipping them is how quietly wrong numbers end up in front of a stakeholder.

Here is a small slice of Priya's real log, six rows of it, called intake:

donor_type category weight_lbs site Individual Produce 12 Downtown Corporate Canned Goods 85 Eastside Grocery Partner Dairy NaN Downtown Individual Bakery 8 Westside Corporate Produce 63 Eastside Grocery Partner Frozen 51 Downtown

Four questions get asked of almost any new DataFrame before anything else happens to it:

  • intake.shape — how many rows and columns are there? No parentheses: .shape is an attribute, a stored fact about the object, not an action it performs. For intake, this is (6, 4): 6 rows, 4 columns.
  • intake.columns — what are the exact column names, spelled and cased exactly as pandas sees them? Also an attribute. Getting this exactly right matters in a few sections, because a filter written against a column name that's spelled slightly wrong fails loudly (or worse, silently does nothing close to what was intended).
  • intake.head() — a real preview of the actual values, the first 5 rows by default. This one is a method: it does something (builds and returns a preview), so it needs parentheses, even with nothing inside them.
  • intake.info() — a one-shot summary of every column: its data type, and how many non-null (non-missing) values it actually has out of the total row count. Also a method.

That last one is exactly how a problem like the missing weight above gets caught before it causes trouble. Running intake.info() on this data would report that weight_lbs has only 5 non-null values out of 6 rows: one donation came in before it was weighed. Catching that now, during inspection, means Priya can make a deliberate decision about it later. Missing it now means it just quietly participates in whatever she calculates next.

Read the diagram left to right: the six colored bars on the left are the six real rows, split into their four columns — the cell with a question mark is the missing weight from row 2. The middle column applies one condition, weight_lbs > 50, to every row and produces exactly one True or False per row: that column of booleans is called a boolean mask. On the right, pandas uses that mask to keep only the rows marked True, in their original positions, and drop the rest. Notice the missing-weight row: comparing a missing value to a number never raises an error, it just quietly evaluates to False, so that row gets dropped from this filter without any warning at all. That's worth remembering, and it comes back later in this reading.

In code, that whole right-hand result is one line:

big_drops = intake[intake["weight_lbs"] > 50]

Two conditions can be combined with & (and) or | (or) — not Python's plain and/or, which don't work row-by-row across a whole column — and each condition needs its own parentheses:

produce_drops = intake[(intake["weight_lbs"] > 50) & (intake["category"] == "Produce")]

And when the goal is a single column from a filtered result, not the whole row, .loc[] takes both the mask and the column name in one step:

intake.loc[intake["weight_lbs"] > 50, "donor_type"]

Why this matters: "which pandas method fits this question" is a skill graded directly the first time a project asks for it unguided, and it starts here: nearly every later step, comparing groups, building new columns, choosing a chart, only works on data that was inspected and filtered correctly first. Get this wrong quietly (a misspelled column name, a filter that silently drops rows because of a missing value) and every number built on top of it inherits the mistake.

Where you're coming from, where this is headed: you already know how a comparison like x > 50 evaluates to True or False, and how square brackets pull one item out of a list by position. This reading is about that same comparison running once per row across an entire column at once, and square brackets used to keep only the rows where it came out True. Once filtering rows down to the ones that matter feels automatic, the next idea builds directly on it: comparing groups of rows against each other, and building brand-new columns computed from the ones already there, instead of reading the same values over and over.

13. How this shows up in interviews

Basic pandas fluency, loading a file, checking its shape, filtering it, is treated as an assumed baseline in almost every data-analyst technical screen. It's rarely asked about directly; it's just expected to already be automatic by the time a harder question about the actual data shows up.

A very common live-coding moment is being handed a small DataFrame and asked to filter it on the spot, sometimes with two conditions combined. Interviewers are watching for the parentheses-around-each-condition habit and &/| instead of and/or, since getting that wrong is the single most common pandas mistake among people who are otherwise strong Python programmers.

A sharper follow-up question tests exactly what section 1's diagram showed: "if a column has a missing value and you filter for column greater than some number, what happens to that row?" Naming that it's silently excluded, because comparing NaN to a number always evaluates to False, is a strong, specific answer that a guess-based answer won't produce.

Interview-style question: a column has a missing value in one row, and you filter with df[df["col"] > 50]. What happens to that row?

15. Summary & critical thinking

Two habits carried this whole reading: always inspecting a new DataFrame with .shape, .head(), .info(), and .columns before trusting it, and thinking of a filter as a two-step move: build a boolean mask with a condition, then use that mask to keep only the matching rows.

New situation: a small veterinary clinic keeps a visits DataFrame with a cost column and a visit_type column. Which line correctly keeps only visits where cost is over 200 AND visit_type is "Surgery"?

16. Thinking ahead

Filtering answers one kind of question: give me only the rows that match. The next idea builds directly on it: comparing groups of rows against each other, like average donation weight per site, instead of reading one row at a time, and creating brand-new columns computed from the ones already there, instead of recalculating the same formula by hand every time it's needed. Both of those start from exactly the same DataFrame habits practiced here.
